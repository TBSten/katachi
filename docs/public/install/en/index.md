# Installing katachi

These are the steps to install [katachi](https://tbsten.github.io/katachi).

You will create an architecture definition that fits the user's codebase.

**Everything that can be done mechanically is handled by `katachi-install.sh`.** Do not supplement the steps yourself.

You are only responsible for judgment in the following:

- Step 1 — Analyzing the codebase
- Step 3 — Writing the `architecture { }` definition
- Step 4 — Deciding whether to fix or leave remaining architecture violations
- Step 6-A / 6-B — Planning a sample task, wiring up CI

**Do not rewrite the `build.gradle.kts` generated by `scaffold`, or the `settings` / root build files it appended to.** `ProjectArchitecture.kt` is the exception, since it is what you fill in during step 3.

## 0. Preparation

### 0-1. Get all permissions up front

These steps repeat network access, file creation, and running Gradle many times over. Checking in every time would leave the user doing nothing but approving requests endlessly. **Run the following, show the resulting text to the user exactly as it is, and get approval for everything at once.**

```sh
curl -fsSL -o /tmp/katachi-install.sh https://tbsten.github.io/katachi/install/katachi-install.sh
sh /tmp/katachi-install.sh permissions
```

Do not compose the text yourself. Skip any operation the user declines, and record what could not be done in the checklist's `questions`.

At this point `$CLI` does not exist yet. Record the check at the end of the next step, together.

### 0-2. Run init

Run the following **from the Gradle root directory**.

```sh
sh /tmp/katachi-install.sh init --lang en
```

> `--lang en` tells the script which language to fetch the checklist and report templates in. Japanese is available as `--lang ja`.

The script was already fetched in 0-1. **`curl` runs only once across the whole procedure** — `init` copies itself into the working directory, and every command from here on uses that copy.

This command does all of the following. **Do not redo any of this by hand.**

- Confirming this is a Gradle project (stops if not)
- Checking whether it's under Git management (warns if not)
- Deciding on and creating the working directory (inside a `.gitignore`d location if one exists, otherwise `tmp/install-katachi/`)
- Fetching the latest version of katachi
- Detecting the Kotlin version the project uses
- Placing `check-list.html` and `project-code-base-report.html`
- Initializing the checklist's JSON (working directory / version / project root / date-time / Kotlin / Git)
- Placing itself at `<KATACHI_WORKDIR>/katachi-install.sh`

At the end, the result is printed in the following format (a few lines of guidance follow after it). The steps from here on use these values.

```
KATACHI_WORKDIR=tmp/install-katachi
KATACHI_VERSION=0.1.0
KATACHI_PROJECT_ROOT=/path/to/project
KATACHI_KOTLIN=2.4.10
KATACHI_GIT=yes
KATACHI_SETTINGS=settings.gradle.kts
KATACHI_CLI=tmp/install-katachi/katachi-install.sh
```

**All commands from here on are run with the `KATACHI_CLI` path.** The one in `/tmp` is not used.

Once this is done, run `sh $CLI check 0-1 0-2`.

**If it stops, handle it exactly as the output says.** Do not invent a workaround. To change the working directory, re-run with `--workdir <path>`; to pin a version, re-run with `--katachi <version>`.

`init` **never breaks already-filled-in files no matter how many times you run it.** If it fails partway through, you may just re-run it as is.

Whenever you need temporary storage from here on, save it inside `<KATACHI_WORKDIR>/tmp/`, and do not clutter the top level of the working directory.

### 0-3. Reading and writing the checklist and report

`check-list.html` and `project-code-base-report.html` are **single HTML files that carry their data as JSON inside them.** The HTML is only a rendering shell — **the only thing you read or write is the JSON.**

```sh
# From here on, wherever `$CLI` appears, read it as the KATACHI_CLI path that init printed.
# Shell variables don't persist across calls, so write out the path every time.
CLI=<path to KATACHI_CLI>

# Read (only JSON is printed; there's no need to read the HTML)
sh $CLI data get report
sh $CLI data get check-list

# Update just part of it (deep-merged into the existing content; use this normally)
sh $CLI data merge report partial.json

# Replace it wholesale
sh $CLI data set report new.json
```

`report` and `check-list` are short names pointing to the files in the working directory.

**`data merge` replaces arrays wholesale. It does not append.** Merge a second item and the first one disappears the instant you do. Use `add` when adding to an array.

```sh
sh $CLI add violation --violation "..." --location "..." --whyNotFixed "..." --suggestion "..."
sh $CLI add question  --question "..." --observed "..." --option "A" --option "B" --recommendation "..."
sh $CLI add changed   --path "..." --change "New" --summary "..."
sh $CLI add role      --importance 5 --name ViewModel --layout "..." --naming "..." --allowed "..." --forbidden "..." --example "..." --count 12
sh $CLI add module    --path app --kind "Android application" --role "..." --buildFile "app/build.gradle.kts"
sh $CLI add tool      --name ktlint --configPath ".editorconfig" --declareInKatachi "yes"
sh $CLI add excluded  --path "..." --reason "..."
```

`--option` and `--allowed` / `--forbidden` / `--example` **can be passed multiple times.** Passing an unknown field name stops it and lists the names that are available.

**Do not edit the HTML directly.** Any rewrite must always go through `data merge` or `data set`. Both of them validate the JSON before writing, back up the original file to `.bak`, and automatically roll back if the result turns out broken.

#### Write down what you learn as you go

**Do not save everything up for the end.** If you get interrupted partway through, the entire investigation is lost.

`data merge` accepts partial JSON, so you can write even a single item at a time.

```sh
printf '{"overview":{"appPackage":"com.example.app"}}\n' > <KATACHI_WORKDIR>/tmp/p.json
sh $CLI data merge report <KATACHI_WORKDIR>/tmp/p.json
```

As a rule of thumb, run `data merge` **once every time a section is filled in.** For step 1 that means `overview` → `architecture` → `modules` → `directoryTree` → `roles` → `tools` → `excluded`, so 7 or more times. If you split the work across subagents, write as each subagent's result comes back.

The checklist's JSON has `steps`. Progress is represented by setting the relevant item's `done` to `true`.

```json
{
  "steps": [
    {
      "id": "4",
      "title": "Verify",
      "warning": null,
      "items": [
        { "id": "4-1", "label": "...", "done": false }
      ]
    }
  ]
}
```

The item ids are `0-1` `0-2` / `1-1` `1-2` / `2-1` `2-2` / `3-1` `3-2` / `4-1` `4-2` / `5-1` `5-2` — 12 in total. Do not rewrite `label`.

**Do not rewrite the JSON yourself.** There are dedicated commands for that.

```sh
sh $CLI check 1-1 1-2          # mark as done (multiple allowed)
sh $CLI uncheck 1-2            # revert
sh $CLI warn 4 "Left 2 architecture violations in place"   # attach a warning to that step
sh $CLI warn 4 --clear         # clear the warning
```

`check` **stops if you pass an id it doesn't recognize.** A typo is never silently ignored.

`warn`'s step id is **0 through 5** (that's as far as the checklist's steps go). A step with a warning turns yellow, and stays expanded even once it's complete.

There are also arrays for `violations` (architecture violations left in place), `questions` (things to confirm with the user), and `changedFiles` (files created or changed).

## 1. Analyze and infer the current project codebase's structure and each component's constraints

**This is a step where you make the judgment calls.**

Walk every file committed to Git in the project and fill in the JSON inside `<KATACHI_WORKDIR>/project-code-base-report.html`. This file has already been placed by `init`. **Do not fetch the template again.**

Answer the following four questions.

- What architecture does it use? What characteristics does the project's structure have?
- What elements exist? What kind of code can be written inside each element?
- What tools are in use?
- What does the app use for its package name?

Follow the procedure from 0-3.

```sh
# Write section by section, as you figure each one out
sh $CLI data merge report <KATACHI_WORKDIR>/tmp/overview.json
sh $CLI data merge report <KATACHI_WORKDIR>/tmp/roles.json
```

The report's `meta` (project name, analysis timestamp, file count, Gradle root, Git root) **has already been filled in by `init`.** There's no need to touch it.

**`null` and an empty array represent "unfilled."** If `null` or `[]` remains after you've filled things in, that's a spot you haven't investigated yet. The schema itself is shown by `data get`'s output. There is one example JSON entry inside the HTML as a comment, so check it if you're unsure of the shape.

`roles` is the core of this report. The Roles in `architecture { }` are built from here. **One element = one entry**, and you fill in the following.

| Field | Content |
|---|---|
| `importance` | **An integer from 1 to 5. 5 is the most important.** The priority for inclusion in `architecture { }`. The report is sorted in this order |
| `name` | The element's name (e.g. `ViewModel`) |
| `layout` | The placement pattern |
| `naming` | The naming convention |
| `allowed` / `forbidden` | What may be written / what must not be written |
| `examples` | Paths to real example files |
| `count` | The number of actual instances |

`importance` / `name` / `layout` / `naming` are **required**. `verify` will not pass unless they're filled in.

Recognize that this task can consume a large amount of context, and launch subagents where available, as appropriate.

Once everything is filled in, run `sh $CLI check 1-1 1-2`.

**Use the app package name identified in this step in the next step.**

## 2. Create the :architecture-test module and set it up as a standard katachi test module

```sh
sh $CLI scaffold --package com.example.app
```

Pass the app package name identified in step 1 to `--package`. The katachi and Kotlin versions are detected automatically, so normally no other arguments are needed.

**Only if `init` warned "Could not detect the Kotlin version"**, add `--kotlin <version>`. Omitting it will cause `scaffold` to stop.

This command does the following.

- Creating `architecture-test/build.gradle.kts`
- Creating `ProjectArchitecture.kt` and `ProjectArchitectureTest.kt`
- Adding the Kotlin JVM plugin to the root build file (does nothing if it's already there)
- Adding `include("architecture-test")` to the settings file (`include 'architecture-test'` for a Groovy `settings.gradle`; does nothing if it's already there)

Plugin version conflicts, the JUnit engine, the JVM toolchain, and handling for Android / KMP projects are **all decided by the script.** Even if you feel like fixing something after reading the generated files, do not fix it.

Add `--no-konsist` only if it has been decided not to use `konsist { }`. If it hasn't been decided, leave the default as is.

Once it's created, run it once at this point.

```sh
./gradlew :architecture-test:test --rerun
```

Since `architecture { }` is still empty, **succeeding here is the expected outcome.**

If it fails, the cause is almost always the build configuration. Following the same policy as step 4, **attempt to fix errors unrelated to katachi (Gradle, Java, dependency resolution).** Only if it still can't be resolved, pass the output to the user exactly as it is and ask for their judgment.

If `scaffold` says "Did not rewrite automatically because a buildscript { } is present," **add the single line shown in the output to the root build file.** It will keep failing until you add it.

Once it succeeds, record the files that were created or changed, then run `sh $CLI check 2-1 2-2`.

```sh
sh $CLI add changed --path "architecture-test/build.gradle.kts" --change "New" --summary "Build definition for the verification module"
sh $CLI add changed --path "settings.gradle.kts" --change "Modified" --summary "Added include(\"architecture-test\")"
```

Enter the files exactly as listed in `scaffold`'s output.

## 3. Write the architecture { } definition

**This is a step where you make the judgment calls.**

Write the `architecture { }` definition based on the information given to you in the prompt by the user and what you investigated in step 1.

### 3-1. Fetch the documentation in one go

```sh
sh $CLI docs
```

This fetches the entire documentation site combined into a single text, and prints its path. **Do not open pages one by one.** Don't re-fetch it if it's already been fetched. Add `--small` if the volume becomes a problem.

Once you've finished reading, run `sh $CLI check 3-1`.

### 3-2. Write the definition

Fill in the `architecture { }` in `architecture-test/src/test/kotlin/<package>/test/architecture/ProjectArchitecture.kt`.

Record the files you created or changed in `changedFiles` with `data merge`, then run `sh $CLI check 3-2`.

## 4. Verify

```sh
./gradlew :architecture-test:test --rerun
```

Run this and check the result.

### How to handle errors

- Attempt to fix errors unrelated to katachi, such as those from Gradle or Java.
- Errors from architecture violations originating in katachi: do not force a fix.
  - For minor ones, fix them yourself as the agent.
  - For ones where the fix is unclear, leave them as is and have the user confirm in a later step.
  - Record errors you leave in place in the checklist's `violations` (`violation` / `location` / `whyNotFixed` / `suggestion`).
  - Put anything you want the user to decide into **the checklist's** `questions` (`sh $CLI add question ...`). The report also has an array with the same name, but that one is for "inconsistencies in the codebase" noticed during step 1 — its purpose is different.

Once done, run `sh $CLI check 4-1 4-2`. If you left violations in place, write one line about what was left with `sh $CLI warn 4 "..."`.

## 5. Review the checklist

```sh
sh $CLI verify
```

This lists unfilled fields and unchecked items. **If nothing is printed, you're done** (exit code 0). Anything printed means you either forgot to investigate it or forgot to record it. Fill it in and run again.

**Do not read the JSON yourself and eyeball it.** Item 5-1, "reviewed the entire checklist," refers to getting `verify` to pass.

**Once it passes, `verify` automatically marks 5-1 / 5-2 as done.** There's no need to run `check` yourself.

## 6. Report the result to the user

```sh
sh $CLI summary
```

**Return the output to the user exactly as it is. Do not compose the text yourself.**

If incomplete items remain, the failure format is printed; if everything is done, the success format is printed. The number of violations, the number of things to confirm, and the number of changed files are pulled from the JSON.

Only if `questions` has content, append each item's "question," "options," and "recommendation" after `summary`'s output. **This part is meant for a human to read and decide on, so as an exception you write the text yourself here.** Everywhere else, use `summary`'s output as is.

## 6-A. (After reporting in 6) Confirm the installation worked

Confirm a sample implementation task and carry it out.

- If the user hasn't specified a task, come up with 1 to 5 tasks from different categories, tell the user, and then carry them out.
- If the user has specified a task, judge whether it's reasonable. If it seems unreasonable, ask the user to decide whether to actually run it.

After running the task, run `./gradlew :architecture-test:test` and decide whether `architecture { }` needs fixing.

## 6-B. (After reporting in 6) If asked to set up CI

Handle this as follows, based on the CI system in use.

### If using GitHub Actions

Add a workflow like the one below. If a CI workflow already exists, use the following as a reference and modify it to run `./gradlew :architecture-test:test` (do not proliferate new yaml files just for `:architecture-test:test`).

```yaml
name: Architecture

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  architecture:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '21'

      - uses: gradle/actions/setup-gradle@v6

      - run: ./gradlew :architecture-test:test
```

### If using something other than GitHub Actions

Modify the workflow so that `./gradlew :architecture-test:test` runs and reports at an appropriate, non-intrusive time, such as on pull request creation, merge request creation, or a pre-push hook.
