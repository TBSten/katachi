# Installing katachi

These are the steps to install [katachi](https://tbsten.github.io/katachi). You will create an architecture definition that fits the user's codebase.

**Do not read this document in one go.** A web-fetch tool's summary drops steps. These steps run on the `katachi` command (installed with `brew install tbsten/tap/katachi`), which also ships this document. `katachi agent guide --lang en <section ID>` prints one section (`katachi agent guide --lang en` prints the table of contents; it works before `init` too, and after `init` `--lang` is not needed). Each section ends with the command for the next one. If `katachi` is not installed yet, save the original and read only chapter 0, cut out of it: `curl -fsSL -o <save location>/install.md https://tbsten.github.io/katachi/install/en/index.md`, then `sed -n '/^## 0\./,/^## 1\./p' <save location>/install.md`.

**Table of contents** (section IDs and headings; fetch the body with `katachi agent guide <section ID>`)

- 0 — Preparation
  - 0-1 — Get all permissions up front
  - 0-2 — Run init
  - 0-3 — Reading and writing the checklist and report
- 1 — Analyze and infer the current project codebase's structure and each component's constraints
  - 1-1 — Read the project's own documentation first
  - 1-2 — Scan the codebase and fill in the report
  - 1-3 — Decide the writing preferences
- 2 — Create the verification module
  - 2-1 — Run scaffold
  - 2-2 — Run once with an empty definition
- 3 — Write the architecture { } definition
  - 3-1 — Fetch the documentation by topic
  - 3-2 — Write the definition
  - 3-3 — Refactor the definition
- 4 — Verify
  - 4-1 — Run the test
  - 4-2 — How to handle errors
  - 4-3 — Generate the documentation
- 5 — Review the checklist
- 6 — Report the result to the user
  - 6-0 — Fix the definition after review
- 6-A — (After reporting in 6) Confirm the installation worked
- 6-B — (After reporting in 6) If asked to set up CI
- 6-C — (After reporting in 6) Set up documentation generation
- 6-D — (After reporting in 6) Set up code generation from templates

In the checklist, 6-A to 6-D are 6-1 to 6-4 (`guide 6-1` fetches them too).

**Dividing the work between the main agent and subagents**

Where subagents are available, split the work as in the table below. Only the main agent writes to the working directory; subagents never do.

| Section | Main agent | Delegated to subagents | What the main agent receives |
|---|---|---|---|

| 6-B to 6-D | Everything | — | — |

## 0. Preparation

**Everything that can be done mechanically is handled by the `katachi` command.** Do not supplement the steps yourself.

You are only responsible for judgment in the following:

- Step 1: Analyzing the codebase and confirming the writing preferences
- Step 3: Writing and refactoring the `architecture { }` definition
- Step 4: Deciding whether to fix or leave remaining architecture violations
- Step 6: Proposing which Roles to give a template, and applying the review
- Step 6-A / 6-B / 6-C / 6-D: Planning a sample task, wiring up CI, setting up documentation generation and templates

**Do not rewrite the `build.gradle.kts` generated by `scaffold`, or the `settings` / root build file / `gradle/libs.versions.toml` it appended to.** `ProjectArchitecture.kt` is the exception, since it is what you fill in during step 3. Adding `processors { }` to the `katachi { }` block of `build.gradle.kts` is allowed only in 6-C / 6-D, once the user has agreed.

### Before you start — clear the session (only if it applies)

This is not a checklist item; it carries no number.

**If this session already holds a lot of unrelated conversation, say so to the user first.** These steps run from 0 to 6, with dozens of exact commands along the way, and step 3 reads documentation. The more unrelated context is in the way, the easier it is to skip a step, invent a workaround nobody wrote down, or carry an assumption over from the earlier topic.

**Suggest it, do not decide it.** If the user chooses to carry on, carry on.

Clearing also throws away this document, so include the text below when you suggest it. Pasting it into a fresh session starts again from the same place.

```
Install katachi in this project.
Follow https://tbsten.github.io/katachi/install/en/index.md
```

If they want to pin the working directory, they can add "use <path> as the working directory".

There are three points in these steps where the session may end (the end of step 6, the end of 6-0, and the end of each of 6-A to 6-D). Each of them says how to resume.

If there is a working directory made by an earlier version (including one made with `katachi-install.sh`), recreate it with `init --force` (the checklist's JSON is lost. With the old HTML left as it is, `check 1-3` stops with "Unknown item id").

### 0-1. Get all permissions up front

These steps repeat network access, file creation, and running Gradle many times over. Checking in every time would leave the user doing nothing but approving requests endlessly.

**Do not ask for permission in prose — actually run a harmless dummy of each.** The tool running you asks for permission per kind of command. Run each one once up front, and the real commands that follow are never asked about.

Run the following **from the Gradle root directory**, **one at a time, separately.** Do not join them into a single line — a single line only earns you one kind of permission.

```sh
# 1. Is the katachi command installed (the first run fetches its body from Maven Central, so it takes a few seconds)
katachi --version
```

```sh
# 2. Creating a file under the project
touch .katachi-probe && rm .katachi-probe
```

```sh
# 3. Running Gradle
./gradlew --version
```

> `# In a project that needs a JDK other than the java on PATH, prefix every ./gradlew and katachi call from here on with the same JAVA_HOME=<path>. Shell variables don't persist across calls. doctor and test print "JDK: N (source)"; if the source is JAVA_HOME, add it every time.`

```sh
# 4. Running katachi (and checking Gradle's JDK and the project's Kotlin)
katachi doctor --lang en
```

`doctor` in 4 checks the version of the JDK that runs Gradle, the project's Kotlin version, and whether `git` is available (recommended). **If anything falls short, it says so, with hints on how to fix it.** Pass that output on to the user, have them fix it, and run 4 again. `init` checks Kotlin and `git` the same way.

Both the working directory and the verification module (`architecture-test/` by default) are created under the project root, so 2 earns permission for both. **The probes leave no trace.** Do not write a probe that creates a directory (an empty verification module directory left behind makes step 2's `scaffold` stop with "already exists").

**If any of them is blocked, tell the user what was refused.** Without 1 you cannot start, without 2 you cannot create files, without 3 you cannot verify, and without 4 you cannot run any of the steps below.

**If 1 cannot find `katachi`, do not try to install it yourself.** Do not invent a workaround either, such as fetching a script and running it, or looking for a jar to put in place. Ask the user to run `brew install tbsten/tap/katachi` (it needs Homebrew; Kotlin comes with it), and run 1 again once it is installed. The same goes for `kotlin is not on PATH`: ask the user to run `brew install kotlin`.

If all four pass, no permission will be asked for in any later step.

**Existing source code is never rewritten.** The only times you touch it are when fixing a build error unrelated to katachi in step 4, and during the implementation task in step 6-A. If you are going to fix an architecture violation itself in step 4, check with the user again at that point.

At this point the working directory does not exist yet. Record the check at the end of the next step, together.

### 0-2. Run init

Run the following **from the Gradle root directory**.

```sh
katachi agent init --lang en
```

`--lang en` specifies that the checklist and report are fetched in English, and that **`katachi`'s output (including the `summary` text) is also in English.** **If you omit it, it is English** (because the site's default is English). Once specified it is recorded in the working directory, so later commands do not need it.

If the user has specified where the verification module goes, add `--module-dir <path relative to the Gradle root>` (for example `--module-dir static-analysis/katachi`). Without it, it is `architecture-test`. To change it later, record it with `preferences set moduleDir=<path>` in step 1-3.

This command does all of the following. **Do not redo any of this by hand.**

- Confirming this is a Gradle project (stops if not)
- Checking whether it's under Git management (warns if not)
- Deciding on and creating the working directory (inside a `.gitignore`d location if one exists, otherwise `tmp/install-katachi/`)
- Deciding the katachi version (the same version as the `katachi` command; if the version given with `--katachi` is below 0.3.0, which this procedure assumes, it stops before creating anything)
- Detecting the Kotlin version the project uses (it warns if it is older than 2.2; see "When Kotlin is too old" below)
- Placing `check-list.html` and `project-code-base-report.html`
- Placing a copy of this document (`<KATACHI_WORKDIR>/tmp/cache/index.md`, for people to open; `guide` prints from the bundled original. To place it again, `katachi agent guide --refresh`)
- Initializing the checklist's JSON (working directory / version / project root / date-time / Kotlin / Git / where the verification module goes)

At the end, the result is printed in the following format (a few lines of guidance follow after it). The steps from here on use these values.

```
KATACHI_WORKDIR=/path/to/project/tmp/install-katachi
KATACHI_VERSION=0.3.0
KATACHI_PROJECT_ROOT=/path/to/project
KATACHI_KOTLIN=2.4.10
KATACHI_GIT=yes
KATACHI_SETTINGS=/path/to/project/settings.gradle.kts
KATACHI_LANG=en
KATACHI_MODULE_DIR=architecture-test
KATACHI_MODULE_PATH=:architecture-test
```

**Run every command from here on as `katachi agent <subcommand>` in the root of the project.** `katachi` finds the working directory under the current directory by itself. When running from somewhere else, prefix it with `KATACHI_WORKDIR=<the KATACHI_WORKDIR value>`. Read `:architecture-test:` in this document as `KATACHI_MODULE_PATH`, and `architecture-test/` as `KATACHI_MODULE_DIR` (they are the same unless you changed `--module-dir`).

Once this is done, run `katachi agent check 0-1 0-2`. The last `Next:` line of `init` points to this command too.

**If it stops, handle it exactly as the output says.** Do not invent a workaround. To change the working directory, re-run with `--workdir <path>`; to pin a version, re-run with `--katachi <version>` (`scaffold` uses the version `init` recorded. Re-running without `--katachi` keeps the version recorded last time).

`init` **never breaks already-filled-in files no matter how many times you run it.** If it fails partway through, you may just re-run it as is.

**If `init` warns that the working directory is visible to git, pass that on to the user** and suggest adding it to `.gitignore`. It happens when the project has no already-ignored place to put it. katachi checks files that are untracked but not ignored, so left alone the working directory itself becomes an `[UnexpectedFile]` in step 4 (and the checklist and the report can end up in their commits). Do not edit `.gitignore` yourself.

**If it lists things that are "untracked and not ignored", the reason is the same.** Ask the user whether to declare each of them in the definition or add it to `.gitignore`.

**When Kotlin is too old.** If `init` warns something like "This project uses Kotlin 1.9.10. katachi needs Kotlin 2.2 or later", ask the user before starting the analysis in step 1 (`doctor` prints the same warning). As it is, `scaffold` in 2-1 will stop, and the analysis up to that point is wasted. Upgrading Kotlin changes the existing build, so do not do it without the user's consent. Once they agree, upgrade Kotlin to 2.2 or later. Kotlin Gradle Plugin 2.2 needs Gradle 7.6.3 or later, so if the warning says "Gradle needs upgrading too", upgrade Gradle as well. Fixing build errors caused by the upgrade is also a change to the existing build, so tell the user what you will change before fixing them. Once `./gradlew` builds, run `init` again (the files already filled in are not broken, and the Kotlin version recorded in the check list becomes the new one), and record the files you changed with `add changed` from 0-3. If the user decides not to upgrade, tell them that katachi cannot be installed in this project, and stop there.

The top level of the working directory holds only `check-list.html` and `project-code-base-report.html`, which people open, plus `tmp/`. Records and fetched files (`tmp/cache/`), and any notes or logs all go inside `<KATACHI_WORKDIR>/tmp/`. Do not add anything to the top level.

### 0-3. Reading and writing the checklist and report

`check-list.html` and `project-code-base-report.html` are **single HTML files that carry their data as JSON inside them.** The HTML is only a rendering shell — **the only thing you read or write is the JSON.**

```sh
# Read (only JSON is printed; there's no need to read the HTML)
katachi agent data get report
katachi agent data get check-list

# Read just part of it (keys are dot-separated; a missing key stops it)
katachi agent data get report questions
katachi agent data get check-list meta.moduleDir

# Update just part of it (deep-merged into the existing content; use this normally)
katachi agent data merge report partial.json

# Replace it wholesale
katachi agent data set report new.json
```

`report` and `check-list` are short names pointing to the files in the working directory.

**`data merge` replaces arrays wholesale. It does not append.** Merge a second item and the first one disappears the instant you do. Use `add` when adding to an array.

```sh
katachi agent add violation --violation "..." --location "..." --whyNotFixed "..." --suggestion "..."
katachi agent add question  --question "..." --observed "..." --options "A" --options "B" --recommendation "..."
katachi agent add codebase-question --question "..." --observed "..." --options "A" --options "B" --recommendation "..."
katachi agent add changed   --path "..." --change "New" --summary "..."
katachi agent add role      --importance 5 --name ViewModel --group feature.ui --layout "..." --naming "..." --allowed "..." --forbidden "..." --examples "..." --count 12
katachi agent add module    --path app --kind "Android application" --responsibility "..." --buildFile "app/build.gradle.kts" --deviation "..."
katachi agent add tool      --name ktlint --configPath ".editorconfig" --declareInKatachi "yes"
katachi agent add excluded  --path "..." --reason "..."
```

`--options` and `--allowed` / `--forbidden` / `--examples` **can be passed multiple times.** Passing an unknown field name stops it and lists the names that are available. It also stops when you pass no fields at all, and when the same `--path` or `--name` is already recorded — so a blank row and a duplicate row cannot get in. Only `add changed` ends without doing anything (exit code 0) when the path is already recorded. If you change a recorded file again later, there is no need to record it again.

`add` also stops in the following two cases.

- `add role` stops if `--layout` is a Gradle build file (`build.gradle.kts`, `settings.gradle.kts`, `gradle.properties`, the version catalog, and so on). Gradle files are covered by `gradle()`, so they are not written as Role candidates (except `buildSrc` and builds added with `includeBuild`). For a Role that exists only to put a constraint on a build file, record it with `--constraint-only --note <what it checks>`
- `add excluded` stops if the path is excluded by `.gitignore`. katachi never looks at `.gitignore`d files in the first place, so there is no point listing them as excluded

`add changed` takes **one entry at a time.** When the definition grows to dozens of files, record them as **a single entry using a directory or a wildcard** (for example `--path "architecture-test/src/test/kotlin/**" --change "New" --summary "the whole architecture { } definition (12 files)"`). There is no need for one entry per file.

**Do not edit the HTML directly.** Any rewrite must always go through `data merge` or `data set`. Both of them validate the JSON before writing, back up the original file to `.bak`, and automatically roll back if the result turns out broken.

#### Write down what you learn as you go

**Do not save everything up for the end.** If you get interrupted partway through, the entire investigation is lost.

`data merge` accepts partial JSON, so you can write even a single item at a time.

```sh
printf '{"overview":{"appPackage":"com.example.app"}}\n' > <KATACHI_WORKDIR>/tmp/p.json
katachi agent data merge report <KATACHI_WORKDIR>/tmp/p.json
```

As a rule of thumb, run `data merge` **once every time a section is filled in.** For step 1 that means `overview` → `architecture` → `modules` → `directoryTree` → `roles` → `tools` → `excluded`, so 7 or more times. If you split the work across subagents, write as each subagent's result comes back. **Write with one process at a time.** Subagents do not write; the main agent writes the results it receives, in order (writes are serialized by a lock, but running them side by side only waits and is no faster).

The checklist's JSON has `steps`. Progress is represented by setting the relevant item's `done` to `true`.

```json
{
  "steps": [
    {
      "id": "4",
      "title": "Verify",
      "warning": null,
      "items": [
        { "id": "4-1", "label": "...", "done": false }
      ]
    }
  ]
}
```

The item ids are `0-1` `0-2` / `1-1` `1-2` `1-3` / `2-1` `2-2` / `3-1` `3-2` `3-3` / `4-1` `4-2` `4-3` / `5-1` `5-2` — 15 of them — plus **`6-1` `6-2` `6-3` `6-4` for the optional step 6**, 19 in all. Check 6-1 to 6-4 only if you did 6-A to 6-D respectively; `verify` does not require them. Do not rewrite `label`.

**Do not rewrite the JSON yourself.** There are dedicated commands for that.

```sh
katachi agent check 1-1 1-2          # mark as done (multiple allowed)
katachi agent uncheck 1-2            # revert
katachi agent warn 4 "Left 2 architecture violations in place"   # attach a warning to that step
katachi agent warn 4 --clear         # clear the warning
```

`check` **stops if you pass an id it doesn't recognize.** A typo is never silently ignored. After marking items done it prints one line, `Next: katachi agent guide <section ID>`, so read that section next. It points to the next section to read in table-of-contents order, including 0-3 and the chapter introductions (`guide 3` and so on), which have no items.

`warn`'s step id is **0 through 6** (that's as far as the checklist's steps go). A step with a warning turns yellow, and stays expanded even once it's complete.

There are also arrays for `violations` (architecture violations left in place), `questions` (things to confirm with the user), and `changedFiles` (files created or changed), plus `preferences` (the writing preferences; 1-3) and `answers` (the answers to the questions; 1-2).

## 1. Analyze and infer the current project codebase's structure and each component's constraints

**This is a step where you make the judgment calls.**

Walk every file committed to Git in the project and fill in the JSON inside `<KATACHI_WORKDIR>/project-code-base-report.html`. This file has already been placed by `init`. **Do not fetch the template again.**

### 1-1. Read the project's own documentation first

**Read it before the code.** The code shows what the project *is*; the documentation shows what it is *meant to be*, and `architecture { }` declares the latter. Write the definition from the code alone and you get **a definition that rubber-stamps the present state**, freezing existing drift in place as if it were the rule.

Look in the following places (whatever exists).

- `README` / `CONTRIBUTING` / `ARCHITECTURE.md`
- `docs/`, `doc/`, `documentation/`, and any documentation site (`docs-site/` and the like)
- ADRs (`docs/adr/`, `doc/architecture/decisions/`, ...)
- `CLAUDE.md` / `AGENTS.md` / `.cursor/rules` - conventions written for AI agents
- a `README` inside each module

Take the following from them.

| What | Where it goes |
|---|---|
| **The vocabulary the team actually uses** (`UseCase` or `Interactor`, `Screen` or `Page`) | `roles[].name`. **Do not invent names of your own** |
| Deliberate rules ("the UI never calls a repository directly") | `roles[].allowed` / `forbidden` |
| The name of the architecture and why it was chosen | `architecture.name` / `rationale` / `characteristics` |
| Checks of their own (a Kotlin compiler plugin, custom detekt rules, ktlint) | `tools` |

Write inconsistencies with `katachi agent add codebase-question ...` (`add question` goes to the checklist, which is for something else). The ids are `cq1`, `cq2`, … in the report and `q1`, `q2`, … in the checklist, so they never collide.

**Where the documentation and the code disagree, write it into `questions`.** Do not quietly side with the code. Whether the documentation is stale or the code has drifted is something only the user can say - and that disagreement is exactly what belongs in front of them before step 3.

If there is no documentation at all, skip this section and infer from the code. Leave one line in `questions` saying so: that everything below is inferred, because the project documents nothing.

Once you've read it all, run `katachi agent check 1-1`.

### 1-2. Scan the codebase and fill in the report

Answer the following four questions.

- What architecture does it use? What characteristics does the project's structure have?
- What elements exist? What kind of code can be written inside each element?
- What tools are in use?
- What does the app use for its package name?

Follow the procedure from 0-3.

```sh
# Write section by section, as you figure each one out
katachi agent data merge report <KATACHI_WORKDIR>/tmp/overview.json
katachi agent data merge report <KATACHI_WORKDIR>/tmp/roles.json
```

The report's `meta` (project name, analysis timestamp, file count, Gradle root, Git root) **has already been filled in by `init`.** There's no need to touch it.

**`null` and an empty array represent "unfilled."** If `null` or `[]` remains after you've filled things in, that's a spot you haven't investigated yet. The schema itself is shown by `data get`'s output. There is one example JSON entry inside the HTML as a comment, so check it if you're unsure of the shape.

In `modules`, write `path` / `kind` / `responsibility` / `buildFile` for each module. If a module's setup differs from the other modules of the same `kind`, write that in `--deviation` (omit it otherwise). The report draws the modules as a tree by `path`, so there is no need to write parents and children separately.

`roles` is the core of this report. The Roles in `architecture { }` are built from here. **One kind of file = one entry**, and you fill in the following. A bundle of different kinds of files — a module, or "the config files at the root" — is not one entry; write it as one entry per kind (in the definition the bundle becomes a group; see "One Role = one kind of file" in 3-2).

| Field | Content |
|---|---|
| `importance` | **An integer from 1 to 5. 5 is the most important.** The priority for inclusion in `architecture { }`. The report is sorted in this order |
| `name` | The element's name (e.g. `ViewModel`) |
| `group` | The group it belongs to. Nest with `.` (e.g. `feature.ui`) |
| `layout` | The placement pattern |
| `naming` | The naming convention |
| `allowed` / `forbidden` | What may be written / what must not be written |
| `examples` | Paths to real example files |
| `count` | The number of actual instances |

`importance` / `name` / `group` / `layout` / `naming` are **required**. `verify` will not pass unless they're filled in.

#### Guidelines for listing Role candidates

- **Write Role candidates as a tree of groups.** Nest groups in the order "module → layer → kind", and do not line up 8 or more Roles in one group (if they do, split the group)
- **`build.gradle.kts` / `settings.gradle.kts` / `gradle.properties` / the version catalog are covered by `gradle()`.** Do not make a Role per kind of module. `add role` refuses them too (except `buildSrc` and builds added with `includeBuild`). The exception is a constraint you want to put on a build file (that the namespace matches the package, say); record it with `add role --constraint-only --note <reason>`. In the definition it does not become a Role: write the constraint in a hook such as `gradle { buildScript { } }`. A hook's constraint receives the build files of every module, so to look at one module only, narrow them inside the constraint (the Gradle paragraph under "One Role = one kind of file" in 3-2)
- **What gets `documented = false`:** (1) generated output (build output, committed generated code), (2) build and tool configuration (`.editorconfig`, CI yaml, lint configuration), (3) single-file helpers (README, LICENSE, `.gitignore`). Only Roles that are useful to a reader go into the generated documentation
- **For the Android staples (`AndroidManifest.xml`, `res/`), copy the recipe and adapt it.** Base them on the definition fetched with `katachi agent docs --topic android-three-layer`

This task can consume a large amount of context, so launch subagents where available, as appropriate (as in the table at the top: subagents read and draft, and the main agent writes).

Once everything is filled in, run `katachi agent check 1-2`.

**Put whatever you wrote into the report's `questions` in front of the user now, and get answers.** What belongs here are inconsistencies like "do screen files go directly in the package, or are subpackages allowed too" — **the answer changes how `layout` is written.** Ask after the definition is done and you will be rewriting it. **Do not leave this until after step 3.**

Ask like this. Do not re-list the questions in chat.

1. Once `questions` is written, show the report's URL (the path to `project-code-base-report.html`, starting with `file://`) and have the user answer in "7. Questions for you" in the browser and save the JSON with "Export answers"
2. Import the JSON you receive with `katachi agent answers import <path to json>`. Ids that could not be imported are printed as warnings
3. If an answer arrives in chat, import it one at a time with `katachi agent answers set <id> "<answer>"` (`--note "<supplement>"` can be added). The id decides where it goes (`cq…` is the report, `q…` the checklist)

`katachi agent answers` prints, for the checklist and the report each, how many are answered and lists the unanswered ones.

**Use the app package name identified in this step in step 2.**

### 1-3. Decide the writing preferences

Decide first the parts of the definition's style that depend on the user's preferences. `scaffold` and `lint` read this record.

```sh
katachi agent preferences
```

Paste the output to the user as is and ask once: "answer only the ones you want to change from the recommendation". Do not ask one item at a time.

| key | Question | Values | Recommended | Read by |
|---|---|---|---|---|
| `nestedGroups` | Nest groups? | `yes` / `no` | `yes` | `lint` |
| `moduleDir` | Where the verification module goes | Path relative to the Gradle root | `architecture-test` | `scaffold` and everything after |
| `testFramework` | Test framework | `junit5` / `kotest` | Detected from the project | `scaffold` |
| `dependencyStyle` | How dependencies are written | `catalog` / `literal` | `catalog` if `gradle/libs.versions.toml` exists | `scaffold` |
| `constraintNames` | Put the question's number in constraint names? | `plain` / `numbered` | `plain` | 3-2 (you read it) |
| `oneRolePerFile` | One Role per file? | `yes` / `no` | `yes` | `lint` (3-3) |

Record the answers and mark it done. If the user says the recommendations are fine, skip `set` and just run `check`.

```sh
katachi agent preferences set nestedGroups=yes testFramework=kotest
katachi agent check 1-3
```

Passing an unknown key or value stops it and lists the values that are available.

## 2. Create the verification module

### 2-1. Run scaffold

```sh
katachi scaffold --package com.example.app
```

Pass the app package name identified in step 1 to `--package`. It uses the katachi version `init` recorded and the Kotlin version detected from the project, so normally no other arguments are needed. Where the verification module goes, the test framework and how dependencies are written come from the preferences recorded in 1-3. Add `--module-dir <path>` / `--test-framework junit5|kotest` / `--deps catalog|literal` only to hard-code them without recording preferences.

**Only if `init` warned "Could not detect the Kotlin version"**, add `--kotlin <version>`. Omitting it will cause `scaffold` to stop. `scaffold` also writes the version you pass into the checklist's `meta.kotlin`.

This command does the following.

- Creating `build.gradle.kts` in the verification module (`architecture-test/` by default). It applies Kotlin JVM and the katachi Gradle plugin (`me.tbsten.katachi`), and tells the plugin where the definition lives with `katachi { architecture = "<package>.test.architecture.projectArchitecture" }`. The plugin does not add katachi as a dependency, so `testImplementation("me.tbsten.katachi:katachi:<version>")` and the rest are written alongside it. `tasks.test { }` also gets `outputs.upToDateWhen { false }` and `outputs.cacheIf { false }`. The files katachi checks (the whole repository) are not inputs of the Test task, so without these Gradle skips the test as `UP-TO-DATE` after a file is added or moved, and it stays green even with violations
- Creating `ProjectArchitecture.kt` and `ProjectArchitectureTest.kt` (in the `FunSpec` form if `testFramework` is `kotest`)
- Appending to `gradle/libs.versions.toml` (when `dependencyStyle` is `catalog`). It adds aliases for `katachi` / `katachiKonsist` / JUnit to `[versions]` / `[libraries]` / `[plugins]`, and `build.gradle.kts` references them as `libs.katachi` and so on. If an alias pointing at the same thing already exists, it is used. Only the Kotlin plugin line stays `kotlin("jvm")` (no version) even with a catalog, because `alias(libs.plugins.kotlin.jvm)` fails with "already on the classpath with an unknown version" when the Kotlin plugin is on the classpath via build-logic (includeBuild). To move it into the catalog, the form is `id(libs.plugins.kotlin.jvm.get().pluginId)`
- Adding the Kotlin JVM plugin to the root build file (does nothing if the root's `plugins { }` / `buildscript { }` or `buildSrc` already has a Kotlin plugin. If only subprojects declare it, with a version, it adds nothing to the root and writes the version in the verification module instead. Gradle then warns `The Kotlin Gradle plugin was loaded multiple times in different subprojects ...`; that is expected with this setup, so leave it. Adding it to the root or removing the version makes plugin resolution fail instead)
- Adding `include(":architecture-test")` to the settings file (`include ':architecture-test'` for a Groovy `settings.gradle`; `include(":static-analysis:katachi")` for `--module-dir static-analysis/katachi`; does nothing if it's already there)
- Adding `mavenCentral()` to `pluginManagement { repositories { } }` in the settings file, because the katachi Gradle plugin is published to Maven Central (does nothing if it's already there; creates `pluginManagement { }` if there is none)

Plugin version conflicts, the JUnit engine, the JVM toolchain (below), the compiler options the project's Kotlin version needs, and handling for Android / KMP projects are **all decided by `scaffold`.** Below Kotlin 2.4 it writes `-Xcontext-parameters`, which the DSL cannot be called without; from 2.4 on it leaves the flag out, because there it only warns that it is redundant. Below Kotlin 2.2 it stops and says so — katachi's metadata cannot be read by a compiler that old (`init` warns about it first; see "When Kotlin is too old" in 0-2). Even if you feel like fixing something after reading the generated files, do not fix it.

The JVM toolchain reuses the N the project already sets: `jvmToolchain(N)` or `JavaLanguageVersion.of(N)` in another module, the same forms inside buildSrc or build-logic, or a value read from the version catalog or a `val`. katachi needs JDK 17 or later, so an N below 17 is not used. When no setting is found it writes no `jvmToolchain` and simply uses the JDK that runs Gradle (so it does not fail where JDK 17 is missing and no toolchain download is configured). Which of the two happened is recorded in the scaffold output and in the "JVM toolchain" field of the checklist. `doctor` and `scaffold` also check that the JDK Gradle uses is 17 or later, and stop with a fix if it is not.

The one exception is when the generated file has to change for the build to run at all. That takes priority over the rule above — but it means katachi has a bug, so record it with `add changed` giving the reason, and register it in `questions` as well.

Add `--no-konsist` only if it has been decided not to use `ktFileContent { }` (it comes with katachi-konsist). With this setup the test passes no `FileConstraintCheck()` to `assert()`, so a `fileConstraint` written in a `gradle { }` hook is not evaluated either, and the test fails with `[UncheckedFileConstraint]` (its How to fix is `Pass FileConstraintCheck() to assert()`). If it hasn't been decided, leave the default as is.

Once it's created, run `katachi agent check 2-1`.

### 3-2. Write the definition

**The goal is a definition that runs.** Writing it in one file is fine. Splitting files and cleaning up duplication happen in 3-3. When unsure about an API, read the llms.txt in "When unsure about an API" in 3-1.

**These are the imports you will need.** The documentation's snippet examples do not show them, so they are here.

```kt
import me.tbsten.katachi.dsl.architecture
import me.tbsten.katachi.dsl.DeclarationContainerScope   // when splitting the definition into functions
import me.tbsten.katachi.dsl.gradle.*                    // mainSourceSet / testSourceSet / kotlin / gradle() / the `/` operator
import me.tbsten.katachi.dsl.kotlin.ktFile
import me.tbsten.katachi.dsl.kotlin.ktsFile
import me.tbsten.katachi.konsist.declarations.ktFileContent   // when writing ktFileContent { } (an experimental API)
```

**Star-import `me.tbsten.katachi.dsl.gradle`.** `/` is the `div` operator, so importing names one by one leaves you unable to chain paths.

**`capture()`, `fileConstraint`, `FileConstraintFailure` and `ktFileContent { }` are experimental APIs.** In a file that uses any of them, write `@file:OptIn(ExperimentalKatachiApi::class)` at the top and add `import me.tbsten.katachi.ExperimentalKatachiApi` to the imports. Without it, every place that uses one is a compile error.

**Do not rename `val projectArchitecture` or move it to another package.** `katachi { architecture = "..." }` in the verification module's `build.gradle.kts` points at that fully qualified name. Splitting the definition into functions or files is fine (3-3).

You can write `title = "..."` and `description = "..."` at the top of `architecture { }`. They become the heading and body of the root page of the documentation generated in step 4 (they cannot be set from `build.gradle.kts`). Take their content from `overview` / `architecture` in the step 1 report.

#### One Role = one kind of file

**A Role (`"Name".role { }`) stands for one kind of file. What bundles different kinds of files is a group (`"name".group { }`).** Pack different kinds of files into one Role and neither its `summary` nor its `ktFileContent { }` fits all of them any more, and the generated documentation shows a box that anything goes into.

Decide whether files belong in the same Role with these three questions. If any file gets a "no", split the Role.

- Does the Role's one-sentence `summary` describe every file?
- Does every file follow the same naming and placement rule (rather than exceptions listed one by one)?
- Does every `ktFileContent { }` constraint you would write for the Role apply to every file?

The other way round, **it is not one Role per file either.** Eighteen `*UseCase.kt` files are one Role, `UseCase`. The snippet a violation's `How to fix:` offers names the Role after the file (`"GetUserUseCase"` and so on), so do not paste it as is — rename it to the kind.

Files directly under the root can be written directly under `layout { }` (`"README.md".file()`). You do not need to gather them in one Role.

**For the Gradle files (the wrapper, settings, each module's build script, `gradle.properties`, the version catalog), do not write Roles yourself: write the one line `gradle()`.** katachi declares a `Gradle` group split into one Role per kind of file (it comes with the star import of `me.tbsten.katachi.dsl.gradle.*`). Only `buildSrc` and builds added with `includeBuild`, which it does not cover, need Roles of your own.

When you want to check the contents of a build file (the ones marked `constraintOnly` in the report), you do not write a Role either. Write the constraint in a hook of the `gradle()` block, as in `gradle { buildScript { fileConstraint("...") { subject -> ... } } }` (`settingsScript { }` for settings, `versionCatalog { }` for the version catalog). `fileConstraint` and `FileConstraintFailure` are experimental APIs, so they need the opt-in described in the "experimental APIs" paragraph above (`@file:OptIn(ExperimentalKatachiApi::class)` and `import me.tbsten.katachi.ExperimentalKatachiApi`). A `buildScript { }` constraint receives the `build.gradle(.kts)` of every module, the root included, in `subject.files`. To look at one module only, narrow `subject.files` by path inside the constraint (for example `subject.files.filter { it == "app/build.gradle.kts" }`). Writing a Role inside `gradle { }` with the same name as one of katachi's (`"BuildScript".role { }` and so on) raises a duplicate exception. A Role outside `gradle { }` that declares a build file claims the same file as katachi's `BuildScript` and becomes `[AmbiguousLayout]`.

<summary>Common mistakes and how to fix them</summary>

In the field tests of the install kit, these shapes turned up in 13 projects.

| Mistake (packed into one Role) | Fix |
|---|---|
| `Gradle` holding `settings.gradle.kts`, `gradle.properties`, `gradlew`, the version catalog and the wrapper — and then `.gitignore` or even `README.md` | Replace the Gradle files with the one line `gradle()`, and give `.gitignore` and `README.md` a Role each |
| `ProjectMeta` / `RootDoc` holding `README`, `LICENSE`, `CONTRIBUTING`, `CLAUDE.md` | One Role per kind — `ProjectReadme` / `License` / … — bundled in a group. A Role named `Readme` gets a documentation page whose name differs from the index `README.md` only in case, and `katachiDocs` fails |
| `AgentAndCiConfig` holding `.claude/`, `.github/`, `.run/` | One Role per tool (if you do not check their contents, `ignore()` in each is fine) |
| `AndroidApp` holding a whole module's contents (Manifest, Activity, `res/`, `build.gradle.kts`) | Make the module a group, with a Role per kind inside |
| Production code and its tests in the same Role | Put the tests in a Role of their own |

```kt
"ProjectMeta".role {
    layout {
        "README.md".file()
        "LICENSE".file()
        ".gitignore".file()
    }
}

// ○ One role per kind, bundled in a group
"meta".group {

    "GitIgnore".role { layout { ".gitignore".file() } }
}
```

#### Do not stop at placement

**Take the conventions you read in step 1 and go through them as candidates for constraints on the contents (`ktFileContent { }`).** A definition that only says where files go only ever tells you that a file is in the right place. `ktFileContent { }` is an experimental API, so the file that uses it needs the opt-in (`@file:OptIn(ExperimentalKatachiApi::class)`). Fetch how to write it with `katachi agent docs --topic kt-file-content`.

**Do not write catch-all Roles.** A layout like `commonMain/**/*.kt` — "anything, as long as it is here" — looks like a check and is not one. In a real adoption this let **a test for the same responsibility be created somewhere else entirely, and accepted.** If a Role would end up a catch-all, give it at least one of the following.

- a pattern in the file name (`"*ViewModel".ktFile()`)
- one constraint on the contents (what a file of this Role declares; write it with `ktFileContent { }`)

A constraint on a file's imports goes in the `import` entries of `ktFileContent { }`. Only the `import`s you write are allowed, so "do not import this" is expressed by not listing that import. Many of a project's conventions are of this form.

```kt
"ViewModel".role {
    layout { /* ... */ }

    ktFileContent {
        `package`("com.example.viewModel")

        // android.** is not listed. Importing it is a violation
        `import`("kotlin.**")
        `import`("kotlinx.coroutines.**")
        `import`("androidx.lifecycle.**")
        `import`("com.example.**")

        required(`class`, fileName) {
            allow(anythingElse)
        }
    }
}
```

Constraint names follow `constraintNames` from 1-3. With `numbered`, prefix the name with the id of the question the constraint came from (`q3`, `cq2` and so on), as in `"q3: Does not import the android package".ktFileContent { }`. With `plain`, it is as in the example above.

#### Dividing the work with the static analysis already there

The project may already run detekt, Android Lint, ktlint or a compiler plugin of its own. **Do not drop a constraint because something else covers it.** In a real adoption the agent leaned so hard on avoiding duplication that it under-constrained, and **the only convention violation actually caught came from the existing checker.**

Decide like this.

- **A convention that belongs to a Role goes into katachi.** "A ViewModel never calls a repository directly" *is* the definition of that Role. Another tool checking something similar does not change that — having it here keeps "what this Role is" in one place
- **The only safe thing to drop is a rule an existing tool already fails the build on, with no per-file suppression.** If it can be suppressed file by file, katachi's copy still earns its place
- When unsure, write it. A constraint is easy to delete later

Fill in the `architecture { }` in `<verification module>/src/test/kotlin/<package>/test/architecture/ProjectArchitecture.kt`.

### 3-3. Refactor the definition

Tidy up the 3-2 definition **without changing the check result.** When unsure about an API, read the llms.txt in "When unsure about an API" in 3-1.

**Refactoring checklist** — go from the top; skip anything that does not apply.

- [ ] **Files and packages are split.** If `oneRolePerFile` from 1-3 is `yes`: one Role per file (`<group>/<Role>Role.kt`), one group per file (`<group>/<Group>Group.kt`), and `ProjectArchitecture.kt` only calls the groups. The naming is in "Where the definition files go" below. If it is `no`, skip this item
- [ ] **No group or directory name matches `.gitignore`.** Do not use a name such as `build` or `out` for a group (use e.g. `buildLogic`). After splitting, run `git ls-files --others --ignored --exclude-standard <verification module>/src` and confirm it prints nothing (no definition file is ignored). An ignored file never shows up in `gitTracked()`, so a gap in the definition goes unnoticed
- [ ] **The functions used for splitting are not `inline`.** katachi reads a violation's declaration site off the stack trace, and `inline` shifts the line numbers
- [ ] **The split definition files pass the check.** The definition files are checked too. The `layout { }` of the Role that covers the verification module accepts files as deep as the deepest definition file (e.g. `<group>/<sub>/<Role>Role.kt`: the depth of the nested groups + 1)
- [ ] **One Role = one kind of file.** Every Role has been gone over with the three questions of "One Role = one kind of file" in 3-2. `lint` reports 0 warnings, or the reason for each one kept is written with `katachi agent warn 3 "..."`
- [ ] **Gradle is the one line `gradle()`.** No Gradle files are declared in hand-written Roles (except `buildSrc` and builds added with `includeBuild`). Constraints on build files (the ones marked `constraintOnly` in the report) were written in a hook such as `gradle { buildScript { } }` (a constraint that looks at one module only narrows `subject.files` by path)
- [ ] **No catch-all Roles are left.** Roles that gather `anyFile()` / `ignore()`, or whose `layout` means "anything, as long as it is here", have a file name pattern or a constraint on the contents (`ktFileContent { }`) ("Do not stop at placement" in 3-2)
- [ ] **The descriptions are complete.** `title` / `summary` / `description` on Roles and groups, and `example()` (the name of a real file) on Roles. Take the content from `roles` in the step 1 report. The Roles you decided to give `documented = false` by the 1-2 guidelines say so
- [ ] **Duplication is shared.** The same `layout` is not copied into several Roles (pull it out into a function). A value that keeps coming up, like a package directory, is pulled out into a `val`
- [ ] **The check result is the same before and after.** "Compare before and after" below ends with "has not changed"

<details>
<summary>Where the definition files go (naming)</summary>

**Unless the user says otherwise, follow this naming.** The files then line up the way the architecture does, so finding where a Role is written takes no searching.

```
<package>/test/architecture/
├── ProjectArchitecture.kt            the architecture { } itself; only calls the group functions
├── <Role>Role.kt                     a Role outside any group   e.g. ProjectReadmeRole.kt
├── <group>/<Group>Group.kt           a group's definition       e.g. app/AppGroup.kt
├── <group>/<Role>Role.kt             a Role the group calls     e.g. app/EntrypointRole.kt
└── <group>/<sub>/<Sub>Group.kt       a nested group's definition  e.g. domain/model/ModelGroup.kt
```

- Directory names are the group name with a lowercase first letter (`domain`). Roles get no directory of their own. File names are `<Group>Group.kt` for a group (`AppGroup.kt`) and `<Role>Role.kt` for a Role (`EntrypointRole.kt`). Function names start lowercase (`fun DeclarationContainerScope.appGroup()`, `entrypoint()`). The package declaration follows the directory
- A group inside a group goes one level deeper the same way (`domain/model/ModelGroup.kt`, and a Role inside it is `domain/model/EntityRole.kt`). If `nestedGroups` from 1-3 is `no`, keep groups to one level and tell them apart by name instead of nesting
- A Role outside any group is `<Role>Role.kt` directly under the definition root (e.g. `ProjectReadmeRole.kt`). Any other Role goes in the directory of the group that calls it
- Each file holds **exactly one** group or Role. A group's file only calls the functions of the Roles under it
- Make the split functions extension functions on `DeclarationContainerScope`, and import them where they are called (an extension function cannot be called by its fully qualified name)

</details>

#### Compare before and after

Once tidied up, run it again the same way as in 3-2 and compare.

```sh
katachi agent test --save after-refactor

```

`compare-violations` pulls the check result out of the two logs (the summary line, and `[Kind] path` for each violation) and compares them. It does not compare the line numbers of declaration sites. `[MissingDescription]` should go down as you add descriptions, so it only prints the counts. **If there is a difference, fix the definition rather than taking the earlier log again.** The refactoring has changed the behavior.

If it stops, capture the cut-off log again as the output says.

**If the earlier log was green (0 violations), this is 0 against 0, and it cannot tell you that the split loosened the definition (a catch-all crept in, say).** In that case, also make one known violation after the split and confirm it fails: put a file that no Role covers somewhere temporarily, run `katachi agent test`, and once it fails with `[UnexpectedFile]`, delete that file.

If the check passes with warnings (`[AmbiguousLayout]` and the like, which never fail the check), a `Warnings: N` line and the warnings' headings are printed too. ### 4-2. How to handle errors

- Attempt to fix errors unrelated to katachi, such as those from Gradle or Java.
- Errors from architecture violations originating in katachi: do not force a fix.
  - For minor ones, fix them yourself as the agent
    - Do not silence an `[UnexpectedFile]` by adding a line to the `layout { }` of whichever existing Role is nearest. If that Role's `summary` does not describe the file, make a new Role ("One Role = one kind of file" in 3-2)
  - For ones where the fix is unclear, leave them as is and have the user confirm in a later step
  - Record errors you leave in place in the checklist's `violations` (`violation` / `location` / `whyNotFixed` / `suggestion`).
  - Put anything you want the user to decide into **the checklist's** `questions` (`katachi agent add question ...`). The report also has an array with the same name, but that one is for "inconsistencies in the codebase" noticed during step 1 — its purpose is different.

Even if more than 10 violations are left, the log of `katachi agent test` holds all of them. There is no need to write `maxViolations` in the test code.

**If many violations remain and the user wants to "tolerate what is there now and fail only on new ones", you can propose the baseline.** It is an experimental feature (`@ExperimentalKatachiApi`), so ask the user in `questions` before putting it in. To use it:

- Write `baseline()` in `architecture { }` in `ProjectArchitecture.kt`, and put `@OptIn(ExperimentalKatachiApi::class)` on `val projectArchitecture`. The baseline file defaults to `katachi-baseline.json` (at the project root)
- The baseline file is checked too, so add a Role that declares it in `layout { }` (e.g. `"BaselineFile".role { layout { "katachi-baseline.json".file() } }`). Without it the baseline file itself becomes an `[UnexpectedFile]`, and that one cannot go into the baseline
- `katachi agent test -- -Dkatachi.baseline.update=true` writes the violations there now into the baseline file. From then on only violations missing from the baseline file fail the test. Once a violation is fixed, its entry fails as `[StaleBaselineEntry]`, so remove it with `katachi agent test -- -Dkatachi.baseline.prune=true` (on CI (`CI=true`) both update and prune are refused)

Write the tolerated violations in `violations` too. Putting them in the baseline file does not make them go away.

If you left violations in place, write one line about what was left with `katachi agent warn 4 "..."`.

## 6-D. (After reporting in 6) Set up code generation from templates

Do this only for the Roles, among the proposals recorded in step 6, that the user agreed to.

**Before you start, read the page on generating code from a template.** Fetch it with `katachi agent docs --topic template` (also at https://tbsten.github.io/katachi/guides/generate-code-from-template/ ). The words `.template { }` offers (the `*Parameter()` functions such as `stringParameter()`), why you don't write the destination path, and what happens when a file already exists are all there. When unsure about a signature, read the llms.txt in "When unsure about an API" in 3-1 instead of guessing (the entry point for `.template { }` is https://tbsten.github.io/katachi/api-docs/katachi/me.tbsten.katachi.dsl/template.html.md ).

1. Check the proposals (`katachi agent data get report templates`).
2. Attach `.template { }` to a file declaration in that Role's `layout { }`. **`.template` is an extension function, so add `import me.tbsten.katachi.dsl.template` to the file you write it in** (`captureValue()` and the like can be used inside the block, so they need no import). **`.template { }`, `capture()` and `captureValue()` are experimental APIs, so also add `@file:OptIn(ExperimentalKatachiApi::class)` and `import me.tbsten.katachi.ExperimentalKatachiApi` to that file.** Without them compilation fails with `This katachi API is experimental. …` (the message says how to opt in). **Base its content on the `basedOn` file.** The destination path comes from the `layout { }` declaration itself, so don't write it on the template's side

   ```kt
   @file:OptIn(ExperimentalKatachiApi::class)

   import me.tbsten.katachi.ExperimentalKatachiApi
   import me.tbsten.katachi.dsl.template

   "UseCase".role {
       layout {
           "useCase" / "${capture("name")}UseCase".ktFile()
               .template {
                   val name = captureValue("name")
                   """
                       package com.example.app.domain.useCase

                       interface ${name}UseCase {
                           suspend operator fun invoke()
                       }
                   """.trimIndent()
               }
       }
   }
   ```

   **For a Role whose destination directory has a wildcard (`*`), name that `*` with `capture()`.** The check's result doesn't change. Attaching `.template { }` to a path that still has an unnamed `*` or `**` fails when layout is expanded (`assert()` in `katachi agent test`). Read the value inside the template with `captureValue("name")` (don't redeclare it with `stringParameter()` — the names collide and it fails)

   ```kt
   @file:OptIn(ExperimentalKatachiApi::class)

   import me.tbsten.katachi.ExperimentalKatachiApi
   import me.tbsten.katachi.dsl.template

   "ViewModel".role {
       layout {
           // was "feature" / "*" / mainSourceSet / kotlin / "com/example/app/feature" / "*" / "*ViewModel".ktFile()
           "feature" / capture("feature") / mainSourceSet / kotlin /
               "com/example/app/feature" / capture("feature") /
               "${capture("name")}ViewModel".ktFile()
                   .template {
                       val feature = captureValue("feature")   // "home" for --arg feature=home
                       val name = captureValue("name")         // "Home" for --arg name=Home

                       """
                           package com.example.app.feature.$feature

                           class ${name}ViewModel
                       """.trimIndent()
                   }
       }
   }
   ```

   For a directory's `*`, rewrite the `"*"` in `"feature" / "*" / ...` as `capture("feature")`. With more than one `*`, write a `capture()` for each, as in `"feature" / capture("feature") / capture("layer") / ...`.

   **Name every `*` left in the directory part of the destination.** If the module directory's `*` and the package directory's `*` get the same value, as in the example above, write one name (`capture("feature")`) in both. katachi checks that the two places have the same value, and reports a file where they differ as `[CaptureMismatch]`. If the values may differ, give each its own name. If even one unnamed `*` is left, an error occurs when layout is expanded for the file with `.template { }` attached (`assert()` catches it; it doesn't wait for `katachiTemplate` to run).

   **If the package directory's name differs from the module directory's name (module `appConfig` and directory `appconfig`, for example), give that directory's `*` its own name, separate from the module's, and use its `captureValue()` in the package.** If you put the module's name (`captureValue("feature")`) in the package, you write a package that disagrees with its directory, and since both the check and the compiler pass, you won't notice.

   All there is to use is `stringParameter()` / `booleanParameter()` / `intParameter()` (optionally with `default = ...`), `enumParameter()` (given `entries` or a default value), plus `capture("name")` — embeddable anywhere in a layout's directory or file name — to name a wildcard in the destination, and, to read its value, `captureValue("name")` (inside the template). Do not add other words by guessing.
3. A template's own parameters (`--arg name=...`) can be passed as-is, with no setting needed on the module side. What is accepted is exactly the set of names the named Role's `.template { }` declares, plus the names given to wildcards in its `layout { }`; a typo still fails, as before, with `Unknown processor argument(s): ...`
4. Generate one file, and confirm **the check passes right after**. `--arg template=` takes `group.Role` if there is a group, or just the Role name if there is none.

   ```sh
   ./gradlew :architecture-test:katachiTemplate --arg template=UseCase --arg name=Sample
   katachi agent test
   ```

   For a Role whose wildcard was named, pass that value too. **A directory's value becomes the destination path as it is, even if no such directory exists** (a typo creates the file in a directory that isn't there). Pass the name of a directory that exists.

   ```sh
   ./gradlew :architecture-test:katachiTemplate --arg template=ViewModel --arg feature=home --arg name=Sample
   katachi agent test
   ```

   If `test` fails, check that the path of the file declaration `.template { }` is attached to is right.
5. **Delete the generated file, since it was only for checking** (unless the user says to keep it). After deleting it, confirm `katachi agent test` passes once more.
