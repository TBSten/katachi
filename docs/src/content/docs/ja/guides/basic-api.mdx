katachi の主要な API を紹介します。
ここに挙げる API を覚えれば、katachi の基本的な使い方を理解できるはずです。

## 1. `architecture { }`

`architecture { }` はプロジェクト全体のアーキテクチャを定義するエントリーポイントです。
このブロックの中に、プロジェクトにあるファイルの Role を書きます。

```kt
architecture {
  "UseCase".role { /* ... */ }
  "RepositoryInterface".role { /* ... */ }
}
// このプロジェクトには `UseCase` と `RepositoryInterface` という2つの Role がある
```

アーキテクチャを構成する要素 (Role) は、後のセクションで詳しく説明します。

## 2. アーキテクチャをテストする `assert()`

`architecture { }` で定義したアーキテクチャをテストする関数が `assert()` です。

```kt {8}
val projectArchitecture = architecture {
  "UseCase".role { /* ... */ }
  "RepositoryInterface".role { /* ... */ }
}

@Test
fun `アーキテクチャに沿ったファイル配置になっている`() {
  projectArchitecture.assert()
}
```

定義に合わないファイルがあると、テストは次のようなレポートで失敗します（一部を省いています）。

```text
Katachi check failed: 1 violation (Unexpected: 1)

[UnexpectedFile] file:///path/to/project/src/main/kotlin/com/example/GetItemUseCase.kt
  No role is defined for this file.
```

## 3. Role を定義する `"名前".role { }`

`"名前".role { }` はプロジェクトの中に登場するファイルの役割 (Role) を定義します。

```kt {2,4}
architecture {
  "UseCase".role { /* ... */ }

  "RepositoryInterface".role { /* ... */ }
}
```

`architecture { }` ブロックの中に `"名前".role { }` を書くと、プロジェクトに登場するファイルの Role を定義できます。

### Role の例

よく知られたアーキテクチャを採用しているなら、Role はたとえば次のようになるでしょう。

| アーキテクチャ | Role |
|---|---|
| MVC | `Controller` |
| | `View` |
| | `Model` |
| MVVM | `View` |
| | `ViewModel` |
| Clean architecture | `Service` |
| | `UseCase` |
| | `Entity` |
| | `RepositoryInterface`, `RepositoryImplementation` |

### Deny by default

katachi では、宣言した Role のファイルしかプロジェクトに存在を許されません。

つまり katachi を導入するときは、プロジェクトの規約に合った Role を列挙する必要があります。

## 4. Role をグルーピングする `"...".group { }`

`"名前".group { }` は Role をまとめるためのブロックです。

例えば Clean architecture では、`UseCase` と `RepositoryInterface` は **同じドメインレイヤーの Role** です。

この場合、以下のように `"...".group { }` で各 Role を囲うことで、その階層構造を表現できます。

```kt {2}
architecture {
  "domain".group {
    "UseCase".role { /* ... */ }
    "RepositoryInterface".role { /* ... */ }
  }
}
```

Role のグループをドメインレイヤーとして DSL で表すと、Role 同士の関係や階層構造が明確になります。分かりやすいアーキテクチャ定義を作るには、分かりやすい粒度で Role をグループ化することが大切です。

### ネストした Role のグループ

`"...".group { }` はネストさせることができます。

```kt {3,6}
architecture {
  "domain".group {
    "usecase".group {
      "UseCase".role { /* ... */ }
    }
    "repository".group {
      "RepositoryInterface".role { /* ... */ }
    }
  }
}
```

## 5. ファイルが存在して良い位置を定義する `layout { }`

`"...".role { }` で Role を定義しただけでは、その Role のファイルをどこに置いてよいかは決まりません。

`layout { }` は Role に対応するファイルをどこに置けるかを定義するためのブロックです。

```kt {3-4}
architecture {
  "UseCase".role {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }
  }
}

// UseCase は `src/main/kotlin/com/example/useCase/*UseCase.kt` に置くことができる
```

### どのように機能するか

Deny by default の原則により、`layout { }` で宣言していない場所にはファイルを置けません。

たとえば AI Agent が、新しい UseCase ファイルを `src/main/kotlin/com/example/GetItemUseCase.kt` に置こうとしたとします。本来は useCase パッケージの中に置くべきファイルです。
`assert()` が呼び出された時点で、katachi はこのパスに一致する Role が無いことを検知し、テストが失敗します。

<FileTree>
- src/main/kotlin/com/example/
  - **GetItemUseCase.kt** ❌ `layout { }` で宣言していない場所
  - useCase/
    - GetUserUseCase.kt ⭐️ 宣言どおりの場所
</FileTree>

## 6. ファイルに置ける宣言を定義する `ktFileContent { }`

`ktFileContent { }` は、Role のファイルに置いてよい package・import・宣言を、許可リストで定義するブロックです。

```kt {7-10}
architecture {
  "UseCase".role {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    ktFileContent {
      `package`("com.example.useCase")
      required(`class`, fileName) {
        allow(anythingElse)          // クラスのメンバは何でもよい
      }
    }
  }
}

// GetUserUseCase.kt には、package com.example.useCase の宣言と class GetUserUseCase だけを置ける
```

`GetUserUseCase.kt` に置いた宣言は、次のように通るか違反になるかが決まります。

```kt title="GetUserUseCase.kt"
package com.example.useCase

class GetUserUseCase { /* ... */ }   // 通る: required の行に一致する
fun helper() {}                      // 違反: 一致する行が無い
```

違反になった宣言は、次のようなレポートで報告されます（一部を省いています）。

```text
[UnsatisfiedFileConstraint] file:///path/to/project/src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "ktFileContent"
  Declaration: helper (line 4)
  Not allowed: fun helper()
```

書いた行が許可リストになり、行を書かなかった種類には何も置けません（Deny by default）。この例には import の行が無いので、import を1つも書けません。クラスのメンバは `{ }` の中の行が許可リストで、`allow(anythingElse)` は「何でもよい」を表します。

`ktFileContent { }` は別モジュール `katachi-konsist` に入っています。検査するには、テストで `assert()` の代わりに `assert(FileConstraintCheck())` を呼びます。`assert()` だけでは検査されず、`[UncheckedFileConstraint]` としてテストが失敗します。

### `ktFileContent { }` の詳細

`ktFileContent { }` については [ファイルの中で定義できる宣言の許可リストを定義する](/katachi/ja/guides/kt-file-content/) も参照してください。

## まとめ

| API | 何をするか |
|---|---|
| `architecture { }` | プロジェクト全体のアーキテクチャを定義する、エントリーポイントです。 |
| `assert()` | 定義どおりにファイルが置かれているかを検査します。テストから呼ぶ1行で、これが無いと何も起きません。 |
| `"名前".role { }` | プロジェクトの中に登場するファイルの役割（Role）を定義します。 |
| `"名前".group { }` | Role をまとめて階層を作ります。使うかどうかは任意です。 |
| `layout { }` | その Role のファイルをどこに置いてよいかを定義します。 |
| `ktFileContent { }` | その Role のファイルに置いてよい package・import・宣言を、許可リストで定義します。 |
