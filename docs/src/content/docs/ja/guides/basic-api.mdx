katachi の主要な API を紹介します。
ここに挙げる API を覚えれば、katachi の基本的な使い方を理解できるはずです。

## 1. `architecture { }`

`architecture { }` はプロジェクト全体のアーキテクチャを定義するエントリーポイントです。
このブロックの中に、プロジェクトにあるファイルの Role を書きます。

```kt
architecture {
  "UseCase".role { /* ... */ }
  "RepositoryInterface".role { /* ... */ }
}
// このプロジェクトには `UseCase` と `RepositoryInterface` という2つの Role がある
```

アーキテクチャを構成する要素 (Role) は、後のセクションで詳しく説明します。

## 2. アーキテクチャをテストする `assert()`

`architecture { }` で定義したアーキテクチャをテストする関数が `assert()` です。

```kt {8}
val projectArchitecture = architecture {
  "UseCase".role { /* ... */ }
  "RepositoryInterface".role { /* ... */ }
}

@Test
fun `アーキテクチャに沿ったファイル配置になっている`() {
  projectArchitecture.assert()
}
```

## 3. Role を定義する `"名前".role { }`

`"名前".role { }` はプロジェクトの中に登場するファイルの役割 (Role) を定義します。

```kt {2,4}
architecture {
  "UseCase".role { /* ... */ }

  "RepositoryInterface".role { /* ... */ }
}
```

`architecture { }` ブロックの中に `"名前".role { }` を書くと、プロジェクトに登場するファイルの Role を定義できます。

### Role の例

よく知られたアーキテクチャを採用しているなら、Role はたとえば次のようになるでしょう。

| アーキテクチャ | Role |
|---|---|
| MVC | `Controller` |
| | `View` |
| | `Model` |
| MVVM | `View` |
| | `ViewModel` |
| Clean architecture | `Service` |
| | `UseCase` |
| | `Entity` |
| | `RepositoryInterface`, `RepositoryImplementation` |

### Deny by default

katachi では、**宣言した Role のファイルしかプロジェクトに存在を許されません**。

つまり katachi を導入するときは、プロジェクトの規約に合った Role を列挙する必要があります。

### 関連ドキュメント

Role については [Role 定義の詳細](/katachi/ja/guides/role/) も参照してください。

## 4. Role をグルーピングする `"...".group { }`

`"名前".group { }` は Role をまとめるためのブロックです。

例えば Clean architecture では、`UseCase` と `RepositoryInterface` は **同じドメインレイヤーの Role** です。

```kt {2}
architecture {
  "domain".group {
    "UseCase".role { /* ... */ }
    "RepositoryInterface".role { /* ... */ }
  }
}
```

Role のグループをドメインレイヤーとして DSL で表すと、Role 同士の関係や階層構造が明確になります。分かりやすいアーキテクチャ定義を作るには、分かりやすい粒度で Role をグループ化することが大切です。

### 関連ドキュメント

Role のグループについては [Role 定義の詳細](/katachi/ja/guides/role/) も参照してください。

## 5. ファイルが存在して良い位置を定義する `layout { }`

`"...".role { }` で Role を定義しただけでは、その Role のファイルをどこに置いてよいかは決まりません。

`layout { }` は Role に対応するファイルをどこに置けるかを定義するためのブロックです。

```kt {3-4}
architecture {
  "UseCase".role {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }
  }
}

// UseCase は `src/main/kotlin/com/example/useCase/*UseCase.kt` に置くことができる
```

### どのように機能するか

Deny by default の原則により、`layout { }` で宣言していない場所にはファイルを置けません。

たとえば AI Agent が、新しい UseCase ファイルを `src/main/kotlin/com/example/GetItemUseCase.kt` に置こうとしたとします (本来は useCase パッケージの中に置くべきです)。
`assert()` が呼び出された時点で、katachi はこのパスに一致する Role が無いことを検知し、テストが失敗します。

<FileTree>
- src/main/kotlin/com/example/
  - **GetItemUseCase.kt** ❌ `layout { }` で宣言していない場所
  - useCase/
    - GetUserUseCase.kt ⭐️ 宣言どおりの場所
</FileTree>

### 関連ドキュメント

`layout { }` については [Layout 定義の詳細](/katachi/ja/guides/layout/) も参照してください。

## 6. ファイルに置ける宣言を定義する `ktFileContent { }`

<Aside type="caution" title="AI が書いた下書き">
この節と、まとめの表の `ktFileContent { }` の行は、AI が書いた下書きです。`ktFileContent { }` は v0.3 で入る予定の実験的な機能です。
</Aside>

`ktFileContent { }` は、Role のファイルに置いてよい package・import・宣言を、許可リストで定義するブロックです。

```kt {7-8}
architecture {
  "UseCase".role {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    ktFileContent {
      `class`(fileName)
    }
  }
}

// GetUserUseCase.kt には、class GetUserUseCase だけを置ける
```

書いた種類（package・import・宣言）だけが許可リストになり、書いた行に当たらないものは違反になります。`fileName` には、検査しているファイルの名前が入ります（`GetUserUseCase.kt` なら `GetUserUseCase`）。

`ktFileContent { }` は別モジュール `katachi-konsist` に入っています。検査するには、テストで `assert()` の代わりに `assert(FileConstraintCheck())` を呼びます。`assert()` だけでは検査されず、`[UncheckedFileConstraint]` としてテストが落ちます。

### 関連ドキュメント

`ktFileContent { }` については [ファイルの中で定義できる宣言の許可リストを定義する](/katachi/ja/guides/kt-file-content/) も参照してください。

## 7. ファイル内の制約を定義する `"...".konsist { }`

Role を定義したファイルには、[Konsist](https://docs.konsist.lemonappdev.com/) で制約をかけられます。`ktFileContent { }` で書けない制約は、こちらで書きます。

```kt {7}
architecture {
  "UseCase".role {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    "invoke 関数を1つだけ持つこと".konsist {
      classes().must { it.functions().map { f -> f.name } == listOf("invoke") }
    }
  }
}
```

制約の対象は `layout { }` で指定したファイルで、制約そのものは Konsist の API で書きます。

制約を検査するには、テストで `assert()` の代わりに `assert(FileConstraintCheck())` を呼びます。`assert()` だけでは制約が評価されず、`[UncheckedFileConstraint]` としてテストが落ちます。

### 関連ドキュメント

`"...".konsist { }` については [カスタムルールを Konsist で定義する](/katachi/ja/guides/konsist-integration/) も参照してください。
