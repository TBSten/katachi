katachi は `architecture { }` 定義から markdown ドキュメントを生成することが可能です。

## 基本

build.gradle.kts に以下のように設定します。

```kts title="architecture-test/build.gradle.kts" {2-3}
katachi {
    // ⭐️ `architecture { }` を定義しているプロパティの FQCN を設定
    architecture = "com.example.projectArchitecture"
}
```

{/* TODO: `docs` は plugin が既定で登録しているので `processors { register("docs", ...) }` は要らない、と明記する。いまの書き方だと登録が要るのかどうか読み取れない */}

設定ができたら `runKatachiProcessor --processor="docs"` gradle task を実行することで ドキュメントが生成されます。

```shell
./gradlew runKatachiProcessor --processor="docs" 
```

### 生成例

次の定義を例にします。

```kt
architecture {
    title = "myapp"

    "domain".group {
        title = "Domain レイヤー"
        summary = "アプリ固有の振る舞いと、その対象になる値"

        "UseCase" {
            title = "ユースケース"
            summary = "各画面で発生するアプリ固有の1つの振る舞い"
            example("GetItemListUseCase", "商品の一覧")
            example("SignInUseCase", "サインイン")
            layout { ":core:domain".module { mainSourceSet / kotlin / modulePackage / "useCase" / "*UseCase".ktFile() } }
            "invoke メソッドのみを持つ".konsist { /* ... */ }
        }

        "Repository" {
            title = "リポジトリ"
            summary = "データの取得と保存の境界"
            layout { ":core:domain".module { mainSourceSet / kotlin / modulePackage / "repository" / "*Repository".ktFile() } }
        }
    }
}
```

```
build/katachi/docs/
├── README.md
└── domain/
    ├── README.md
    ├── UseCase.md
    └── Repository.md
```

見出しの `myapp` は `architecture { title = "myapp" }` が名乗ったもので、**書かなければ `アーキテクチャ` になります。**
各ページの先頭にある `[myapp](../README.md) / [Domain レイヤー](README.md)` はパンくずで、
**どのページからも索引まで戻れます。**

配置ツリーは**単一の子しか持たないディレクトリを畳みます。** `src/` `main/` `kotlin/` `**/` が
4行に分かれず1行になるのはそのためで、木の意味は**分岐が始まるところから**しかありません。

`Repository` には `konsist { }` も `example()` も書いていないので、**`## 制約` と `## 例` の節ごと出ません。** 空の節は作られません。

## 出力先ディレクトリ

デフォルトではドキュメントは `build/katachi/docs/` 配下に生成されます。

出力先は build.gradle.kts で `katachi.processors.docs.outputDir` に設定することで変更可能です。

{/* TODO: 出力先を `build/` の外にすると `gitTracked()` が生成物を拾い、

    sample/<name>/docs がまさにその形なので、そこを実例として指す */}

{/* TODO: ルートページの `title` / `description` の節が無い。

    書かなければ見出しは `アーキテクチャ ドキュメント`、本文は出ない。
    **build.gradle.kts からは設定できない**（0.2 で `docs { rootTitle }` と `--arg rootTitle` を

{/* TODO: `--arg mode=check` の節が無い。書かずにディスク上と比べ、食い違えば落ちる。

    欠けている / 中身が違う / 余分 の3種類を1つの例外にまとめて報告する */}

```kt {5-7}
katachi {
    architecture = "com.example.projectArchitecture"

    processors {
        docs {
            outputDir = rootProject.layout.projectDirectory.dir("docs/")
        }
    }
}
```

## 生成されるファイル

`architecture { }` 定義から生成されるファイルは以下のとおりです。

### 通常

- `<出力先ディレクトリ>/README.md`
- `<出力先ディレクトリ>/<Role名>.md`

### グループがある場合

- `<出力先ディレクトリ>/README.md`
- `<出力先ディレクトリ>/<Role名>.md`
- `<出力先ディレクトリ>/<グループ名>/README.md`
- `<出力先ディレクトリ>/<グループ名>/<Role名>.md`

{/* TODO: group はネストできるので `<グループ名>/<ネストしたグループ名>/...` も出る。
    ファイル名は識別子であって title ではない（title を変えてもファイル名は変わらない）ことも書く */}

## ドキュメント生成に利用されるプロパティ

ドキュメントは、Role と group に設定したプロパティから生成されます。

### Role

| プロパティ | 生成されるドキュメントでの役割 | 使用されるページ |
|---|---|---|
| `title` | 役割ページの見出し。既定は役割の識別子 | `<Role名>.md`、および索引・一覧のリンク文字列 |
| `summary` | 一覧の表に入る1行 | `<Role名>.md`、親の `README.md` |
| `description` | 役割ページの本文。書いた Markdown が改行も含めてそのまま入ります。katachi は構造を足さないので、**中の見出しは書き手が決めます** | `<Role名>.md` |
| `example(name, description)` | 具体例。1つの例につき1回呼びます。**呼んだ順**に並びます | `<Role名>.md` の `## 例` |
| `documented` | `false` にするとドキュメントに出ません。ドキュメント化されないだけで **assert() などの検査には引き続き参加します** | --- |

### group

group に設定できるのは Role と同じ4つです。**`example()` だけがありません。**

| プロパティ | 生成されるドキュメントでの役割 | 使用されるページ |
|---|---|---|
| `title` | group の README の見出し。既定は group の識別子 | `README.md`, `<グループ名>/README.md` |
| `summary` | 親の Document map と group の節に出る1行 | `README.md`, `<グループ名>/README.md` |
| `description` | group の README の本文。 | `<グループ名>/README.md` |
| `documented` | `false` にすると group ごとドキュメントに出ません。検査には参加します | --- |

<details>
    <summary>注意: documented は継承されません</summary>

    `documented = false` にした group の中の Role は、**自分でも `documented = false` と書かない限りドキュメントに出ます。** ネストした group も同じです。

    ```kt
    "build".group {
        documented = false
        "VersionCatalog" { documented = false }   // group 側だけでは足りない
    }
    ```

</details>

title などデフォルトで用意されているセクションに加えて、独自のセクションをドキュメントに追加したい場合は `documentSection()` を使ってセクションを定義します。

## まとめ

- ドキュメントは**検査と同じ定義**から生成されます。2つを別々に書かないので、**ドキュメントと実体がずれません**。
- 生成されるのは2軸です。**役割ページ**（この役割は何で、どこに置くか）と、**group の README の配置ツリー**（このディレクトリに何が置けるか）。
{/* TODO: 配置ツリーは group の README だけでなく、ルート README にも `## ルート直下の配置` として出る。
    「group の README の」を「コンテナページの」相当に直す */}
- **`## 制約` に出るのは名前付きの `konsist { }` だけ**です。名前を書けば載るので、書く動機が自然に生まれます。
