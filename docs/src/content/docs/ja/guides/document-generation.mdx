katachi は `architecture { }` 定義から markdown ドキュメントを生成できます。

## 基本

build.gradle.kts に以下のように設定します。

```kts title="architecture-test/build.gradle.kts" {2-3}
katachi {
    // ⭐️ `architecture { }` を定義しているプロパティの FQCN を設定
    architecture = "com.example.projectArchitecture"
}
```

{/* TODO: `docs` は plugin が既定で登録しているので `processors { register("docs", ...) }` は要らない、と明記する。いまの書き方だと登録が要るのかどうか読み取れない */}

設定したら、Gradle タスク `katachiDocs` を実行すると、ドキュメントが生成されます。

```shell
./gradlew katachiDocs
```

### 生成例

次の定義を例にします。

```kt
val modulePackage = capitalizedModuleNamePackage("com.example")

architecture {
    title = "myapp"

    "domain".group {
        title = "Domain レイヤー"
        summary = "アプリ固有の振る舞いと、その対象になる値"

        "UseCase" {
            title = "ユースケース"
            summary = "各画面で発生するアプリ固有の1つの振る舞い"
            example("GetItemListUseCase", "商品の一覧")
            example("SignInUseCase", "サインイン")
            layout { ":core:domain".module { mainSourceSet / kotlin / modulePackage / "useCase" / "*UseCase".ktFile() } }
            "invoke メソッドのみを持つ".konsist { /* ... */ }
        }

        "Repository" {
            title = "リポジトリ"
            summary = "データの取得と保存の境界"
            layout { ":core:domain".module { mainSourceSet / kotlin / modulePackage / "repository" / "*Repository".ktFile() } }
        }
    }
}
```

## 出力先ディレクトリ

ドキュメントは、デフォルトでは `build/katachi/docs/` 配下に生成されます。

出力先は、build.gradle.kts で `katachi.processors.docs.outputDir` を設定すると変更できます。

{/* TODO: 出力先を `build/` の外にすると `gitTracked()` が生成物を拾い、
    「どの役割も宣言していないファイル」として検査が落ちる。**役割として宣言する**必要がある。
    sample/<name>/docs がまさにその形なので、そこを実例として指す */}

{/* TODO: ルートページの `title` / `description` の節が無い。
    `architecture { title = "..."; description = "..." }` の2つで、group や役割に書くのと同じ語。
    書かなければ見出しは `Architecture documentation`、本文は出ない。
    **build.gradle.kts からは設定できない**（0.2 で `docs { rootTitle }` と `--arg rootTitle` を
    廃止した。書ける場所は定義の中の1箇所だけ） */}

{/* TODO: `--arg mode=check` の節が無い。書かずにディスク上と比べ、食い違えば落ちる。
    生成物をコミットしている場合に CI で「最新か」を見る手段で、いちばん需要がある。
    欠けている / 中身が違う / 余分 の3種類を1つの例外にまとめて報告する */}

```kt {5-7}
katachi {
    architecture = "com.example.projectArchitecture"

    processors {
        docs {
            outputDir = rootProject.layout.projectDirectory.dir("docs/architecture")
        }
    }
}
```

<Aside type="caution">
出力先ディレクトリは katachi が管理します。その回に生成しなかった `*.md` は削除されます（`.md` 以外のファイルは残り、削除したファイルはログに1件ずつ出ます）。手書きの Markdown があるディレクトリを出力先にすると、その Markdown が消えます。専用のディレクトリを指定してください。

`outputDir` には String / Directory / File を渡せます。String はモジュールからの相対パス、Directory と File は絶対パスとして扱います。
</Aside>

## 生成されるファイル

`architecture { }` 定義から生成されるファイルは以下のとおりです。

### 通常

<FileTree>
- \<出力先ディレクトリ>/
  - README.md
  - \<Role名>.md
</FileTree>

### グループがある場合

<FileTree>
- \<出力先ディレクトリ>/
  - README.md
  - \<Role名>.md
  - \<グループ名>/
    - README.md
    - \<Role名>.md
    - \<ネストしたグループ名>/
      - README.md
      - \<Role名>.md
</FileTree>

group は入れ子にでき、入れ子の group はその親の group のディレクトリの下に出ます。

ファイル名とディレクトリ名は、`title` ではなく**識別子**（`"UseCase" { }` の `UseCase`、`"domain".group { }` の `domain`）で決まります。`title` を変えても、ファイル名は変わりません。

## ドキュメント生成に利用されるプロパティ

ドキュメントは、Role と group に設定したプロパティから生成されます。

### Role

| プロパティ | 生成されるドキュメントでの役割 | 使用されるページ |
|---|---|---|
| [`title`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/title.html) | 役割ページの見出し。既定は役割の識別子 | `<Role名>.md`、および索引・一覧のリンク文字列 |
| [`summary`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/summary.html) | 一覧の表に入る1行 | `<Role名>.md`、親の `README.md` |
| [`description`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/description.html) | 役割ページの本文。書いた Markdown が改行も含めてそのまま入ります。katachi は構造を足さないので、**中の見出しは書き手が決めます** | `<Role名>.md` |
| [`example(name, description)`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/example.html) | 具体例。1つの例につき1回呼びます。**呼んだ順**に並びます | `<Role名>.md` の `## Examples` |
| [`documented`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/documented.html) | `false` にするとドキュメントに出ません。出ないだけで、**assert() などの検査には引き続き参加します** | --- |

### group

group に設定できるのは Role と同じ4つです。**`example()` だけがありません。**

| プロパティ | 生成されるドキュメントでの役割 | 使用されるページ |
|---|---|---|
| [`title`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/title.html) | group の README の見出し。既定は group の識別子 | `README.md`, `<グループ名>/README.md` |
| [`summary`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/summary.html) | 親の Document map と group の節に出る1行 | `README.md`, `<グループ名>/README.md` |
| [`description`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/description.html) | group の README の本文。 | `<グループ名>/README.md` |
| [`documented`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/documented.html) | `false` にすると group ごとドキュメントに出ません。検査には参加します | --- |

<details>
    <summary>注意: documented は継承されません</summary>

    `documented = false` にした group の中の Role は、**自分でも `documented = false` と書かない限りドキュメントに出ます。** ネストした group も同じです。

    ```kt
    "build".group {
        documented = false
        "VersionCatalog" { documented = false }   // group 側だけでは足りない
    }
    ```

</details>

### 独自のセクション

title などデフォルトで用意されているセクションのほかに独自のセクションをドキュメントへ足したいときは、[`documentSection()`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/document-section.html) でセクションを定義します。

セクションは `documentSection("見出し")` で宣言し、書き込むためのプロパティを `by` で作ります。

```kt
@file:OptIn(ExperimentalKatachiApi::class)

val TestPolicy = documentSection("テスト方針")
var MetadataScope.testPolicy by TestPolicy
```

**プロパティの受け口の型で、どこに書けるかが決まります。**

| 受け口の型 | 書ける場所 |
|---|---|
| `MetadataScope` | group・役割・ルートのどこでも |
| `DeclarationContainerScope` | group とルートだけ（役割には書けない） |
| `RoleScope` | 役割だけ |

セクションは入れ子にできます。`TestPolicy.documentSection("ユニットテスト")` のように、親のセクションに対して宣言します。
**見出しのレベルは深さで決まります。** 最上位が `##` で、1段深くなるごとに `#` が1つ増えます。
親に本文を書いていなくても、子に本文があれば親の見出しは出ます。

独自のセクションは、**組み込みの節（`## Placement` / `## Constraints` / `## Examples`）の後ろ**に、定義の中で書いた順に並びます。

## まとめ

- ドキュメントは**検査と同じ定義**から生成されます。2つを別々に書かないので、**ドキュメントと実体がずれません**。
- 生成されるのは2軸です。**役割ページ**（この役割は何で、どこに置くか）と、**group とルートの README の配置ツリー**（このディレクトリに何が置けるか）。配置ツリーは group の README では `## Placement in this group`、ルートの README では `## Placement at the root` として出ます。
- **`## Constraints` に出るのは名前付きの `konsist { }` だけ**です。名前を書けば載るので、書く動機が自然に生まれます。
