katachi は `architecture { }` 定義から markdown ドキュメントを生成できます。

## ドキュメント生成を実行する

build.gradle.kts に以下のように設定します。

```kts title="architecture-test/build.gradle.kts" {2-3}
katachi {
  // ⭐️ `architecture { }` を定義しているプロパティの FQCN を設定
  architecture = "com.example.projectArchitecture"
}
```

設定したら、Gradle タスク `katachiDocs` を実行すると、ドキュメントが生成されます。

```shell
./gradlew katachiDocs
```

### 生成例

次の定義を例にします。

```kt
architecture {
  title = "myapp"

  "Domain".group {
    title = "Domain レイヤー"
    summary = "アプリ固有の振る舞いと、その対象になる値"

    "UseCase".role {
      title = "ユースケース"
      summary = "各画面で発生するアプリ固有の1つの振る舞い"
      example("GetItemListUseCase", "商品の一覧")
      example("SignInUseCase", "サインイン")
      layout { "core/domain" / mainSourceSet / kotlin / "com/example/core/domain/useCase" / "*UseCase".ktFile() }
    }

    "RepositoryInterface".role {
      title = "リポジトリ"
      summary = "データの取得と保存の境界"
      layout { "core/domain" / mainSourceSet / kotlin / "com/example/core/domain/repository" / "*Repository".ktFile() }
    }
  }
}
```

## 出力先ディレクトリ

ドキュメントは、デフォルトでは `build/katachi/docs/` 配下に生成されます。

出力先は、build.gradle.kts で `katachi.processors.docs.outputDir` を設定すると変更できます。

```kts {6}
katachi {
  architecture = "com.example.projectArchitecture"

  processors {
    docs {
      outputDir = rootProject.layout.projectDirectory.dir("docs/architecture")
    }
  }
}
```

## 生成されるファイル

`architecture { }` 定義から生成されるファイルは以下のとおりです。

### 通常

<FileTree>
- \<出力先ディレクトリ>/
  - README.md
  - \<Role名>.md
</FileTree>

### グループがある場合

<FileTree>
- \<出力先ディレクトリ>/
  - README.md
  - \<Role名>.md
  - \<グループ名>/
    - README.md
    - \<Role名>.md
    - \<ネストしたグループ名>/
      - README.md
      - \<Role名>.md
</FileTree>

group は入れ子にでき、入れ子の group はその親の group のディレクトリの下に出ます。

ファイル名とディレクトリ名は、`title` ではなく**識別子**（`"UseCase".role { }` の `UseCase`、`"Domain".group { }` の `Domain`）で決まります。`title` を変えても、ファイル名は変わりません。

## ドキュメント生成に利用されるプロパティ

ドキュメントは、Role と group に設定したプロパティから生成されます。

### Role

| プロパティ | 生成されるドキュメントでの役割 | 使用されるページ |
|---|---|---|
| [`title`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/title.html) | Role のページの見出し。デフォルトは Role の識別子 | `<Role名>.md`、および索引・一覧のリンク文字列 |
| [`summary`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/summary.html) | 一覧の表に入る1行 | `<Role名>.md`、親の `README.md` |
| [`description`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/description.html) | Role のページの本文。書いた Markdown が改行も含めてそのまま入ります。katachi は構造を足さないので、中の見出しは書き手が決めます | `<Role名>.md` |
| [`example(name, description)`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/example.html) | 具体例。1つの例につき1回呼びます。呼んだ順に並びます | `<Role名>.md` の `## Examples` |
| [`documented`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/documented.html) | `false` にするとドキュメントに出ません。出ないだけで、assert() などの検査には引き続き参加します | --- |

### group

group に設定できるのは Role と同じ4つです。`example()` だけがありません。

| プロパティ | 生成されるドキュメントでの役割 | 使用されるページ |
|---|---|---|
| [`title`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/title.html) | group の README の見出し。デフォルトは group の識別子 | `README.md`, `<グループ名>/README.md` |
| [`summary`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/summary.html) | 親の Document map と group のセクションに出る1行 | `README.md`, `<グループ名>/README.md` |
| [`description`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/description.html) | group の README の本文 | `<グループ名>/README.md` |
| [`documented`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/documented.html) | `false` にすると group ごとドキュメントに出ません。検査には参加します | --- |

<details>
    <summary>注意: documented = false は group の中身ごと外します</summary>

    `documented = false` にした group は、中の Role とネストした group もまとめてドキュメントに出なくなります。 中の Role が自分で何と書いていても同じです。

    ```kt
    "Build".group {
      documented = false
      "VersionCatalog".role { }   // group と一緒にドキュメントから外れる
    }
    ```

    値そのものは中の Role や group に写されません（それぞれ自分が書いた値を持ちます）。自作の processor でこの値を見るときは、`Role.groupPath` をたどって親の group の値も見てください。

</details>

### 独自のセクション

title などデフォルトで用意されているセクションのほかに、独自のセクションをドキュメントへ足したいときは、[`documentSection()`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/document-section.html) でセクションを定義します。

セクションは `documentSection("見出し")` で宣言し、書き込むためのプロパティを `by` で作ります。

```kt
val TestPolicy = documentSection("テスト方針")
var MetadataScope.testPolicy by TestPolicy
```

<details>
    <summary>セクションを入れ子にする</summary>

    セクションは入れ子にできます。`TestPolicy.documentSection("Unit test")` のように、親のセクションに対して宣言します。
    見出しのレベルは深さで決まります。 最上位が `##` で、1段深くなるごとに `#` が1つ増えます。
    親に本文を書いていなくても、子に本文があれば親の見出しは出ます。

    <CodeComparison>
        <CodeComparison.Panel label="セクションの定義">
            ```kt
            val TestPolicy = documentSection("テスト方針")
            var MetadataScope.testPolicy by TestPolicy

            val UnitTest = TestPolicy.documentSection("Unit test")
            var MetadataScope.unitTest by UnitTest

            val projectArchitecture = architecture {
              "UseCase".role {
                title = "ユースケース"
                summary = "各画面で発生するアプリ固有の1つの振る舞い"
                example("SignInUseCase", "サインイン")
                layout { "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile() }

                unitTest = "Repository を偽物に差し替えて、戻り値を確かめる。"
              }
            }
            ```
        </CodeComparison.Panel>
        <CodeComparison.Panel label="生成されるマークダウン">

            | Path | When to use |
            |---|---|
            | `src/main/kotlin/com/example/useCase/*UseCase.kt` |  |

            - `SignInUseCase` ... サインイン

            ## テスト方針                                  ← 本文は無いが、子があるので出る

### `ktFileContent { }` のセクション

[`ktFileContent { }`](/katachi/ja/guides/kt-file-content/) を書いた Role のページには、`## Constraints` と `## Examples` のあいだに `## Kotlin file content` のセクションが出ます。
このセクションは、`ktFileContent { }` に書いた宣言を、例のファイルに当てはめた表です。

<CodeComparison>
    <CodeComparison.Panel label="Role 定義">
        ```kt nocollapse
        "ViewModel".role {
          summary = "画面の状態を StateFlow で公開し、画面からのイベントを受け取る"
          example("HomeViewModel", "ホーム画面の状態")

          layout {
            "feature" / capture("feature") / mainSourceSet / kotlin / "**" / "*ViewModel".ktFile()
          }

          ktFileContent {
            `package`("com.example.feature.${captureValue("feature")}")

            `import`("androidx.lifecycle.**")
            `import`("kotlinx.coroutines.**")

            required(`class`, fileName).superclass("ViewModel") {
              required(public, `val`, "uiState").type("StateFlow<${fileName.replace("ViewModel", "UiState")}>")
              allow(private, anythingElse)
            }
          }
        }
        ```
    </CodeComparison.Panel>
    <CodeComparison.Panel label="生成されるマークダウン">
        ```md title="ViewModel.md（抜粋）" nocollapse
        ## Kotlin file content

        Example: `HomeViewModel.kt`

        | Package |
        |---|
        | `com.example.feature.<feature>` |

        | Import | |
        |---|---|
        | `androidx.lifecycle.**` | optional |
        | `kotlinx.coroutines.**` | optional |

        | Declaration | |
        |---|---|
        | `class HomeViewModel : ViewModel` | required |

        ### Members of `class HomeViewModel`

        | Member | |
        |---|---|
        | `public val uiState: StateFlow<HomeUiState>` | required |
        | `private` (anything) | optional |
        ```
    </CodeComparison.Panel>
</CodeComparison>

例のファイルは、次の順に決まります。

1. Role の `example(…)` の最初の名前（`example("HomeViewModel")` なら `HomeViewModel.kt`）
2. `example(…)` が無ければ、その Role に該当したプロジェクトのファイルのうち最初のもの
3. どちらも無ければ `Sample.kt`

例のファイルの名前から分からない capture の値は、`com.example.feature.<feature>` の `<feature>` のように、capture の名前で出ます。

## まとめ

title / summary / description / example / layout を全部使った Role の定義と、生成されるマークダウンは次のとおりです。

```kt nocollapse
"UseCase".role {
  title = "UseCase"
  summary = "各画面で発生するアプリ固有の1つの振る舞い"
  description = """
    UseCase はアプリ固有の1つの振る舞いを表すクラスです。
  """.trimIndent()

  example("GetItemListUseCase", "商品の一覧を取得する")
  example("SignInUseCase", "サインインする")

  layout {
    "src/main/kotlin/com/example/useCase" /
      "*UseCase".ktFile()
  }
}
```
