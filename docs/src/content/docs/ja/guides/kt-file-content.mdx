`ktFileContent { }` を使うと、Role の Kotlin ファイルに何を置いてよいかを、`layout { }` と同じ許可リスト（allow list）で定義できます。
対象は package・import・ファイル直下の宣言・クラスのメンバの4種類で、書き方は Kotlin のソースと同じ並びです。

```kt {6,8-13,15-19}
"ViewModel" {
    layout {
        "feature" / capture("feature") / mainSourceSet / kotlin / "**" / "*ViewModel".ktFile()
    }
    ktFileContent {
        `package`("com.example.feature.**")

        `import`("kotlin.**")
        `import`("kotlinx.coroutines.**")
        `import`("androidx.**")
        `import`("dagger.hilt.**")             // @HiltViewModel
        `import`("javax.inject.**")            // @Inject
        `import`("com.example.domain.**")

        annotated("HiltViewModel")
            .public.`class`(fileName).superclass("ViewModel") {
                public.`val`("uiState", "StateFlow<${fileName.replace("ViewModel", "UiState")}>")
                public.`fun`("on*")().returns("Unit")
                private.anythingElse()
            }
    }
}
```

package・import・宣言の順に並べ、クラスの `{ }` の中にはそのクラスのメンバを書きます。
修飾子とアノテーションは宣言の前に、親の型・型・引数・戻り値は宣言の後ろに付けます。どれも Kotlin で書くときと同じ位置です。

<details>
<summary>この定義を満たす HomeViewModel.kt</summary>

```kt title="feature/home/src/main/kotlin/com/example/feature/home/HomeViewModel.kt"
package com.example.feature.home

import androidx.lifecycle.ViewModel
import com.example.domain.GetUserUseCase
import dagger.hilt.android.lifecycle.HiltViewModel
import javax.inject.Inject
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow

@HiltViewModel
class HomeViewModel @Inject constructor(
    private val getUser: GetUserUseCase,
) : ViewModel() {
    private val state = MutableStateFlow(HomeUiState())
    val uiState: StateFlow<HomeUiState> = state

    fun onRefresh() {}
}
```

`ktFileContent { }` に import の行を1行でも書くと、書いた行のどれにも当たらない import は違反になります。
そのため `dagger.hilt.**` と `javax.inject.**` の行が無いと、`@HiltViewModel` と `@Inject` の import が違反になります。

</details>

実際に動いている定義は、[sample/android の Role の定義](https://github.com/TBSten/katachi/tree/main/sample/android/architecture-test/src/test/kotlin/com/example/sample/roles) にあります。

## 書いた種類だけが許可リストになる

package・import・ファイル直下の宣言・クラスのメンバのうち、**1行でも書いた種類は許可リストになり**、書いた行のどれにも当たらないものは違反になります。1行も書かなかった種類は見ません。

```kt
// 宣言だけを決める。package と import は見ない
ktFileContent {
    `interface`(fileName)
}
```

```kt
// import だけを決める。宣言は見ない
ktFileContent {
    `import`("kotlin.**")
    `import`("kotlinx.serialization.**")
}
```

メンバも同じです。クラスの行に `{ }` を付けなければ、そのクラスのメンバは見ません。`{ }` を付けると、中に書いた行がメンバの許可リストになります。中身の無い `{ }` は「メンバを1つも置かない」という意味です。

## インストール

`ktFileContent { }` は別アーティファクト `me.tbsten.katachi:katachi-konsist` に入っています。`build.gradle.kts` の依存に追加してください。

```kts title="build.gradle.kts" {2}
dependencies {
    testImplementation("me.tbsten.katachi:katachi-konsist:<version>")
}
```

次に、`projectArchitecture.assert()` に `FileConstraintCheck()` を渡すと、`ktFileContent { }` の検査を実行できます。`assert()` だけでは検査されず、`[UncheckedFileConstraint]` でテストが落ちます。

```kt del={3} ins={4}
@Test
fun `アーキテクチャに沿ったファイル配置になっている`() {
  projectArchitecture.assert()
  projectArchitecture.assert(FileConstraintCheck())
}
```

[`konsist { }`](/katachi/ja/guides/konsist-integration/) も同じアーティファクトに入っていて、検査するのも同じ `assert(FileConstraintCheck())` です。

`ktFileContent { }` は Role のブロックの中に書きます。対象は、その Role の `layout { }` に当てはまる `.kt` ファイルです。`.kts` ファイルは見ません。
`layout { }` の無い Role には書けません。また、1つの Role に書ける `ktFileContent { }` は、今のところ1つだけです。

`ktFileContent { }` は v0.3 の間は実験的な機能で、`@ExperimentalKatachiApi` が付いています。書き方は今後変わる可能性があります。

## 宣言の書き方

### 種類と名前

宣言の行は、Kotlin のキーワードをバッククオートで囲み、名前を渡して書きます。

| 書き方 | 当たるもの |
|---|---|
| `` `class`(名前) `` | class（data class・enum class・sealed class・value class・annotation class を含む） |
| `` `interface`(名前) `` | interface（fun interface を含む） |
| `` `object`(名前) `` | object（data object・companion object を含む） |
| `type(名前)` | class・interface・object のどれか |
| `` `fun`(名前) `` | 関数（拡張関数を含む。名前は受け手を除いた部分） |
| `` `val`(名前) `` / `` `var`(名前) `` | プロパティ（クラスの中では、主コンストラクタの `val`・`var` を含む） |
| `` `typealias`(名前) `` | typealias（ファイル直下だけに書ける） |

### 修飾子

修飾子は、Kotlin と同じく宣言の前に `.` でつなぎます。

```kt
public.data.`class`(fileName)          // public data class HomeUiState
sealed.`interface`(fileName)           // sealed interface HomeAction
const.`val`("*")                       // const val TAG = "Home"
`fun`.`interface`("*Listener")         // fun interface ClickListener
```

書いた修飾子は、すべて付いている必要があります。書かなかった修飾子は問わないので、可視性を書かなければ public でも private でも当たります。
`public` は、`public` と書いた宣言にも、可視性を何も書いていない宣言にも当たります。Kotlin ではどちらも public だからです。

`` data.`interface` `` や `public.internal` のように、どの宣言にも付けられない組み合わせを書くと、定義を読んだ時点でエラーになります。

### アノテーション

アノテーションは `annotated("…")` と書き、修飾子と同じく宣言の前につなぎます。
長くなるときは、次の行を `.` で始めて続けます。Kotlin でアノテーションを上の行に書いたときと同じ見た目です。

```kt
annotated("HiltViewModel")
    .public.`class`(fileName).superclass("ViewModel")      // @HiltViewModel public class HomeViewModel : ViewModel()

annotated("Composable").public.`fun`(fileName)            // @Composable public fun HomeScreen()
annotated("Serializable").data.`object`(fileName)         // @Serializable data object HomeNavKey
```

<Aside type="caution">
`annotated("…")` だけを1行に書いても、次の行の宣言には付きません。次の行を `.` で始めて、1つの宣言としてつなげてください。
</Aside>

アノテーションは単純名で比べます。`annotated("androidx.compose.runtime.Composable")` のように `.` を含めて書くと、完全修飾名で比べます。
引数は見ません。いくつも書いたときは、そのすべてが付いている必要があります。

### 「どれか」を書く

`or` でつなぐと「どれか」になります。修飾子にも、アノテーションにも、種類にも使えます。

```kt
(internal or private).data.`object`("*")                                     // internal か private の data object
(annotated("Preview") or annotated("PreviewLightDark")).private.`fun`("*Preview")
(`class` or `interface`)(fileName)                                           // class か interface。object は当たらない
```

種類は値なので、よく使う組み合わせに自分で名前を付けて使い回せます。
`DeclarationListScope` の拡張プロパティにすると、`ktFileContent { }` の中でだけ使えます。ファイル直下でも、クラスの `{ }` の中でも使えます。

```kt
val DeclarationListScope.classOrInterface get() = `class` or `interface`

ktFileContent {
    classOrInterface(fileName)
}
```

### 親の型・型・引数・戻り値

親の型・プロパティの型・関数の引数・戻り値の型は、宣言の後ろに書きます。

| 書き方 | 意味 |
|---|---|
| `` `class`(fileName).superclass("ViewModel") `` | 親の型（Kotlin で `:` の後ろに書くもの）に `ViewModel` がある。class の継承にも interface の実装にも当たる |
| `` `val`("uiState", "StateFlow<*>") `` | プロパティの型 |
| `` `fun`("load")() `` | 引数が無い |
| `` `fun`("save")("String", "Int") `` | 引数の型が、この順に並ぶ（引数の名前は見ない） |
| `` `fun`("on*")(anyArgs()) `` | 引数は何でもよい（引数を書かないのと同じ） |
| `` `fun`("on*")().returns("Unit") `` | 戻り値の型 |

`superclass` に名前をいくつも書くと、そのすべてを親の型に持つ必要があります。型引数を書かなければ、型引数を外した名前で比べます。たとえば `superclass("Repository")` は `Repository<User>` に当たります。

型は、ソースに書いてある型の文字列と比べます。package の部分は外して比べ、`*` も使えます（`"StateFlow<*UiState>"`）。nullable は区別するので、`"String"` は `String?` に当たりません。
型を書かずに推論させたプロパティや関数は、型を指定した行には当たりません。ただし、戻り値の型を書いていない関数のうちブロック本体のものは、Kotlin と同じく `Unit` を返す関数として扱います。

### package

```kt
`package`("com.example.feature.**")       // com.example.feature の下の package
`package`(matchingDirectory)              // ファイルのディレクトリと一致する package
```

パスは `.` で区切り、`*` は1階層に、`**` は何階層にでも当たります。
`matchingDirectory` は、ソースセットの `kotlin/`（Android の `java/` を含む）より下のディレクトリを `.` でつないだ package です。`src/main/kotlin/com/example/home/HomeScreen.kt` なら `com.example.home` になります。

### import

```kt
`import`("kotlinx.coroutines.**")       // kotlinx.coroutines の下ならどれでも
`import`("kotlinx.coroutines.*")        // kotlinx.coroutines.launch には当たり、kotlinx.coroutines.flow.Flow には当たらない
```

パスの書き方は package と同じです。import は、ファイルに書いてあるパスのまま比べます。
alias（`as`）は見ません。star import（`import a.b.*`）は `a.b.*` というパスとして比べます。Kotlin がデフォルトで読み込む `kotlin.*` などは、ファイルに import が書かれていないので見ません。

## 名前

### `*` で名前の一部を書く

名前の `*` は、`layout { }` のファイル名と同じく1文字以上に当たります。`"*Preview"` は `HomePreview` に当たりますが、`Preview` には当たりません。大文字と小文字は区別します。

### ファイルの名前と capture の値を使う

`fileName` は、いま見ているファイルの名前の、最初の `.` より前の部分です。`GetUserUseCase.kt` なら `GetUserUseCase`、`Platform.android.kt` なら `Platform` になります。
`captureValue("feature")` は、`layout { }` のパスで `capture("feature")` が捕まえた値です。

`ktFileContent { }` のブロックはファイルごとに評価されます。そのため `fileName` と `captureValue(…)` は、どちらもそのファイルの値を持つ普通の `String` です。

| 書いた行 | `HomeViewModel.kt` では | `SettingsViewModel.kt` では |
|---|---|---|
| `` `class`(fileName) `` | `class HomeViewModel` | `class SettingsViewModel` |
| `` `val`("uiState", "StateFlow<${fileName.replace("ViewModel", "UiState")}>") `` | `val uiState: StateFlow<HomeUiState>` | `val uiState: StateFlow<SettingsUiState>` |
| `` `package`("com.example.feature.${captureValue("feature")}") `` | `package com.example.feature.home` | `package com.example.feature.settings` |

`replace` などの String の関数がそのまま使え、`if` でファイルごとに書き分けることもできます。

```kt
// HomeRoute.kt には object HomeRoute と NavGraphBuilder.homeScreen(…) を置く
ktFileContent {
    val feature = fileName.removeSuffix("Route").replaceFirstChar { it.lowercaseChar() }
    `object`(fileName) {
        const.`val`("PATH", "String")
    }
    `fun`("${feature}Screen")
}
```

## 必須と任意

必須か任意かは、`layout { }` と同じ決まりです。

| 名前・パス | 意味 |
|---|---|
| `*` を含まない（`fileName` や `captureValue(…)` を埋めたものも含む） | 必須。ファイルに1つ以上ないと違反になる |
| `*` を含む | 任意。無くてもよく、あれば何個でもよい |

`.optional()` を付けると任意になります。

```kt
ktFileContent {
    `import`("com.example.App")                // 必須。このファイルは App を import していなければならない
    `import`("androidx.compose.**")            // 任意

    `class`(fileName)                          // 必須
    private.const.`val`("TAG").optional()      // 任意
}
```

`*` を含まない import の行も必須になります。1つのクラスの import を許すだけなら、`.optional()` を付けてください。

## 禁止と「ほかは何でもよい」

行の先頭に `not.` を付けると、禁止の行になります。禁止の行に当たったものは、許可の行に当たっていても違反です。禁止の一部を許すときは、`.except(…)` を付けます。

```kt
ktFileContent {
    `import`("**")
    not.`import`("com.example.feature.**")
        .except("com.example.feature.${captureValue("feature")}.**")   // ほかの feature は import しない
}
```

`anythingElse()` は、宣言（ファイル直下とクラスのメンバ）のうち、どの行にも当たらないものを許します。前に修飾子を付けると、その修飾子を持つものだけを許します。
「ほかは何でもよい」を import で書くときは、`` `import`("**") `` と書きます。

```kt
ktFileContent {
    `class`(fileName)
    private.anythingElse()        // private な補助関数や定数は何でもよい
}
```

判定は、禁止の行、許可の行、`anythingElse()` の順に行います。どれにも当たらなければ違反です。

<Aside type="caution">
`not.` の行だけを書いた種類も、許可リストになります。許可の行が無いので、禁止の行に当たらないものもすべて違反です。
一部だけを禁止したいときは、`` `import`("**") `` や `anythingElse()` のように、残りを許す行も一緒に書いてください。
</Aside>

## クラスのメンバ

class・interface・object の行に `{ }` を付けると、そのメンバも許可リストになります。`{ }` の中の書き方は、ファイル直下と同じです。

```kt {5,8-9}
"UseCase" {
    layout { "core/domain" / mainSourceSet / kotlin / "com/example/domain" / "*UseCase".ktFile() }
    ktFileContent {
        `interface`(fileName) {                                    // GetUserUseCase.kt なら interface GetUserUseCase
            operator.`fun`("invoke")
        }
        `class`("Default$fileName").superclass(fileName) {          // class DefaultGetUserUseCase : GetUserUseCase
            override.`fun`("invoke")
            private.anythingElse()
        }
    }
}
```

メンバとして数えるのは、関数・プロパティ・入れ子の class・interface・object です。プロパティには主コンストラクタの `val`・`var` を、object には companion object を含みます。
コンストラクタ・`init` ブロック・enum の項目は数えません。

private・protected・override のメンバも、ほかのメンバと同じく数えます。親から継承したメンバや、data class が作る `copy` のような、ソースに書いていないメンバは見ません。

主コンストラクタの `val`・`var` もメンバなので、`` data.`class`(fileName) { } `` と中身の無い `{ }` を書くと、プロパティを1つも持てません。プロパティを許すときは、`{ }` の中に `` `val`("*") `` のように書いてください。

## 既存のプロジェクトに入れるとき

`ktFileContent { }` は、何も特別扱いしません。private の宣言も、外部ライブラリの import も、同じ Role のファイルの import も、書かなければ違反になります。

既存のプロジェクトに入れるときは、広く許す行から始めると進めやすいでしょう。宣言は、必ず置くものの行に `anythingElse()` を添えて、ほかの宣言を許しておきます。
`` `import`("**") `` で import を全部許し、使わせたくないものだけを `not.` で禁止します。違反を直しながら、`anythingElse()` を外したり import の行を絞ったりして、許すものを減らしていきます。

```kt
ktFileContent {
    `import`("**")
    not.`import`("android.**")

    `class`(fileName)
    anythingElse()
}
```

違反が多くてすぐには直しきれないときは、[Baseline](/katachi/ja/guides/baseline/) で今ある違反を許容し、新しい違反だけをエラーにできます。

## `konsist { }` との分担

`layout { }`・`ktFileContent { }`・`konsist { }` は、次のように決めることを分けています。

| 何を決めるか | 書く場所 |
|---|---|
| ファイルをどこに置いてよいか | `layout { }` |
| package・import と、宣言・メンバの形（種類・修飾子・アノテーション・名前・親の型・型・引数の型・戻り値の型） | `ktFileContent { }` |
| それ以外（式・関数の本文・KDoc・文字列など） | `konsist { }` |

`ktFileContent { }` で書けない規則は、`konsist { }` で Konsist の API を使って書きます。1つの Role に `ktFileContent { }` と `konsist { }` の両方を書けます。
詳しくは [カスタムルールを Konsist で定義する](/katachi/ja/guides/konsist-integration/) を参照してください。

## 生成されるドキュメント

[ドキュメント生成](/katachi/ja/guides/document-generation/) で作る Role のページには、`## Kotlin file content` の節が出ます。`ktFileContent { }` に書いた行を、Role の例のファイルに当てはめて表にしたものです。

## まとめ

- `ktFileContent { }` は、Role の Kotlin ファイルに置いてよい package・import・宣言・メンバを、Kotlin のソースと同じ並びで書く許可リストです。
- **1行でも書いた種類だけが許可リストになります。** 1行も書かなかった種類は見ません。
- 名前に `*` を含まない行は必須、含む行は任意です（`layout { }` と同じ）。`.optional()` で任意にできます。
- `not.` で禁止し、`anythingElse()` と `` `import`("**") `` で残りを許します。
- `fileName` と `captureValue(…)` は、ファイルごとの値を持つ普通の `String` です。
- 依存に `katachi-konsist` を足し、テストで `assert(FileConstraintCheck())` を呼ぶと検査されます。
