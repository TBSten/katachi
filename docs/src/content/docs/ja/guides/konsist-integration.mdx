katachi のコア API は、ディレクトリ構造やファイルの位置に着目して検証します。`"...".konsist { }` を使うと、Konsist の API で **ファイル内の宣言を検証** できます。

## インストール

`"...".konsist { }` はオプション機能として別モジュールに切り出してあるため、別途インストールが必要です。
`build.gradle.kts` に以下を追加してください。

<table>
  <tr>
    <td>バージョン</td>
    <td>`katachi` 本体と同じもの。2つの artifact は常に同じバージョンで公開されます</td>
  </tr>
  <tr>
    <td>同梱する Konsist</td>
    <td>0.17.3</td>
  </tr>
</table>

<Aside type="note">
  Maven Central に `me.tbsten.katachi:katachi-konsist` として公開しています。どのバージョンで何ができるかは [ロードマップ](/katachi/ja/roadmap/) を参照してください。
</Aside>

```kts title="build.gradle.kts" {2}
dependencies {
    testImplementation("me.tbsten.katachi:katachi-konsist:<version>")
}
```

次に、`projectArchitecture.assert()` に `FileConstraintCheck()` を渡すと、Konsist の検証を実行できます。

```kt del={4} ins={1,5}
@OptIn(ExperimentalKatachiApi::class)
@Test
fun `アーキテクチャに沿ったファイル配置になっている`() {
  projectArchitecture.assert()
  projectArchitecture.assert(FileConstraintCheck())
}
```

`FileConstraintCheck` は実験的 API なので、`@OptIn(ExperimentalKatachiApi::class)` が必要です。
`FileConstraintCheck()` を渡さずに `assert()` だけを呼ぶと、制約は評価されず、`[UncheckedFileConstraint]` の違反としてテストが落ちます。

## 基本的な使い方

Role の中で、その Role のファイルにどういう宣言があるのかを定義します。

```kt
architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    "invoke 関数を1つだけ持つこと".konsist {
        classes().must { it.functions().map { f -> f.name } == listOf("invoke") }
    }
  }
}
```

制約の対象は、その Role の `layout { }` に当てはまったファイルです。`layout { }` の無い Role に制約を書くと、定義を評価した時点で `KatachiFileConstraintWithoutLayoutException` になります。

<Aside type="caution">
  `konsist { }` の中で `assertTrue { }` を書くと、**コンパイルエラーになります**（ERROR レベルの `@Deprecated` で塞いでいます）。Konsist の `assertTrue` はその場でアサーションの例外を投げるので、DSL による宣言と検証を分けるという設計に反するためです。
  代わりに must / mustNot / mustBeEmpty を使ってください。
</Aside>

## エラーの例

制約の違反を検知すると、次のようなエラーメッセージが表示されます。

```text
Katachi check failed: 1 violation (FileConstraint: 1)

[UnsatisfiedFileConstraint] src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "invoke 関数を1つだけ持つこと"
  Declaration: GetUserUseCase (line 3)
  Declared at: ProjectArchitecture.kt:12
```

**制約に付けた名前がそのまま出ます。** 制約が複数あるとき、どれが落ちたのかはこの1行で分かるので、名前は「満たすべきこと」の形で書いてください。

## Konsist API

`"...".konsist { }` ブロック内では通常の Konsist API が使えます。

<LinkCard
  title="Konsist のドキュメント"
  href="https://docs.konsist.lemonappdev.com/"
/>

katachi が差し替えているのは `must` / `mustNot` / `mustBeEmpty` の3つだけで、対象を絞るまでの書き方は Konsist のものがそのまま使えます。

## まとめ

- `layout { }` が **どこに置いてよいか**、`konsist { }` が **中身がどうあるべきか** を担当します。
- `katachi-konsist` は**任意のモジュール**です。依存の追加と `assert(FileConstraintCheck())` の設定が必要です。
- **制約名がそのまま違反レポートに出ます。** 名前は「満たすべきこと」の形で書いてください。
- `assertTrue` 系は**コンパイルエラーになります**。その場で例外を投げてしまい、1回の実行で全違反を集める設計と噛み合わないためです。
