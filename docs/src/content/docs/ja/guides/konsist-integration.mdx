katachi のコア API で検証できるのは、ディレクトリ構造やファイルの位置です。ファイルに置いてよい宣言は、[`ktFileContent { }`](/katachi/ja/guides/kt-file-content/) で定義できます。
`ktFileContent { }` で書けない規則は、`"...".konsist { }` を使うと、Konsist の API で書けます。

## インストール

`"...".konsist { }` は、`ktFileContent { }` と同じ別アーティファクト `me.tbsten.katachi:katachi-konsist` に入っています。
依存の追加と、テストで `assert(FileConstraintCheck())` を呼ぶ手順は、[ファイルの中で定義できる宣言の許可リストを定義する](/katachi/ja/guides/kt-file-content/#インストール) を参照してください。

## 基本的な使い方

Role の中で、その Role のファイルにどんな宣言があるべきかを定義します。

```kt {7-8}
architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    "invoke 関数を1つだけ持つこと".konsist {
        classes().must { it.functions().map { f -> f.name } == listOf("invoke") }
    }
  }
}
```

制約の対象は、その Role の `layout { }` に当てはまったファイルです。`layout { }` の無い Role には制約を書けません。

## エラーの例

制約の違反を検知すると、次のようなエラーメッセージが表示されます。

```text
Katachi check failed: 1 violation (FileConstraint: 1)

[UnsatisfiedFileConstraint] file:///path/to/project/src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "invoke 関数を1つだけ持つこと"
  Declaration: GetUserUseCase (line 3)
  Declared at: ProjectArchitecture.kt:12
```

**制約に付けた名前がそのまま出ます。** 制約が複数あるとき、どれが落ちたのかはこの1行で分かるので、名前は「満たすべきこと」の形で書いてください。

## 理由と直し方を添える

`must` / `mustNot` / `mustBeEmpty` には、規則がある理由と、違反の直し方を渡せます。1つめの引数が理由、2つめが直し方の一覧です。

```kt {9-10}
architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    "invoke 関数を1つだけ持つこと".konsist {
        classes().must(
            "UseCase は1つの振る舞いだけを表す",
            listOf("invoke 以外の関数は、別の UseCase に分ける"),
        ) { it.functions().map { f -> f.name } == listOf("invoke") }
    }
  }
}
```

違反には、理由が `Reason:` の行に、直し方が `How to fix:` の下に出ます。

```text
[UnsatisfiedFileConstraint] file:///path/to/project/src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "invoke 関数を1つだけ持つこと"
  Declaration: GetUserUseCase (line 3)
  Reason: UseCase は1つの振る舞いだけを表す
  Declared at: ProjectArchitecture.kt:12

  How to fix:
    - invoke 以外の関数は、別の UseCase に分ける
```

直し方は省略できます。省略すると、`How to fix:` の欄は出ません。

## Konsist API

`"...".konsist { }` ブロック内では通常の Konsist API が使えます。

<LinkCard
  title="Konsist のドキュメント"
  href="https://docs.konsist.lemonappdev.com/"
/>

katachi が足しているのは `must` / `mustNot` / `mustBeEmpty` の3つで、Konsist の `assertTrue` などのアサーションは、コンパイルエラーにして使えないようにしています。対象を絞るまでの書き方は Konsist のものがそのまま使えます。

## まとめ

- `layout { }` が **ファイルをどこに置いてよいか**、`ktFileContent { }` が **ファイルに置く宣言の形**、`konsist { }` が **それ以外の規則** を担当します。
- `katachi-konsist` は**任意のモジュール**です。依存の追加と `assert(FileConstraintCheck())` の設定が必要です。
- **制約名がそのまま違反レポートに出ます。** 名前は「満たすべきこと」の形で書いてください。理由と直し方も `must("理由", listOf("直し方")) { }` の形で添えられます。
- Konsist の `assertTrue` 系は `konsist { }` の中では**使えません**（コンパイルエラーになります）。`must` / `mustNot` / `mustBeEmpty` で書いてください。
