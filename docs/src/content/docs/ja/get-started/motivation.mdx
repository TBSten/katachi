## アーキテクチャドキュメントは必ず実装と乖離する

優秀なあなたのことですから、プロジェクトには `/docs` ディレクトリがあり、プロジェクト全体の構造や各コンポーネントのルールが詳しく書かれていることでしょう。

しかし、**ドキュメントに書かれた「UseCase はこう書く」という文言には、何の強制力もありません**。プロジェクトのルールを知らない新規参入者や、振る舞いに不確実さのある AI Agent は、そのルールをたやすく破りかねません。

## Konsist だけでは足りない

ルールを無視したコードを通さないガードレールとして働くツールの1つに、[Konsist](https://docs.konsist.lemonappdev.com/) があります。

Konsist はプロジェクトのルールを Unit test として記述できます。

```kt
class UseCaseKonsistTest {
  @Test
  fun `UseCase は 1 つの invoke 関数のみを持つ`() {
      Konsist
          .scopeFromProject()
          .classes()
          .withNameEndingWith("UseCase")
          .assertTrue { it.functions().map { function -> function.name } == listOf("invoke") }
  }
}
```

一見すると、Konsist があればプロジェクトのルールを十分に強制できそうです。
しかし実際には、Konsist のある特性のために、それは難しいのです。

:::caution[Scope の外は検証されない]
Konsist は Scope と呼ばれる記法で、プロジェクト内の特定のファイルに絞って検証します。**Scope の外にあるファイルやディレクトリは、検証されません**。
:::

特定のファイルに絞って見るだけでなく、**プロジェクト全体を見渡して検証する手段が必要** です。

## katachi の出番

katachi を使うと、プロジェクト全体を俯瞰して、そこに現れて良いファイルの種類と、その置き方を宣言できます。

```kt
val projectArchitecture = architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/project/useCase" / "*UseCase".ktFile()
    }
  }
}
```

katachi では次の2つを宣言します。

- プロジェクトの中に現れて良いファイルの種類（Role と呼ばれます）
- その Role のファイルがどこに現れて良いか

これを宣言的な DSL で書くと、プロジェクト全体のディレクトリ構造をテストできるようになります。

<Aside title="Deny by default" type="tip">

katachi が採用している Deny by default の原則により、**`projectArchitecture` に宣言されていないファイルはその存在を許されません**。

AI Agent がルールに背くコードを書いたとしても、katachi はその存在を許さず、違反として報告します。
</Aside>

<details>
<summary>このルールによって検知される例</summary>

もし AI Agent が `com.example.project.GetUserUseCase` という名前のファイルを配置した場合:

```kt
// com/example/project/GetUserUseCase.kt
package com.example.project // ❌ 本来は com.example.project.useCase に置くべきです

class GetUserUseCase {
  suspend fun invoke() = ...
}
```

<FileTree>
- src/main/kotlin/com/example/project/
  - **GetUserUseCase.kt** ❌ 宣言されていない場所に置かれた
  - useCase/
    - UpdateUserUseCase.kt ⭐️ 宣言どおりの場所
</FileTree>

katachi を含んだ Unit test を実行すると、以下のようにエラーが報告されます。

```
Katachi check failed: 1 violation (Unexpected: 1)

[UnexpectedFile] file:///path/to/project/src/main/kotlin/com/example/project/GetUserUseCase.kt
  No role is defined for this file.

  Nearby locations:
    UseCase file:///path/to/project/src/main/kotlin/com/example/project/useCase/

  How to fix:
    - Move it to one of the locations above
    - Delete it if it is not needed
    - Add a new role for it:
        "GetUserUseCase" {
          summary = "TODO"
          layout {
            "src/main/kotlin/com/example/project" / "GetUserUseCase".ktFile()
          }
        }
```

</details>

## katachi による自動生成

katachi ではアーキテクチャ定義から様々な物を生成することができます。

<details>
<summary>ドキュメントを生成する</summary>

katachi で書いたプロジェクト構造の定義から、markdown のドキュメントを生成できます。

```shell
$ ./gradlew katachiDocs
```

Gradle plugin の `katachi { architecture = "..." }` で定義の場所を指定しておくと、定義を置いたモジュールの `build/katachi/docs` に書き出されます。

## katachi と Konsist

katachi は Konsist と連携すると、プロジェクト全体を検証したあとで、個々のファイルを別々に検証できます。

```kt
val projectArchitecture = architecture {
  "UseCase" {
    // どこに置いてよいか
    layout {
      "src/main/kotlin/com/example/project/useCase" / "*UseCase".ktFile()
    }

    // 中身がどうあるべきか
    "1 つの invoke 関数のみを持つこと".konsist {
      classes()
        .withNameEndingWith("UseCase")
        .must { it.functions().map { function -> function.name } == listOf("invoke") }
    }
  }
}
```

テストで `assert(FileConstraintCheck())` を呼ぶと、配置の違反と中身の違反が、同じ1つのレポートに並びます。

**katachi でプロジェクト全体の構造をテストし、そのあと Konsist で各ファイルの中身を検証する** という使い分けをおすすめします。

詳しくは [Konsist との統合](/katachi/ja/guides/konsist-integration/) のドキュメントをご覧ください。

## まとめ

- AI を使った開発では、**プロジェクト構造のルールを AI Agent に守らせる手段** が必要です。
- katachi はプロジェクト全体の構造を定義・テストしたり、ドキュメントを生成したりする DSL を提供します。
- プロジェクト全体の構造は katachi、各ファイルの中身は Konsist。**役割が違うので併用します**。
