katachi に似たツールとして、Konsist や ArchUnit などがあります。
これらは **katachi と排他的とは限りません**。

## 比較表

<div class="comparison-table">

| ツール | 何を見るか | どう走るか | katachi と併用 |
|---|---|---|---|
| **katachi** | **ファイルが存在してよいか。どこに置かれるか** | Unit test | — |
| [Konsist](https://docs.konsist.lemonappdev.com/) | クラス・関数・プロパティの中身。scope で絞った範囲 | Unit test | ⭐️ 統合あり/推奨 |
| [detekt](https://detekt.dev/) | ソースの静的解析。コードスメルと自作ルール | Gradle タスク / CLI | 🆗 可能 |
| [ArchUnit](https://www.archunit.org/) | クラス間の依存と層。JVM のクラス情報 | Unit test | 🆗 可能 |
| [ProjectGuard](https://github.com/rubensousa/ProjectGuard) | モジュール同士の依存宣言。ビルドグラフ | Gradle プラグイン | 🆗 可能 |
| [Konture](https://github.com/baole/konture) | モジュール依存・パッケージの閉じ方・クラスの性質 | Unit test | 🆗 統合あり（`katachi-konture`） |

</div>

katachi だけが「そのファイルは存在してよいか」を問います。
ほかの5つはすべて、**すでに存在しているもの**について、中身や関係を検証します。

だから重なりません。むしろ重なるのは**他ツール同士**で、Konsist・ArchUnit・Konture は
互いに守備範囲が近く、3つ全部を入れる意味は薄いはずです。

## katachi と Konsist

Konsist は `Konsist.scopeFromProject()` で対象を絞り、絞った範囲のクラスや関数を検証します。
絞った範囲に入らないものは検証されません（詳しくは [FAQ](/katachi/ja/get-started/faq/) をご覧ください）。

katachi はその逆で、プロジェクト全体を走査して宣言と突き合わせます。
**「配置」と「中身」で担当が分かれる**ので、どちらか片方だけでは検証できない部分が残ります。

katachi は `katachi-konsist` という任意モジュールでこの2つを繋ぎます。
Role の中に `ktFileContent { }` を書き、テストで `assert(FileConstraintCheck())` を呼ぶと、**配置の違反と中身の違反が1つのレポートにまとまります。**

```kt title="ProjectArchitecture.kt"
"UseCase".role {
  // どこに置いてよいか — katachi の担当
  layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
  }

  // 中身がどうあるべきか — katachi-konsist の担当
  ktFileContent {
    `package`("**")
    `import`("**")

    required(`class`, fileName) {
      required(suspend.optional(), operator, `fun`, "invoke")(anyArgs()) // invoke 関数が必ず 1 つ
      allow(private, anythingElse)
    }
  }
}
```

### Role の性質を ktFileContent で書く

Role の性質を、そのファイルに置いてよい宣言の許可リストとして書けます。許可リストに無い宣言は違反になります。

<details>
<summary>`UseCase` は `invoke` 関数を1つだけ持つ</summary>

Role の定義そのものです。

```kt nocollapse
"UseCase".role {
  layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
  }

  ktFileContent {
    `package`("com.example.useCase")
    `import`("**")

    required(`class`, fileName) {
      required(suspend.optional(), operator, `fun`, "invoke")(anyArgs())
      allow(private, anythingElse) // invoke のほかに public な関数を書くと違反
    }
  }
}
```

</details>

<details>
<summary>`Repository` は interface として宣言される</summary>

実装の差し替えを前提にした層で役に立ちます。

```kt nocollapse
"Repository".role {
  layout {
    "src/main/kotlin/com/example/repository" / "*Repository".ktFile()
  }

  ktFileContent {
    `package`("com.example.repository")
    `import`("**")

    required(`interface`, fileName) { // class で宣言すると違反
      allow(suspend.optional(), `fun`, "*")
    }
  }
}
```

</details>

<details>
<summary>Role のファイルは外から使える可視性を持つ</summary>

```kt nocollapse
"UseCase".role {
  layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
  }

  ktFileContent {
    `package`("com.example.useCase")
    `import`("**")

    required(public, `class`, fileName) { // internal や private を付けると違反
      allow(anythingElse)
    }
  }
}
```

</details>

<details>
<summary>`ViewModel` は Android の View 型を参照しない</summary>

層の漏れを中身の側から止めます。書いた `import` だけが許可されるので、`android.view` を並べなければ、import した時点で違反になります。

```kt nocollapse
"ViewModel".role {
  layout {
    "src/main/kotlin/com/example/viewModel" / "*ViewModel".ktFile()
  }

  ktFileContent {
    `package`("com.example.viewModel")

    `import`("kotlin.**")
    `import`("kotlinx.coroutines.**")
    `import`("androidx.lifecycle.**")
    `import`("com.example.**")

    required(`class`, fileName) {
      allow(anythingElse)
    }
  }
}
```

</details>

<details>
<summary>`data` 層のクラスは特定のアノテーションを持つ</summary>

シリアライズ対象の取りこぼしを防ぎます。

```kt nocollapse
"DataModel".role {
  layout {
    "src/main/kotlin/com/example/data" / "*Dto".ktFile()
  }

  ktFileContent {
    `package`("com.example.data")
    `import`("kotlinx.serialization.**")

    allow(annotated("Serializable"), data, `class`, "*") { // @Serializable の無い class は違反
      allow(`val`, "*")
    }
  }
}
```

</details>

## katachi と detekt

detekt は Kotlin のソースを静的解析して、コードスメルやスタイルの逸脱を指摘します。
自作ルールを書けば、プロジェクト固有の約束も検査できます。

見ている単位がファイルの中身なので、katachi とは衝突しません。
katachi が「このファイルはここに置いてよい」を決め、detekt が「その中身がどう書かれているか」を見ます。

katachi は detekt との統合を持っていませんが、役割分担としては問題なく機能します。

### detekt と `ktFileContent { }` の使い分けを決める

detekt と `ktFileContent { }` のどちらに書くか迷う場面があります。目安は2つです。

- **レポートを1つにまとめたいなら `ktFileContent { }`。**
  `assert(FileConstraintCheck())` で検査すれば配置の違反と並んで出るので、直す材料が1回のテスト実行で揃います
- **プロジェクト全体に一律で規則をかけたいなら detekt。**
  Role に紐づかない約束（関数の長さ、複雑度、命名の一般則）は、Role の中に書いても
  意味が薄くなります

detekt が向いているもの:

- 関数の長さ・ネストの深さ・循環的複雑度
- `println` や `TODO()` の残存
- 特定の API の使用禁止（プロジェクト共通のもの）
