katachi は「同じ定義から**テストとドキュメントの両方**を出す」ライブラリです。いまはその前半、**テスト**だけが動きます。

並び順は **外部依存の少ない順、かつ利用者の負担が増えない順** です。各段階で単独で価値が出るようにしてあります。

<Aside type="note" title="リリース済みは v0.1 だけ">
Maven Central に出ているのは v0.1.0 です。このページのそれより先のバージョンは計画であって、リリース済みのものではありません。
</Aside>

## 全体像

| バージョン | テーマ | 完了と言える条件 |
|---|---|---|
| **v0.1** | DSL + 検査 + `konsist { }` | 大規模なプロジェクトを表現でき、検査が通る |
| **v0.2** | `declarations { }` | v0.1 で書いた `konsist { }` の大半を置き換えられる |
| **v0.3** | Gradle plugin + ドキュメント生成 | `./gradlew generateKatachiDocs` でドキュメントが出る |
| **v0.4 以降** | baseline / レポート出力 / 語彙数の計測 | **既存プロジェクト**に導入できる |

## v0.1 — 定義と検査

最初のリリースです。**Deny by default のアーキテクチャテスト**として出します。

<Steps>

1. **役割を起点にした DSL**

   「どの役割のファイルをどこに置けるか」を1箇所に書けます。[Role](/katachi/ja/guides/role/) と [Layout](/katachi/ja/guides/layout/) がこれにあたります。

2. **宣言していないファイルが増えたら落ちる**

   書いた allow list と実際のファイルツリーを突き合わせ、載っていないもの（`Unexpected`）と、あるはずなのに無いもの（`Missing`）を報告します。

3. **ファイルの中身の制約**

   `"名前".konsist { }` に Konsist の式を書けば、配置だけでなく中の宣言も検査できます。[Konsist との統合](/katachi/ja/guides/konsist-integration/) を参照してください。

</Steps>

出る artifact は 2 つです。

| artifact | 中身 |
|---|---|
| `katachi` | 本体。**実行時依存ゼロ** |
| `katachi-konsist` | `konsist { }` の実装。任意 |

**対象は新規プロジェクトです。** 既存プロジェクトに入れると既存の違反が一度に噴き出すので、それを扱う仕組み（baseline）は v0.4 以降になります。

## v0.2 — `declarations { }`

v0.1 の `konsist { }` は、言ってしまえば**逃げ道**です。「ファイル名と同じクラスが1つだけあること」のようなよくある制約を、毎回 Konsist の式で書き下すことになります。

v0.2 では、そこから**一級機能であるべきものを昇格**させます。

- 役割ごとに「このファイルに置いてよい top-level 宣言」を**列挙**する
- 列挙されていない宣言は禁止される — **deny by default がファイルの中身にも及ぶ**
- 違反したとき「期待 / 実際」と、リネーム先のような**具体的な直し方**が出る

前提として、v0.1 を実プロジェクトで使い込み、`konsist { }` のブロックが溜まっていることが要ります。**何を昇格させるべきかは、溜まったものを見てから決めます。**

## v0.3 — Gradle plugin とドキュメント生成

katachi の売りが揃う段階です。

```shell
./gradlew generateKatachiDocs
```

プラグインを適用するだけで、**テストと同じ定義から** Markdown が 2 軸で生成されます。

- **役割リファレンス** — この役割は何で、どこに置くか
- **ディレクトリ構成** — このディレクトリに何が置けるか

両方が同じモデルから導かれるので、**互いに矛盾しません。** そして生成したドキュメント自体も検査の対象になります。

[ArchitectureProcessor とそのカスタマイズ](/katachi/ja/guides/processor/) で説明している仕組みが、ここで使われます。`assert()` と同じ interface の上に乗るので、特別扱いはありません。

## v0.4 以降 — 既存プロジェクトへの導入

ここまでは新規プロジェクト専用です。既存プロジェクトに入れられるようにするのが v0.4 以降の主題です。

| 機能 | 何ができるか |
|---|---|
| **baseline** | 既存の違反を記録し、**新しく増えた分だけ**で落とす |
| **レポート出力** | JSON / SARIF で出し、GitHub の PR にアノテーションとして載せる |
| **語彙数の計測** | 役割の数と、役割ごとのファイル数を数値で出す |
| **`pairedWith`** | 「すべての `Screen` に対応する `Preview` がある」のような網羅性を検査する |

**なぜ baseline が最後なのか。** baseline は「いまの違反を見なかったことにする」仕組みです。先に入れてしまうと、katachi を入れても何も起きないプロジェクトが量産されます。まず**新規プロジェクトで価値が出ること**を確かめてから出します。

この段階の仕様はまだほとんど決まっていません。バージョン番号の割り当ても「v0.4 以降」とひとまとまりです。
