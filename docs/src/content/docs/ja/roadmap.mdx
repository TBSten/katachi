## v0.2 — Gradle plugin・ドキュメント生成・`declarations { }`

katachi の売りが揃う段階で、**いま実装中**です。Gradle plugin の足場と、その上で処理を走らせる仕組み（processor）、**ドキュメント生成**、テンプレートからのコード生成、IDE プラグイン、baseline（実験的）までが動いています。**`declarations { }` はこれからです。**

```shell
./gradlew katachiDocs
```

プラグインを適用すれば、**テストと同じ定義から** Markdown を 2 軸で生成できます。

- **役割リファレンス** — この役割は何で、どこに置くか
- **ディレクトリ構成** — このディレクトリに何が置けるか

両方が同じモデルから導かれるので、**互いに矛盾しません。** 生成したあとのリンク切れも機械的に検査します。

出力の形は [ドキュメント生成](/katachi/ja/guides/document-generation/) に、走らせる仕組みは [ArchitectureProcessor とそのカスタマイズ](/katachi/ja/guides/processor/) に書いてあります。ドキュメント生成は processor の1つにすぎず、利用者が書いた処理も同じタスクから呼べます。

### `declarations { }` — `konsist { }` からの昇格

v0.1 の `konsist { }` は、言ってしまえば**逃げ道**です。「`*UseCase` interface と `Default*UseCase` class だけを置く」のように、ほとんどの役割が言いたいことでも、毎回 Konsist の式で書き下すことになります。

```kt
"interface と Default 実装のみ".konsist {
    files.must { file ->
        val decls = file.declarations(includeNested = false, includeLocal = false)
        decls.size == 2 &&
            decls.any { it is KoInterfaceDeclaration && it.name.endsWith("UseCase") } &&
            decls.any { it is KoClassDeclaration && it.name.startsWith("Default") }
    }
}
```

同じ規則が、こう読めるようにしたい。

```kt
"UseCase" {
    declarations {
        `interface`("*UseCase")
        `class`("Default*UseCase")
    }
}
```

列挙していない top-level 宣言は書けません。2つめのクラスも、トップレベルの拡張関数も、置き忘れた `typealias` も。`layout { }` が配置の allow list であるのと同じ意味で、このブロックが中身の allow list になります。

katachi は「何が期待されていたか」を知っています。だから違反のときに、「制約が落ちた」以上のことを言えます。

```
[UnsatisfiedFileConstraint] core/domain/.../GetUserUseCase.kt
  The top-level declarations do not match what role UseCase allows.
  Expected: interface *UseCase, class Default*UseCase
  Actual:   interface GetUserUseCase, class GetUserUseCaseImpl, object Factory
  How to fix:
    - Rename GetUserUseCaseImpl to DefaultGetUserUseCase
    - Delete object Factory, or move it to another file
```

**上の形は素案で、確定ではありません。** 何を昇格させるかは、v0.1 を実プロジェクトで使って**溜まった `konsist { }` を見てから**決めます。材料が足りなければ、この機能だけ次の版へ回します。ドキュメント生成より後に実装するのはそのためです。

### そのほか v0.2 に入るもの

| 機能 | 何ができるか |
|---|---|
| [`template { }`](/katachi/ja/guides/generate-code-from-template/) | 役割に適合するファイルをテンプレートから生成する。引数は型付きで受けられる（`stringParameter()` / `booleanParameter()` / `intParameter()` / `enumParameter()`） |
| IDE プラグイン | IntelliJ IDEA / Android Studio のツールウィンドウからテンプレートを選び、引数を埋めてコードを生成する |
| **baseline**（実験的） | 既存の違反を台帳のファイルに記録し、**新しく増えた分だけ**で落とす。`architecture { baseline = baselineFile() }` と書き、`-Dkatachi.baseline.update=true` で記録、`-Dkatachi.baseline.prune=true` で直した分を台帳から消す |
| `dependsOnlyOn` | 依存してよい先を**許可リスト**で書く。禁止リスト方式は書き漏れが素通りする |
| ディレクトリの `konsist { }` の直下限定 | サブツリー全体ではなく、直下のファイルだけに効かせる |

## v0.3 以降 — 既存プロジェクトへの導入

既存プロジェクトに入れやすくするのが v0.3 以降の主題です。今ある違反を棚上げする baseline だけは、実験的な機能として v0.2 に先に入りました。

| 機能 | 何ができるか |
|---|---|
| **レポート出力** | JSON / SARIF で出し、GitHub の PR にアノテーションとして載せる |
| **語彙数の計測** | 役割の数と、役割ごとのファイル数を数値で出す |
| **`pairedWith`** | 「すべての `Screen` に対応する `Preview` がある」のような網羅性を検査する |

この段階の仕様はまだほとんど決まっていません。バージョン番号の割り当ても「v0.3 以降」とひとまとまりです。
