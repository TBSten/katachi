## Architecture documentation always drifts from the implementation

Being the diligent developer you are, your project surely has a `/docs` directory that spells out the overall structure and the rules for every component.

But **the sentence "a UseCase is written like this" in that documentation has no power to enforce anything**. A newcomer who does not know the project's rules, or an AI agent that is uncertain by nature, can break those rules without effort.

## Konsist alone is not enough

[Konsist](https://docs.konsist.lemonappdev.com/) is one of the tools that act as a guardrail against code that ignores project rules like these.

Konsist lets you write your project's rules as unit tests.

```kt
class UseCaseKonsistTest {
  @Test
  fun `a UseCase has exactly one invoke function`() {
      Konsist
          .scopeFromProject()
          .classes()
          .withNameEndingWith("UseCase")
          .assertTrue { it.functions().map { function -> function.name } == listOf("invoke") }
  }
}
```

At first glance Konsist looks like all you need to enforce your project's rules.
In practice, the way Konsist works makes that hard.

:::caution[Nothing outside the scope is checked]
Konsist uses a notation called a scope to narrow checking down to particular files in the project. **Files and directories outside that scope are never checked.**
:::

Focusing on particular files is not enough. **You need a way to check the project as a whole.**

## Where katachi comes in

katachi looks at the whole project from above and lets you declare which kinds of files may appear in it and where they may be placed.

```kt
val projectArchitecture = architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/project/useCase" / "*UseCase".ktFile()
    }
  }
}
```

katachi has you declare two things:

- The kinds of files that may appear in the project (these are called Roles)
- Where the files of that Role may appear

Writing this in a declarative DSL lets you test the directory structure of the entire project.

import { Aside, FileTree } from '@astrojs/starlight/components';
import CodeComparison from '../../../components/CodeComparison';

<Aside title="Deny by default" type="tip">

Under the Deny by default principle that katachi adopts, **a file that is not declared in `projectArchitecture` is not allowed to exist**.

Even if an AI agent writes code that breaks the rules, katachi refuses to let it exist and reports it as a violation.
</Aside>

<details>
<summary>An example this rule catches</summary>

Suppose an AI agent places a file named `com.example.project.GetUserUseCase`:

```kt
// com/example/project/GetUserUseCase.kt
package com.example.project // ❌ this belongs in com.example.project.useCase

class GetUserUseCase {
  suspend fun invoke() = ...
}
```

<FileTree>
- src/main/kotlin/com/example/project/
  - **GetUserUseCase.kt** ❌ placed somewhere that was never declared
  - useCase/
    - UpdateUserUseCase.kt ⭐️ exactly where the declaration says
</FileTree>

Running the unit test that includes katachi reports the error like this:

```
Katachi check failed: 1 violation (Unexpected: 1)

[UnexpectedFile] src/main/kotlin/com/example/project/GetUserUseCase.kt
  No role is defined for this file.

  Nearby locations:
    UseCase    src/main/kotlin/com/example/project/useCase/

  How to fix:
    - Move it to one of the locations above
    - Delete it if it is not needed
    - Add a new role for it:
        "GetUserUseCase" {
          summary = "TODO"
          layout {
            "src/main/kotlin/com/example/project" / "GetUserUseCase".ktFile()
          }
        }
```

</details>

## Generate documentation

From the project structure you defined with katachi, you can have Markdown (or MDX) documentation generated.

```shell
$ ./gradlew generateKatachiDocs
```

<CodeComparison>
<CodeComparison.Panel label="Architecture definition" labelVariant="note">
```kt title="ProjectArchitecture.kt"
val projectArchitecture = architecture {
  "UseCase" {
    title = "Use case"
    summary = "A single app-specific behavior that occurs on a screen"

    example("GetUserUseCase", "Gets a user")
    example("UpdateUserUseCase", "Updates a user")

    layout {
      "src/main/kotlin/com/example/project/useCase" {
        description = "Ones used from more than one screen"
        "*UseCase".ktFile()
      }
    }
  }

  // ...
}
```

</CodeComparison.Panel>

<CodeComparison.Panel label="Generated Markdown" labelVariant="success">
```md title="docs/UseCase.md"

A single app-specific behavior that occurs on a screen

## Locations

| Path | When to use it |
|---|---|
| `src/main/kotlin/com/example/project/useCase/*UseCase.kt` | Ones used from more than one screen |

## Examples

- `GetUserUseCase` ... Gets a user
- `UpdateUserUseCase` ... Updates a user
```

</CodeComparison.Panel>
</CodeComparison>

Treat the project structure you defined with katachi as the single source of truth, and generate documentation that both humans and AI agents can read.

## katachi and Konsist

katachi works together with Konsist: it verifies the project as a whole, then checks each individual file.

```kt
val projectArchitecture = architecture {
  "UseCase" {
    // where it may be placed
    layout {
      "src/main/kotlin/com/example/project/useCase" / "*UseCase".ktFile()
    }

    // what its contents should look like
    "has exactly one invoke function".konsist {
      classes()
        .withNameEndingWith("UseCase")
        .assertTrue { it.functions().map { function -> function.name } == listOf("invoke") }
    }
  }
}
```

Placement violations and content violations line up in one and the same report.

The recommended split is to **test the structure of the whole project with katachi, then check the contents of each file with Konsist**.

See [Konsist integration](/katachi/guides/konsist-integration/) for the details.

## Summary

- Developing with AI calls for **a way to make AI agents follow the rules about project structure**.
- katachi gives you a DSL for defining and testing the structure of the whole project, and for generating documentation from it.
- katachi for the structure of the whole project, Konsist for the contents of each file. **They do different jobs, so use both.**
