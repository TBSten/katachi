Tools similar to katachi include Konsist, ArchUnit, and others.
They are **not necessarily exclusive with katachi**.

## Comparison table

<div class="comparison-table">

| Tool | What it looks at | How it runs | Use with katachi |
|---|---|---|---|
| **katachi** | **Whether a file may exist at all, and where it is placed** | Unit test | — |
| [Konsist](https://docs.konsist.lemonappdev.com/) | The contents of classes, functions, and properties, within a scope | Unit test | ⭐️ Integrated / recommended |
| [detekt](https://detekt.dev/) | Static analysis of the source. Code smells and your own rules | Gradle task / CLI | 🆗 Works |
| [ArchUnit](https://www.archunit.org/) | Dependencies between classes and layers. JVM class information | Unit test | 🆗 Works |
| [ProjectGuard](https://github.com/rubensousa/ProjectGuard) | Dependency declarations between modules. The build graph | Gradle plugin | 🆗 Works |
| [Konture](https://github.com/baole/konture) | Module dependencies, package encapsulation, class characteristics | Unit test | 🆗 Integrated (`katachi-konture`) |

</div>

katachi is the only one that asks whether a file may exist.
The other five all check the contents of, or the relationships between, **things that already exist**.

That is why they do not overlap. What does overlap is **the other tools with each other**:
Konsist, ArchUnit, and Konture cover similar ground, and there is little point in adopting all three.

## katachi and Konsist

Konsist narrows its target with `Konsist.scopeFromProject()` and checks the classes and functions
inside that range. Anything outside the narrowed range is never checked (see the [FAQ](/katachi/get-started/faq/) for details).

katachi is the reverse: it scans the whole project and matches it against the declaration.
**Responsibility splits between "placement" and "contents"**, so either one alone leaves something unchecked.

katachi bridges the two through an optional module called `katachi-konsist`.
Write `ktFileContent { }` inside a role and call `assert(FileConstraintCheck())` in the test, and **placement violations and content violations land in a single report.**

```kt title="ProjectArchitecture.kt"
"UseCase".role {
  // where it may be placed — katachi's job
  layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
  }

  // what its contents should look like — katachi-konsist's job
  ktFileContent {
    `package`("**")
    `import`("**")

    required(`class`, fileName) {
      required(suspend.optional(), operator, `fun`, "invoke")(anyArgs()) // exactly one invoke function
      allow(private, anythingElse)
    }
  }
}
```

### Write the properties of a Role with ktFileContent

You can write the nature of a role as an allow list of the declarations its files may hold. A declaration not on the allow list is a violation.

<details>
<summary>A `UseCase` has exactly one `invoke` function</summary>

```kt nocollapse
"UseCase".role {
  layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
  }

  ktFileContent {
    `package`("com.example.useCase")
    `import`("**")

    required(`class`, fileName) {
      required(suspend.optional(), operator, `fun`, "invoke")(anyArgs())
      allow(private, anythingElse) // a public function other than invoke is a violation
    }
  }
}
```

</details>

<details>
<summary>A `Repository` is declared as an interface</summary>

This is useful in a layer built around swappable implementations.

```kt nocollapse
"Repository".role {
  layout {
    "src/main/kotlin/com/example/repository" / "*Repository".ktFile()
  }

  ktFileContent {
    `package`("com.example.repository")
    `import`("**")

    required(`interface`, fileName) { // declaring it as a class is a violation
      allow(suspend.optional(), `fun`, "*")
    }
  }
}
```

</details>

<details>
<summary>A role's files are visible from the outside</summary>

```kt nocollapse
"UseCase".role {
  layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
  }

  ktFileContent {
    `package`("com.example.useCase")
    `import`("**")

    required(public, `class`, fileName) { // adding internal or private is a violation
      allow(anythingElse)
    }
  }
}
```

</details>

<details>
<summary>A `ViewModel` does not reference Android view types</summary>

This stops layer leaks from the contents side. Only the `import` lines you write are allowed, so as long as `android.view` is not among them, importing it is a violation.

```kt nocollapse
"ViewModel".role {
  layout {
    "src/main/kotlin/com/example/viewModel" / "*ViewModel".ktFile()
  }

  ktFileContent {
    `package`("com.example.viewModel")

    `import`("kotlin.**")
    `import`("kotlinx.coroutines.**")
    `import`("androidx.lifecycle.**")
    `import`("com.example.**")

    required(`class`, fileName) {
      allow(anythingElse)
    }
  }
}
```

</details>

<details>
<summary>Classes in the `data` layer carry a particular annotation</summary>

This keeps serializable types from being missed.

```kt nocollapse
"Dto".role {
  layout {
    "src/main/kotlin/com/example/data" / "*Dto".ktFile()
  }

  ktFileContent {
    `package`("com.example.data")
    `import`("kotlinx.serialization.**")

    allow(annotated("Serializable"), data, `class`, "*") { // a class without @Serializable is a violation
      allow(`val`, "*")
    }
  }
}
```

</details>

## katachi and detekt

detekt statically analyses Kotlin source and points out code smells and style deviations.
Write your own rules and it can check project-specific conventions too.

Its unit of attention is the contents of a file, so it does not clash with katachi.
katachi decides "this file may live here"; detekt looks at "how the contents are written".

katachi has no detekt integration, but the division of roles works fine as it is.

### Decide when to use detekt and when to use `ktFileContent { }`

Sometimes it is unclear whether something belongs in detekt or in `ktFileContent { }`. Two rules of thumb:

- **If you want one report, use `ktFileContent { }`.**
  Checked with `assert(FileConstraintCheck())`, it comes out alongside the placement violations, so a single test run gives you everything you need to fix
- **If you want to apply rules uniformly across the project, use detekt.**
  Conventions that are not tied to a role (function length, complexity, general naming rules) lose
  their meaning when written inside a role

What detekt is good at:

- Function length, nesting depth, cyclomatic complexity
- Leftover `println` and `TODO()`
- Banning specific APIs (project-wide ones)
