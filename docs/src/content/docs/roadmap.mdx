## Overview

| Version | Theme | Definition of done |
|---|---|---|
| **v0.1** | DSL + checks + `konsist { }` | Can express a large project, and checks pass |
| **v0.2** | Gradle plugin + documentation generation + templates + baseline | `./gradlew katachiDocs` produces documentation. With existing violations set aside in a baseline, only new violations fail the test |
| **v0.3 and beyond** | `declarations { }` / report output / vocabulary-size measurement | Can be adopted in an **existing project**. Most of the `konsist { }` written in v0.1 can be replaced with `declarations { }` |

## v0.2 — Gradle plugin, documentation generation and templates

This is the stage where katachi's selling points all come together, and it is **currently being implemented.** The Gradle plugin scaffolding, the mechanism that runs work on top of it (processors), **documentation generation**, code generation from templates and baseline (experimental) are in place. **`dependsOnlyOn` and limiting a directory's `konsist { }` to direct children are still ahead of us.**

```shell
./gradlew katachiDocs
```

Applying the plugin lets you generate Markdown along two axes **from the same definition as the tests.**

- **Role reference** — what this role is, and where it goes
- **Directory structure** — what can go in this directory

Since both are derived from the same model, **they can never contradict each other.** Broken links in the generated output are checked mechanically afterwards, too.

The shape of the output is described in [Document generation](/katachi/guides/document-generation/), and the mechanism that runs it in [ArchitectureProcessor and customizing it](/katachi/guides/processor/). Documentation generation is just one processor; a processor you write yourself is invoked through the same task.

### Also landing in v0.2

| Feature | What it enables |
|---|---|
| [`template { }`](/katachi/guides/generate-code-from-template/) | Generates a file that conforms to a role from a template. Arguments can be typed (`stringParameter()` / `booleanParameter()` / `intParameter()` / `enumParameter()`). `katachiTemplates` shows the list of templates and their details |
| [**baseline**](/katachi/guides/baseline/) (experimental) | Records existing violations in a ledger file and fails only on **newly added** ones. Write `architecture { baseline = baselineFile() }` (this needs `@OptIn(ExperimentalKatachiApi::class)`) and declare the ledger file itself in `layout { }` too. Record with `-Dkatachi.baseline.update=true`, and drop what you fixed from the ledger with `-Dkatachi.baseline.prune=true` |
| [`gradle()`](/katachi/recipes/gradle/) | Declares, in one line, the Gradle files every project has: the wrapper, settings, build scripts, `gradle.properties` and the version catalog |
| IDE plugin (**unpublished**) | Pick a template from a tool window in IntelliJ IDEA / Android Studio, fill in its arguments and generate the code. It is developed separately from katachi's own versions and has not been published yet |
| `dependsOnlyOn` (**not available yet**) | Writes what may be depended on as an **allow list**. A deny-list approach lets omissions slip through |
| Limiting a directory's `konsist { }` to direct children (**not available yet**) | Applies it only to the files directly in that directory, not the whole subtree |

## v0.3 and beyond — Adoption in existing projects and `declarations { }`

Making katachi easier to adopt in existing projects is the theme of v0.3 and beyond. Only baseline, which sets the current violations aside, has already landed in v0.2 as an experimental feature.

| Feature | What it enables |
|---|---|
| **Report output** | Outputs JSON / SARIF, surfaced as annotations on GitHub PRs |
| **`pairedWith`** | Checks coverage, such as "every `Screen` has a corresponding `Preview`" |
| **Vocabulary-size measurement** | Reports the number of roles and the file count per role as numbers |
| **Module resolution based on Gradle's model** | Follows modules whose `projectDir` was changed, and where source sets actually are |

The specification for this stage is largely undecided. Even the version numbering is grouped together as "v0.3 and beyond" for now.

### `declarations { }` — a promotion out of `konsist { }`

v0.1's `konsist { }` is, frankly, **an escape hatch.** Something almost every role wants to say — like "only a `*UseCase` interface and a `Default*UseCase` class go here" — ends up being spelled out as a Konsist expression every time.

```kt
"only the interface and its Default implementation".konsist {
    files.must { file ->
        val decls = file.declarations(includeNested = false, includeLocal = false)
        decls.size == 2 &&
            decls.any { it is KoInterfaceDeclaration && it.name.endsWith("UseCase") } &&
            decls.any { it is KoClassDeclaration && it.name.startsWith("Default") }
    }
}
```

The aim is for the same rule to read like this.

```kt
"UseCase" {
    declarations {
        `interface`("*UseCase")
        `class`("Default*UseCase")
    }
}
```

Top-level declarations that aren't enumerated may not appear — a second class, a top-level extension function, a stray `typealias` — because the block is the allow list for contents, in the same way `layout { }` is the allow list for placement.

And the violation can say more than "a constraint failed", because katachi knows what was expected:

```
[UnsatisfiedFileConstraint] core/domain/.../GetUserUseCase.kt
  The top-level declarations do not match what role UseCase allows.
  Expected: interface *UseCase, class Default*UseCase
  Actual:   interface GetUserUseCase, class GetUserUseCaseImpl, object Factory
  How to fix:
    - Rename GetUserUseCaseImpl to DefaultGetUserUseCase
    - Delete object Factory, or move it to another file
```

**The shape above is a sketch, not a commitment.** What to promote will be decided **after looking at the `konsist { }` that has accumulated** from using v0.1 on real projects. It was moved here from v0.2 to leave time to gather that material.
