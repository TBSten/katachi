A Role is the unit that declares the kinds of files that may appear in your project. This page explains how to write a Role's description, placement, and constraints, how to bring Roles together in groups, and how to split the definition when it grows large.

## Declaring a Role

An app that follows an architecture definition has files with specific roles (Roles).
For example `UseCase`, `Repository`, `Controller`, or `ViewModel`.

You define what Roles exist inside `architecture { }`.

```kt
architecture {
  // Define a Role called UseCase
  "UseCase".role {
    // Write the description, placement, and constraints inside here
  }
}
```

A Role is declared with `"Name".role { }`. This matches the shape of `"name".group { }` and sets it apart from a directory declaration such as `"src" { }`, which you write inside `layout { }`.

Because Role names are used for things like documentation generation, they must be ASCII only (starting with a letter, followed by letters, digits, `_`, or `-`).

You write a Role's description, placement, and constraints inside that Role's block.

| What you write | Description | Documentation |
|---|---|---|
| `title`, `summary`, `description`, etc. | The description of the Role. Used when generating documentation | "Writing a description" on this page |
| `layout { }` | Defines where the files for that Role may be placed | [Layout definitions](/katachi/guides/layout/) |
| `ktFileContent { }` | Defines, as an allow list, the package, imports, and declarations that may be placed in that Role's files | "Constraining the contents" on this page |
| `.template { }` | Attached to a file declared in `layout { }`, it defines the template used when that file is newly created | [Generate code from a template](/katachi/guides/generate-code-from-template/) |

Next is an example that puts title / summary / layout / ktFileContent together in one place.

```kt nocollapse
architecture {
  "UseCase".role {
    title = "Use case"
    summary = "A single app-specific behavior that occurs on each screen"

    example("GetUserUseCase", "Fetch the user")

    // Where it may be placed
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    // What its contents should look like
    ktFileContent {
      `package`("com.example.useCase")
      `import`("com.example.repository.**")

      required(`class`, fileName) {
        required(suspend.optional(), operator, `fun`, "invoke")
        allow(private, anythingElse)
      }
    }
  }
}
```

Let's look at each of these in a bit more detail.

### Writing a description

At minimum, all you need is `summary`. It is the text shown in the Role table when documentation is generated.

```kt
"UseCase".role {
  summary = "A single app-specific behavior that occurs on each screen"
}
```

`description` can hold a longer explanation, and `example()` a representative example. Calls to `example()` are kept in the order you call them.

```kt
"UseCase".role {
  title = "Use case"
  summary = "A single app-specific behavior that occurs on each screen"
  description = """
    Call only UseCase from the UI; never touch Repository directly.

    ### Things not to do
    - Depend on Android types
  """.trimIndent()

  example("GetUserUseCase", "Fetch the user")
  example("UpdateUserUseCase", "Update the user")
}
```

### Declaring where files go

This is the case where a Role has just one place to live.

```kt
"UseCase".role {
  layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
  }
}
```

You can write multiple `layout { }` blocks. This declares that the same kind of file is allowed to appear in more than one place. Files of different kinds go in separate Roles.

```kt
"UseCase".role {
  // In the feature-home module
  layout {
    "feature-home/src/main/kotlin/useCase" / "*UseCase".ktFile()
  }

  // And in the feature-settings module
  layout {
    "feature-settings/src/main/kotlin/useCase" / "*UseCase".ktFile()
  }
}
```

### Checking a placement violation

Placing a file anywhere you haven't declared is a violation.

```text
src/main/kotlin/com/example/GetUserUseCase.kt   ← placed outside useCase/
```

When you run the test, katachi reports the nearby valid location and how to fix it together in a single block.

```text nocollapse
Katachi check failed: 1 violation (Unexpected: 1)

[UnexpectedFile] file:///path/to/project/src/main/kotlin/com/example/GetUserUseCase.kt
  No role is defined for this file.

  Nearby locations:
    UseCase file:///path/to/project/src/main/kotlin/com/example/useCase/ (*UseCase.kt)

  How to fix:
    - Move it to one of the locations above, with a name matching the pattern in parentheses
    - Delete it if it is not needed
    - Add a new role for it:
        "GetUserUseCase".role {
          summary = "TODO"
          layout {
            "src/main/kotlin/com/example" / "GetUserUseCase".ktFile()
          }
        }
```

### Constraining the contents

Constraints on a file's contents are written with `ktFileContent { }`. You list, one line at a time as an allow list, the package, imports, and declarations that may be placed in the file.

```kt nocollapse
"UseCase".role {
  layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
  }

  ktFileContent {
    `package`("com.example.useCase")
    `import`("com.example.repository.**")

    // Place a class named after the file. The only function it may make public is invoke
    required(`class`, fileName) {
      required(suspend.optional(), operator, `fun`, "invoke")
      allow(private, anythingElse) // the Repository it receives in its constructor, etc.
    }
  }
}
```

A constraint applies to the files that matched the Role's `layout { }`. You cannot write a constraint on a Role that has no `layout { }`. A Role can hold only one `ktFileContent { }`.

Because it is an allow list, you don't need to write what you want to forbid one by one. A declaration that matches no line is a violation. A declaration that carries a modifier the line doesn't write (such as `internal`) is a violation too.

```kt nocollapse
"RepositoryInterface".role {
  layout {
    "src/main/kotlin/com/example/repository" / "*Repository".ktFile()
  }

  ktFileContent {
    `package`("com.example.repository")

    // Place a public interface. If you add internal, it doesn't match this line and is a violation
    required(public, `interface`, fileName) {
      allow(suspend.optional(), `fun`, "*")
    }

    // No class line is written, so placing an Impl in the same file is a violation
  }
}
```

How to write `ktFileContent { }` is explained in detail in [Define an allow list of the declarations a file may contain](/katachi/guides/kt-file-content/).

### Checking a constraint violation

A declaration that matches no line of the allow list is a violation.

```kt title="src/main/kotlin/com/example/useCase/GetUserUseCase.kt" {8}
package com.example.useCase

import com.example.repository.UserRepository

// Besides invoke, it has a public function
class GetUserUseCase(private val repository: UserRepository) {
  suspend operator fun invoke(id: String) = repository.find(id)
  fun clearCache() = repository.clear()
}
```

`ktFileContent { }` lives in the separate `katachi-konsist` module. When the test calls `assert(FileConstraintCheck())` instead of `assert()`, the violation shows up in the same report as placement violations. The report even tells you which file and which line (the example below omits some lines).

```text
[UnsatisfiedFileConstraint] file:///path/to/project/src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "ktFileContent"
  Declaration: GetUserUseCase.clearCache (line 8)
  Not allowed: fun clearCache() in class GetUserUseCase
  Allowed members of class GetUserUseCase:
    suspend.optional() operator fun invoke(...)
    private (anything)
```

### Grouping Roles

You can group Roles together using `"group name".group { ... }`.

```kt {2}
architecture {
  "domain".group {
    "UseCase".role {
      // ...
    }

    "RepositoryInterface".role {
      // ...
    }
  }
}
```

## Designing Roles that are easy to maintain

### A good Role definition needs no changes

<Badge text="Recommended" variant="success" />

If you rewrite `architecture { }` every time you add a feature to the app, the definition tends to become a duplicate of your directory structure, requiring double the work to maintain. Make good use of wildcards like `*` and `**` so that you can add features without changing the definition.

### Put only one kind of file in a Role

<Badge text="Recommended" variant="success" />

Make each Role stand for exactly one kind of file.
For example, a Repository interface and its implementation have similar names but are different kinds of file. If you put both in one Role, its description, constraints, and templates split by "which of the two files this is about".
With one Role per kind, the description and constraints only deal with that kind of file, and the generated documentation gets one page per kind.

<CodeComparison>
    <CodeComparison.Panel label="🆖 Two kinds of file in one Role" labelVariant="danger">

    ```kt {4-5} nocollapse
    "Repository".role {
      summary = "Loads and saves data"
      layout {
        "repository" / "*Repository".ktFile()      // interface
        "repository" / "*RepositoryImpl".ktFile()  // implementation
      }
      ktFileContent {
        // the allowed declarations have to differ between the interface file and the implementation file
      }
    }
    ```

    </CodeComparison.Panel>

    <CodeComparison.Panel label="🆗 One Role per kind" labelVariant="success">

    ```kt {1,12} nocollapse
    "RepositoryInterface".role {
      summary = "The entry point for loading and saving data"
      layout { "repository" / "*Repository".ktFile() }
      ktFileContent {
        // package / import lines omitted
        required(public, `interface`, fileName) {
          allow(suspend.optional(), `fun`, "*")
        }
      }
    }

    "RepositoryImplementation".role {
      summary = "The implementation of RepositoryInterface"
      layout { "repository" / "*RepositoryImpl".ktFile() }
    }
    ```

    </CodeComparison.Panel>
</CodeComparison>

## Splitting Role definitions

The bigger the project, the more the `architecture { }` definition tends to bloat.

Because `architecture { }` is a Kotlin DSL, you can factor it out into extension functions just like ordinary Kotlin code.

Here's the recommended **way to split Role definitions**.

### Splitting the `architecture { }` definition

What tends to bloat is **the detail inside each Role**.
Factor each Role out into its own extension function.

<CodeComparison>
    <CodeComparison.Panel label="Before">

    ```kt title=ProjectArchitecture.kt nocollapse
    architecture {
      "UseCase".role {
        layout { 
          "src/main/kotlin/com/example/project/useCase" / "*UseCase".ktFile()
        }
        ktFileContent {
          `package`("com.example.project.useCase")
          `import`("com.example.project.repository.**")

          required(`class`, fileName) {
            required(suspend.optional(), operator, `fun`, "invoke")
            allow(private, anythingElse)
          }
        }
        // ...
      }

      "RepositoryInterface".role {
        layout { 
          "src/main/kotlin/com/example/project/repository" / "*Repository".ktFile()
        }
        ktFileContent {
          `package`("com.example.project.repository")

          required(public, `interface`, fileName) {
            allow(suspend.optional(), `fun`, "*")
          }
        }
        // ...
      }

      // ...
    }
    ```

    </CodeComparison.Panel>

    <CodeComparison.Panel label="After" labelVariant="success">

    <FileTree>
        - ProjectArchitecture.kt
        - **domain/**
            - UseCaseRole.kt
            - RepositoryInterfaceRole.kt
    </FileTree>

    ```kt title=ProjectArchitecture.kt
    architecture {
      useCase()
      repositoryInterface()

      // ...
    }
    ```

    ```kt title=domain/UseCaseRole.kt
    // hint: DeclarationContainerScope is the receiver of architecture { } and "...".group { }.
    fun DeclarationContainerScope.useCase() = "UseCase".role {
      layout {
        "src/main/kotlin/com/example/project/useCase" / "*UseCase".ktFile()
      }
      ktFileContent {
        `package`("com.example.project.useCase")
        `import`("com.example.project.repository.**")

        required(`class`, fileName) {
          required(suspend.optional(), operator, `fun`, "invoke")
          allow(private, anythingElse)
        }
      }
      // ...
    }
    ```

    ```kt title=domain/RepositoryInterfaceRole.kt
    fun DeclarationContainerScope.repositoryInterface() = "RepositoryInterface".role {
      layout {
        "src/main/kotlin/com/example/project/repository" / "*Repository".ktFile()
      }
      ktFileContent {
        `package`("com.example.project.repository")

        required(public, `interface`, fileName) {
          allow(suspend.optional(), `fun`, "*")
        }
      }
      // ...
    }
    ```

    </CodeComparison.Panel>

</CodeComparison>

<Aside type="caution" title="Writing a placement pattern in KDoc causes a compile error">

If you write a path such as `feature/*` in the KDoc of an extracted function, Kotlin reads `/*` as the start of a nested comment and causes a compile error.

Write the placement explanation in the Role's `description` (a string), or write it as `feature/<name>` in KDoc.

</Aside>

### Splitting the inside of a Role definition

Within a Role definition, `ktFileContent { }` in particular tends to bloat as the imports and declarations it allows grow.

Don't hesitate to factor `ktFileContent { }` out into private extension functions.

<CodeComparison>
    <CodeComparison.Panel label="Before">
      ```kt
      fun DeclarationContainerScope.useCase() = "UseCase".role {
        layout {
          "src/main/kotlin/com/example/project/useCase" / "*UseCase".ktFile()
        }
        ktFileContent {
          `package`("com.example.project.useCase")
          `import`("com.example.project.repository.**")

          required(`class`, fileName) {
            required(suspend.optional(), operator, `fun`, "invoke")
            allow(private, anythingElse)
          }
        }
        // ...
      }
      ```
    </CodeComparison.Panel>

    <CodeComparison.Panel label="After" labelVariant="success">
      ```kt
      fun DeclarationContainerScope.useCase() = "UseCase".role {
        layout {
          "src/main/kotlin/com/example/project/useCase" / "*UseCase".ktFile()
        }

        useCaseFileContent()
        // ...
      }

      private fun RoleScope.useCaseFileContent() =
        ktFileContent {
          `package`("com.example.project.useCase")
          `import`("com.example.project.repository.**")

          required(`class`, fileName) {
            required(suspend.optional(), operator, `fun`, "invoke")
            allow(private, anythingElse)
          }
        }
      ```
    </CodeComparison.Panel>
</CodeComparison>

## Summary

This is a complete example that uses everything covered so far. The Role definition is factored out into extension functions, as described in [Splitting Role definitions](#splitting-role-definitions).

<FileTree>
    - ProjectArchitecture.kt
    - **domain/**
        - UseCaseRole.kt
</FileTree>

```kt title=ProjectArchitecture.kt nocollapse
architecture {
  "domain".group {
    useCase()
  }
}
```

```kt title=domain/UseCaseRole.kt nocollapse
fun DeclarationContainerScope.useCase() = "UseCase".role {
  summary = "A single app-specific behavior that occurs on each screen"

  // However many places it is put in, the description stays in this one place
  layout {
    "core/domain/src/main/kotlin/useCase" / "*UseCase".ktFile()
  }

  useCaseFileContent()
}

private fun RoleScope.useCaseFileContent() =
  ktFileContent {
    `package`("com.example.useCase")
    `import`("com.example.repository.**")

    required(`class`, fileName) {
      required(suspend.optional(), operator, `fun`, "invoke")
      allow(private, anythingElse)
    }
  }
```
