This page introduces katachi's core API.
Once you know these, you should understand the basics of using katachi.

## 1. `architecture { }`

`architecture { }` is the entry point for defining your project's overall architecture.
Inside it, you write the roles of the files that exist in your project.

```kt
architecture {
  "UseCase".role { /* ... */ }
  "RepositoryInterface".role { /* ... */ }
}
// This project has two roles: `UseCase` and `RepositoryInterface`
```

The elements inside an architecture (Role) are covered in more depth in a later section.

## 2. Testing the architecture with `assert()`

`assert()` is the function that tests the architecture defined with `architecture { }`.

```kt {8}
val projectArchitecture = architecture {
  "UseCase".role { /* ... */ }
  "RepositoryInterface".role { /* ... */ }
}

@Test
fun `files are placed according to the architecture`() {
  projectArchitecture.assert()
}
```

If a file doesn't match the definition, the test fails with a report like this (some lines are omitted).

```text
Katachi check failed: 1 violation (Unexpected: 1)

[UnexpectedFile] file:///path/to/project/src/main/kotlin/com/example/GetItemUseCase.kt
  No role is defined for this file.
```

## 3. Declaring a Role with `"Name".role { }`

`"Name".role { }` declares the role that a file appearing in the project plays.

```kt {2,4}
architecture {
  "UseCase".role { /* ... */ }

  "RepositoryInterface".role { /* ... */ }
}
```

Writing `"Name".role { }` inside an `architecture { }` block lets you declare the roles of files that appear in the project.

### Example roles

If you're using a well-known architecture, roles typically look something like this.

| Architecture | Role |
|---|---|
| MVC | `Controller` |
| | `View` |
| | `Model` |
| MVVM | `View` |
| | `ViewModel` |
| Clean architecture | `Service` |
| | `UseCase` |
| | `Entity` |
| | `RepositoryInterface`, `RepositoryImplementation` |

### Deny by default

In katachi, only files with a declared Role are allowed to exist in the project.

In other words, adopting katachi requires you to enumerate the Roles that match your project's conventions.

## 4. Grouping Roles with `"...".group { }`

`"Name".group { }` is a block for grouping Roles together.

For example, in Clean architecture, `UseCase` and `RepositoryInterface` are both **roles in the same domain layer**.

In this case, you can express that hierarchy by wrapping the Roles in `"...".group { }`, as below.

```kt {2}
architecture {
  "Domain".group {
    "UseCase".role { /* ... */ }
    "RepositoryInterface".role { /* ... */ }
  }
}
```

Expressing a group like "the domain layer" in the DSL makes the relationships and hierarchy between roles clear. Grouping Roles at a sensible granularity is important for building an architecture definition that's easy to understand.

### Nested Role groups

`"...".group { }` can be nested.

```kt {3,6}
architecture {
  "Domain".group {
    "UseCase".group {
      "UseCase".role { /* ... */ }
    }
    "Repository".group {
      "RepositoryInterface".role { /* ... */ }
    }
  }
}
```

For grouping Roles, also see [Role definitions in depth](/katachi/guides/role/).

## 5. Defining where files may exist with `layout { }`

Declaring a Role with `"...".role { }` alone doesn't decide where that Role's files may be placed.

`layout { }` is the block that defines where the files for a Role may be placed.

```kt {3-4}
architecture {
  "UseCase".role {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }
  }
}

// A UseCase may be placed at `src/main/kotlin/com/example/useCase/*UseCase.kt`
```

### How it works

Under the Deny by default principle, you can't place a file anywhere that isn't declared in `layout { }`.

Say an AI Agent tries to place a new UseCase file at `src/main/kotlin/com/example/GetItemUseCase.kt`. It should really go inside the useCase package. The moment `assert()` is called, katachi detects that no Role matches this path, and the test fails.

<FileTree>
- src/main/kotlin/com/example/
  - **GetItemUseCase.kt** ❌ a place not declared in `layout { }`
  - useCase/
    - GetUserUseCase.kt ⭐️ where the declaration puts it
</FileTree>

## 6. Defining the declarations a file may contain with `ktFileContent { }`

`ktFileContent { }` is the block that defines, as an allow list, the package, imports, and declarations that may be placed in a Role's files.

```kt {7-12} nocollapse
architecture {
  "UseCase".role {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    ktFileContent {
      `package`("com.example.useCase")
      required(`class`, fileName) {
        allow(anythingElse)          // the class may have any members
      }
    }
  }
}

// GetUserUseCase.kt may contain only the package com.example.useCase declaration and class GetUserUseCase
```

Declarations placed in `GetUserUseCase.kt` are either allowed or a violation, like this.

```kt title="GetUserUseCase.kt"
package com.example.useCase

class GetUserUseCase { /* ... */ }   // not a violation: matches the required line
fun helper() {}                      // violation: no line matches
```

The declaration that is a violation is reported like this (some lines are omitted).

```text
[UnsatisfiedFileConstraint] file:///path/to/project/src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "ktFileContent"
  Declaration: helper (line 4)
  Not allowed: fun helper()
```

The lines you write become the allow list, and nothing may be placed for a kind you wrote no line for (deny by default). The `ktFileContent { }` example has no import line, so the file may not have a single import.

`ktFileContent { }` lives in the separate `katachi-konsist` module. To check it, call `assert(FileConstraintCheck())` instead of `assert()` in the test. With `assert()` alone it is not checked, and the test fails with `[UncheckedFileConstraint]`.

### `ktFileContent { }` details

For `ktFileContent { }`, also see [Define an allow list of the declarations a file may contain](/katachi/guides/kt-file-content/).

## Summary

| API | What it does |
|---|---|
| `architecture { }` | The entry point that defines the architecture of the whole project. |
| `assert()` | Checks that files are placed as defined. It is the one line you call from a test, and nothing happens without it. |
| `"Name".role { }` | Declares the role (Role) that a file appearing in the project plays. |
| `"Name".group { }` | Brings Roles together to build a hierarchy. Using it is optional. |
| `layout { }` | Defines where the files for that Role may be placed. |
| `ktFileContent { }` | Defines, as an allow list, the package, imports, and declarations that may be placed in that Role's files. |
