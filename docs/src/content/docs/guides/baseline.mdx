{/*
  The purpose of this page: to gain a deep, comprehensive understanding of the baseline feature, which is useful when introducing katachi into an existing project.
*/}

Adding katachi to an existing project means that on the first run, **every undeclared file comes out as a violation.** The basic approach is to work through the reported paths one by one — adding them to the definition, moving them, or deleting them — but when there are a lot of them, you can't clear them all right away.

baseline is a feature that temporarily suppresses existing violations, so that only new violations fail the test.

## Setting it up

### 1. Write `baseline = baselineFile()` in the definition

```kt title="ProjectArchitecture.kt (excerpt)" {1,5}
@OptIn(ExperimentalKatachiApi::class)
val projectArchitecture: Architecture = architecture {
    // ...
    baseline = baselineFile()

    // ...
}
```

By default, setting baseline generates `katachi-baseline.json` at the project root, and the contents of baseline are written into this file.

To change the location, set it like `baselineFile("config/katachi-baseline.json")`.

### 2. Declare the baseline file itself with `layout { }`

The baseline file is also one of the project's files, so unless it's declared as a role, `projectArchitecture.assert()` will error out.

Following convention, prepare a role named `"BaselineFile"` and add it to your architecture definition.

```kt
val projectArchitecture = architecture {
    // ...
    "Tool".group {
      "Katachi".group {
        baselineFile()
      }
    }

    // ...
}

fun DeclarationContainerScope.baselineFile() = "BaselineFile" {
    title = "katachi Baseline file"
    summary = "A file for temporarily suppressing existing violations"
    description = "See: https://tbsten.github.io/katachi/guides/baseline/"
    layout {
        "katachi-baseline.json".file()
    }
}
```

### 3. Create the baseline file

Running the architecture test with `-Dkatachi.baseline.update=true` makes all violations pass instead of erroring, and writes them into the baseline file.

```shell
./gradlew :architecture-test:test -Dkatachi.baseline.update=true
```

How many were recorded is reported in the following line. This line goes to the test's standard error output, so with Gradle's default settings it doesn't show up in the console.

```
Katachi baseline file:///path/to/project/katachi-baseline.json: 2 violations recorded in 2 entries (+2, -0).
```

It's recommended to commit the created/updated file.

## Summary

- baseline is a feature that records existing violations in the baseline file and temporarily suppresses them, so that only **newly added violations** fail the test.
- To use it, write `baseline = baselineFile()` in the definition, and declare the baseline file itself as a role in `layout { }`.
- The baseline file is created and updated by running the architecture test with `-Dkatachi.baseline.update=true`. Commit the resulting file.
