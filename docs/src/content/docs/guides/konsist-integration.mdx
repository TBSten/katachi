What katachi's core API can validate is directory structure and file location. The declarations a file may contain can be defined with [`ktFileContent { }`](/katachi/guides/kt-file-content/).
For rules that `ktFileContent { }` cannot express, you can write them with the Konsist API by using `"...".konsist { }`.

## Installation

`"...".konsist { }` lives in `me.tbsten.katachi:katachi-konsist`, the same separate artifact as `ktFileContent { }`.
For how to add the dependency and call `assert(FileConstraintCheck())` in your tests, see [Define an allow list of the declarations a file may contain](/katachi/guides/kt-file-content/#installation).

## Basic usage

Inside a Role, you define what declarations that Role's files should have.

```kt {7-8}
architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    "has exactly one invoke function".konsist {
        classes().must { it.functions().map { f -> f.name } == listOf("invoke") }
    }
  }
}
```

A constraint applies to the files that matched the Role's `layout { }`. A Role with no `layout { }` can't have constraints.

## Example error

When a constraint violation is detected, the error message looks like this.

```text
Katachi check failed: 1 violation (FileConstraint: 1)

[UnsatisfiedFileConstraint] file:///path/to/project/src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "has exactly one invoke function"
  Declaration: GetUserUseCase (line 3)
  Declared at: ProjectArchitecture.kt:12
```

**The name you gave the constraint appears exactly as written.** When there are multiple constraints, this single line tells you which one failed, so write the name in the form of what must be satisfied.

## Attach a reason and how to fix

`must` / `mustNot` / `mustBeEmpty` accept the reason the rule exists and how to fix a violation. The first argument is the reason, and the second is the list of fixes.

```kt {9-10}
architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    "has exactly one invoke function".konsist {
        classes().must(
            "A UseCase represents exactly one behavior",
            listOf("Move functions other than invoke into a separate UseCase"),
        ) { it.functions().map { f -> f.name } == listOf("invoke") }
    }
  }
}
```

A violation shows the reason on the `Reason:` line, and the fixes under `How to fix:`.

```text
[UnsatisfiedFileConstraint] file:///path/to/project/src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "has exactly one invoke function"
  Declaration: GetUserUseCase (line 3)
  Reason: A UseCase represents exactly one behavior
  Declared at: ProjectArchitecture.kt:12

  How to fix:
    - Move functions other than invoke into a separate UseCase
```

The fixes can be omitted. If you omit them, the `How to fix:` section does not appear.

## Konsist API

Inside a `"...".konsist { }` block, you can use the regular Konsist API.

<LinkCard
  title="Konsist documentation"
  href="https://docs.konsist.lemonappdev.com/"
/>

katachi adds three things — `must`, `mustNot`, and `mustBeEmpty` — and turns Konsist's assertions such as `assertTrue` into compile errors so they cannot be used. Everything up to narrowing down the target uses Konsist's syntax as-is.

## Summary

- `layout { }` handles **where files may be placed**, `ktFileContent { }` handles **the shape of the declarations a file contains**, and `konsist { }` handles **all other rules**.
- `katachi-konsist` is an **optional module**. It requires adding the dependency and setting up `assert(FileConstraintCheck())`.
- **The constraint name appears directly in the violation report.** Write the name in the form of what must be satisfied. You can also attach the reason and how to fix a violation, in the form `must("reason", listOf("how to fix")) { }`.
- Konsist's `assertTrue` family **can't be used** inside `konsist { }` (it causes a compile error). Write `must` / `mustNot` / `mustBeEmpty` instead.
