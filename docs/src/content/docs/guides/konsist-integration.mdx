While katachi's core API focuses on validating directory structure and file location, `"...".konsist { }` lets you use the Konsist API to **validate the declarations inside a file**.

## Installation

`"...".konsist { }` lives in a separate, optional module, so you need to install it separately.
Add the following to `build.gradle.kts`.

<table>
  <tr>
    <td>Version</td>
    <td>Same as the core `katachi` module. The two artifacts are always published with the same version</td>
  </tr>
  <tr>
    <td>Bundled Konsist</td>
    <td>0.17.3</td>
  </tr>
</table>

<Aside type="note">
  Published on Maven Central as `me.tbsten.katachi:katachi-konsist`. See the [roadmap](/katachi/roadmap/) for what each version covers.
</Aside>

```kts title="build.gradle.kts" {2}
dependencies {
    testImplementation("me.tbsten.katachi:katachi-konsist:<version>")
}
```

Next, pass `FileConstraintCheck()` to `projectArchitecture.assert()` to run the Konsist checks.

```kt del={4} ins={1,5}
@OptIn(ExperimentalKatachiApi::class)
@Test
fun `files are placed according to the architecture`() {
  projectArchitecture.assert()
  projectArchitecture.assert(FileConstraintCheck())
}
```

`FileConstraintCheck` is an experimental API, so it needs `@OptIn(ExperimentalKatachiApi::class)`.
If you call `assert()` alone without passing `FileConstraintCheck()`, the constraints are not evaluated and the test fails with an `[UncheckedFileConstraint]` violation.

## Basic usage

Inside a Role, you define what declarations that Role's files should have.

```kt
architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    "has exactly one invoke function".konsist {
        classes().must { it.functions().map { f -> f.name } == listOf("invoke") }
    }
  }
}
```

A constraint applies to the files that matched the Role's `layout { }`. Writing a constraint on a Role with no `layout { }` throws `KatachiFileConstraintWithoutLayoutException` as soon as the definition is evaluated.

<Aside type="caution">
  Writing `assertTrue { }` inside `konsist { }` **causes a compile error** (it is blocked with an ERROR-level `@Deprecated`). Konsist's `assertTrue` throws on the spot at the first declaration it rejects, so katachi cannot learn which declarations were rejected and cannot collect every violation in a single run.
  Use must / mustNot / mustBeEmpty instead.
</Aside>

## Constraining one directory

`konsist { }` can also be written in a directory block inside `layout { }`. It then covers **the files declared below that block (its whole subtree)**.

When **a parent and its child need different rules** — `util/` may use only the Kotlin standard library while `util/ksp/` may also use the KSP API — add `directOnly = true`. The constraint then covers **only the files declared directly in that block**, and does not reach its child directories.

```kt {4}
"Util" {
  layout {
    "src/main/kotlin/com/example/util" {
      "does not use the KSP API".konsist(directOnly = true) {
        files.must { file -> file.imports.none { it.name.startsWith("com.google.devtools.ksp") } }
      }
      "*".ktFile()           // covered
      "ksp" { "*".ktFile() } // not covered
    }
  }
}
```

- "Directly" is decided by the shape of the declaration. A file declared a level down with `/`, such as `"ksp" / "*".ktFile()`, is not covered, and neither is one containing `**`, such as `"**/*.md".file()`. The block's own `anyFile()` is covered.
- The unnamed `konsist(directOnly = true) { }` and the experimental `fileConstraint(name, directOnly = true) { }` work the same way.
- Without it, the whole subtree is covered, as before.

<Aside type="caution" title="Where directOnly cannot be written">
  - **Directly on a Role, directly under `layout { }`, or inside `":".module { }`.** There is no directory there to be "directly" in, so it throws `KatachiFileConstraintDirectOnlyWithoutDirectoryException`.
  - **In a block that declares no file directly.** It throws `KatachiFileConstraintDirectOnlyCoversNothingException`, so that a constraint that checks nothing cannot pass. The `build.gradle.kts` that `.module { }` adds on its own does not count.
</Aside>

## Example error

When a constraint violation is detected, the error message looks like this.

```text
Katachi check failed: 1 violation (FileConstraint: 1)

[UnsatisfiedFileConstraint] file:///path/to/project/src/main/kotlin/com/example/useCase/GetUserUseCase.kt
  Role: UseCase / FileConstraint: "has exactly one invoke function"
  Declaration: GetUserUseCase (line 3)
  Declared at: ProjectArchitecture.kt:12
```

**The name you gave the constraint appears exactly as written.** When there are multiple constraints, this single line tells you which one failed, so write the name in the form of what must be satisfied.

## Konsist API

Inside a `"...".konsist { }` block, you can use the regular Konsist API.

<LinkCard
  title="Konsist documentation"
  href="https://docs.konsist.lemonappdev.com/"
/>

katachi adds three things — `must`, `mustNot`, and `mustBeEmpty` — and blocks Konsist's assertions such as `assertTrue` with compile errors. Everything up to narrowing down the target uses Konsist's syntax as-is.

<Aside type="caution" title="What this block cannot do">
  - **`.kts` files are never covered.** Konsist only reads `.kt` files. Rules about `build.gradle.kts` and the like cannot be written with `konsist { }`. Write them with `fileConstraint(name) { subject -> ... }` (an experimental API), which reads the file contents itself.
  - **Do not rely on `projectPath` / `moduleName`.** They are relative to the root Konsist guessed, not to the project katachi walked.
</Aside>

## Summary

- `layout { }` handles **where files may be placed**, and `konsist { }` handles **what their contents should look like**.
- A `konsist { }` written in a directory block covers its whole subtree. Add `directOnly = true` to cover only the files directly in it.
- `katachi-konsist` is an **optional module**. It requires adding the dependency and setting up `assert(FileConstraintCheck())`.
- **The constraint name appears directly in the violation report.** Write the name in the form of what must be satisfied.
- The `assertTrue` family **causes a compile error**. It throws an exception on the spot, which doesn't fit the design that collects every violation in a single run.
