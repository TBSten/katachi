While katachi's core API focuses on validating directory structure and file location, `"...".konture { }` lets you use [Konture](https://baole.github.io/konture/) rules to **validate the declarations inside a file**.

You write it in the same place and the same shape as [`konsist { }`](/katachi/guides/konsist-integration/). The difference is that the body is written in Konture's `that()` / `should()` style.

## Installation

`"...".konture { }` lives in a separate artifact, `me.tbsten.katachi:katachi-konture`, so add it to the dependencies in `build.gradle.kts`. You do not need Konture's Gradle plugin.

```kts title="build.gradle.kts" {2}
dependencies {
    testImplementation("me.tbsten.katachi:katachi-konture:<version>")
}
```

**Do not put it in the same test module as `katachi-konsist`.** If you put both on the same test classpath, one of the checks always fails. The reason is described under "What you can't do" below.

A module that uses `katachi-konture` needs Kotlin 2.3 or later.

Next, pass `FileConstraintCheck()` to `projectArchitecture.assert()` to run the Konture checks.

```kt del={3} ins={4}
@Test
fun `files are placed according to the architecture`() {
  projectArchitecture.assert()
  projectArchitecture.assert(FileConstraintCheck())
}
```

## Basic usage

Inside a Role, you define what declarations that Role's files should have.

```kt {3-5}
architecture {
  "ViewModel".role {
    "Does not depend on Compose".konture {
      classes { should() notDependOnPackages "androidx.compose.." }
    }

    layout {
      "feature" / "*" / "commonMain".sourceSet / kotlin / "com/example/kmp/feature" / "*" /
        "*ViewModel".ktFile()
    }
  }
}
```

A constraint applies to the files that matched the Role's `layout { }`. A Role with no `layout { }` can't have constraints.

Inside `konture { }` you can write four blocks: `files { }`, `classes { }`, `functions { }`, and `properties { }`. What goes inside each is Konture's rules as-is. To narrow down the target, write `that()` first.

```kt {3-4}
"Does not depend on Compose".konture {
  classes {
    that() nameEndsWith "ViewModel"
    should() notDependOnPackages "androidx.compose.."
  }
}
```

Even if the result of narrowing down with `that()` is zero items, it is not a violation. "A file that should exist is missing" is detected by `layout { }`. The test fails if one `konture { }` has none of `classes { }` and the others, or if a rule does not end with `should()`.

## Example error

When a constraint violation is detected, the error message looks like this.

```text
Katachi check failed: 1 violation (FileConstraint: 1)

[UnsatisfiedFileConstraint] file:///path/to/project/feature/home/src/commonMain/kotlin/com/example/kmp/feature/home/HomeViewModel.kt
  Role: ViewModel / FileConstraint: "Does not depend on Compose"
  Declaration: HomeViewModel (line 12)
  Declared at: ProjectArchitecture.kt:12
```

**The name you gave the constraint appears exactly as written.** When there are multiple constraints, this single line tells you which one failed, so write the name in the form of what must be satisfied.

Konture's own message (in English) is not shown. The location of the violation is given by `Declaration` and the line number.

## What you can't do

katachi handles where files are placed, and Konture handles what is inside them. Konture also has module graph validation, but you can't use it in `konture { }`.

- **You can't write module graph rules (`modules { }` / `slices { }` / `layeredArchitecture` / `assertNoCycles`).** `konture { }` only sees the files that `layout { }` matched, and dependencies between Gradle modules are outside katachi's scope. To validate the module graph, put Konture, including its Gradle plugin, in a separate test module and use it directly.
- **You can't use the filters and rules that name a module (`inModule` / `notInModule` / `resideInModule` and so on).** The graph `konture { }` builds has a single module, `:`, so in `that()` they select zero items and no violation appears, and in `should()` they reject everything. Say where a file lives with `layout { }`, and which package it is in with `inPackage`.
- **You can't put it in the same test module as `konsist { }`.** Konsist and Konture each use a different version of the Kotlin compiler (`kotlin-compiler-embeddable`), and putting both on the same test classpath stops one of them from working. `ktFileContent { }` also runs on Konsist, so it can't be put in the same test module as `konture { }` either. If you split them into separate test modules, you can use both.
- **Konture's own entry points (`architecture { }` / `Konture.files()` / `rule { }` / `architectureRules { }` and so on) are compile errors inside `konture { }`.** Write the rules inside `files { }`, `classes { }` and so on.
- **Konture's own settings such as `Konture.reset()` and `Konture.failOnSeverity` can be written inside `konture { }`, but they have no effect on evaluation.** For example, writing `Konture.failOnSeverity = ERROR` does not turn a violation into an exception.
- **Inside `satisfy { }`, return `true` / `false` instead of asserting.** If an assertion fails, evaluation stops at the first declaration that does not satisfy it, and the constraint is reported as one that could not be evaluated.
- **Konture's baseline, HTML / JSON reports, and `severity` are not used.** All violations go into katachi's report, and tolerating existing violations is the job of [katachi's baseline](/katachi/guides/baseline/). However, if the JVM is started with a `konture.*` system property such as `-Dkonture.baseline.generate=true`, Konture itself may write out its baseline or reports. katachi's report does not change.
- **Inheritance chains and type resolution work only within the files the constraint covers.** `areAssignableTo` / `beAssignableTo` cannot follow inheritance through a class the constraint does not cover, so what they can decide is narrower than when you use Konture directly. In a file with two or more wildcard imports, the short name of a class that is not covered cannot be resolved either. Cover the whole hierarchy, or write the type's fully qualified name.
- **Rules about the side being referenced from outside (such as `onlyBeAccessedByAnyPackage`) only look inside the files the constraint covers.** References from files it does not cover are not counted. Rules about the depending side (such as `notDependOnPackages`) can also see dependencies on packages it does not cover.
- **`.kts` files are not targets.** If every file covered is a `.kts`, the test fails.

`@Suppress("konture:classes.rule")` written in the source, and Konture's `suppress { }`, also work inside `konture { }`.

## Konture API

Inside `files { }` and the other blocks of a `"...".konture { }` block, you can use the regular Konture API.

katachi adds only the four entry points `files { }` / `classes { }` / `functions { }` / `properties { }`, and the narrowing down and the rules use Konture's as-is. The entry points you can't use and the settings that have no effect are described under "What you can't do".

## Summary

- `layout { }` handles **where files may be placed**, and `konture { }` handles **what their contents should look like**.
- `katachi-konture` is an **optional module**. It requires adding the dependency and setting up `assert(FileConstraintCheck())`. You do not need Konture's Gradle plugin.
- **The constraint name appears directly in the violation report.** Write the name in the form of what must be satisfied.
- `konsist { }` and `konture { }` **can't be put in the same test module**. Choose one, or split the test modules.
