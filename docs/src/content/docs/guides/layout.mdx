## Defining where files may be placed

`layout { }` defines where the files for a Role may be placed.

```kt {3-6}
architecture {
    "UseCase" {
        // A UseCase may only be placed as *UseCase.kt inside useCase/
        layout {
            "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
        }
    }
}
```

## Styles for writing directory declarations

There are a few ways to write a directory declaration. You can use whichever style you prefer.

### Chaining with slashes

When each level has only one thing in it, you can chain them with `/` on a single line.

```kt
layout {
    "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
}
```

You can also declare just a directory.

```kt
layout {
    "app" / "ios"
}
```

In this case, only the directory `app/ios` is allowed to exist. Under the Deny by default principle, anything beyond that — such as placing files inside `app/ios` — isn't allowed.

### Wrapping in a block

When you want to place multiple things in the same directory, wrap them in a block.
This is useful when you want to place multiple files inside a specific directory.

```kt
layout {
    "src/main/kotlin/com/example/useCase" {
        "*UseCase".ktFile()
        "*UseCaseImpl".ktFile()
    }
}
```

Inside the block, you can write `description`. It becomes the explanation of "what this location is for" in the generated documentation.

```kt
layout {
    "src/main/kotlin/com/example/useCase" {
        description = "Used from multiple screens"
        "*UseCase".ktFile()
    }
}
```

## Allowing arbitrary files to be placed

### `anyFile()` — allow only files directly inside

Allows any file to be placed, but **only directly inside** that directory.

```kt
layout {
    "generated" { anyFile() }
}
```

**Subdirectories aren't allowed.** A file one level deeper is still reported as a violation.

### `ignore()` — stop checking everything below

Stops checking everything below that directory, **at any depth**.

```kt
layout {
    "build" { ignore() }
}
```

You can also write it more concisely as `"build".ignore()`.

### An empty block means the opposite

This is the easiest thing to get wrong, since they look similar.

| Syntax | Meaning |
|---|---|
| `"generated" { }` | **Nothing can be placed.** Any file inside is a violation |
| `"generated" { anyFile() }` | Any file is fine, directly inside |
| `"generated" { ignore() }` | Nothing below is checked |

**Don't leave a block empty unless you really mean "nothing goes here."**

As a rule, an empty block for a directory declaration isn't recommended, because it permits the directory to exist as an empty directory whose contents can never hold anything.

<Aside type="caution">
These are **escape hatches from deny by default**. Wherever you use them, checking stops applying to that scope.

If you overuse `ignore()` and `anyFile()` just because "declaring it is a hassle," you undermine the point of adopting katachi. Use them only for **things a machine generates** or **things whose structure is decided by another tool**.
</Aside>

## Naming a wildcard

`*` matches any name for one level. Write `"feature" / "*" / "src"` and both `feature/home/src` and `feature/settings/src` are allowed.

`capture()` gives that `*` a name.

```kt {2}
layout {
    "feature" / capture("feature") / "src" / "main" / "kotlin" / "*ViewModel".ktFile()
}
```

**As far as checking goes, it's exactly the same as `*`.** Rewriting `capture("feature")` as `"*"` doesn't change which files are allowed, not even one.

The only difference is that it has a name. This name is used when deciding [a template's destination](/katachi/guides/generate-code-from-template/#when-the-destination-has-a-wildcard-name-it-and-pass-a-value). Left as `*`, a template can't tell whether to generate into `feature/home` or `feature/settings`. Name it, and you can choose with `--arg feature=home`. For a Role with no template, `*` on its own is fine.

`capture()` can also be written midway through a `/` chain, or in a block.

```kt
layout {
    "feature" {
        capture("feature") {
            "build.gradle.kts".file()
            "src" / "main" / "kotlin" / "*ViewModel".ktFile()
        }
    }
}
```

### Only a `*` that fills a whole segment can be named

What `capture()` replaces is a `*` that occupies one whole level. The rules:

- **It can't be used for a partial match.** Write a glob like `feature-*` as `*`, unchanged
- **It can't be used on `**`.** How many levels of directory to create isn't decided
- A name follows the same rule as a Role name (starts with a letter, followed by letters, digits, `_`, `-`)
- **Using the same name twice in one path fails at declaration time.** Using the same name in a different path of the same Role is fine — the two paths then share one value

### Module wildcards can be named too

The `*` in `":feature:*".module { }` is named with the `capture` argument.

```kt {1-2}
":feature:*".module(capture = "feature") {
    mainSourceSet / kotlin / "${wildcard("feature").pascalCase}Screen".ktFile()
}
```

Inside the block, `wildcard("feature")` returns the value of the module currently being evaluated. For `:feature:home`, that's `home`, so the file the declaration above requires is `HomeScreen.kt`.

When there's more than one `*`, pass the names in order, as in `":feature:*:*".module("feature", "layer") { }`. If the number of names doesn't match the number of `*`, it fails at declaration time. Naming it doesn't change the check's result from the unnamed `":feature:*".module { }`.

In a module key, even a partial match like `":feature:*-impl".module(capture = "feature")` can be named. The value is the part matched by `*` (`home` for `:feature:home-impl`).

## Best practices

Writing out every directory for every Role is inefficient.
Extract them into constants at a meaningful unit.

```kt {1,6}
val appPackageDir = "src/main/kotlin/com/example"

architecture {
    "UseCase" {
        layout {
            appPackageDir / "useCase" / "*UseCase".ktFile()
        }
    }
}
```

## Summary

- `layout { }` declares **where a Role's files may appear**. A file in an undeclared location is a violation.
- There are two ways to write it — chaining with `/` or wrapping in a block — and **they declare the same thing**. Pick whichever is more readable.
- `anyFile()` and `ignore()` are **escape hatches from deny by default**. Checking stops applying wherever you use them.
- `capture("name")` is **a named `*`**. It checks the same as `*`; the name is used when choosing a template's destination.
- Paths **can be extracted into constants**. This keeps the definition from becoming a copy of your directory structure.
