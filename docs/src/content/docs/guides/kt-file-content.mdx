`ktFileContent { }` lets you define what may be placed in a Role's Kotlin files, using the same kind of allow list as `layout { }`.
It covers four kinds: the package, imports, top-level declarations, and class members. You write them in the same order as in Kotlin source.

```kt {6,8-13,15-19}
"ViewModel" {
    layout {
        "feature" / capture("feature") / mainSourceSet / kotlin / "**" / "*ViewModel".ktFile()
    }
    ktFileContent {
        `package`("com.example.feature.**")

        `import`("kotlin.**")
        `import`("kotlinx.coroutines.**")
        `import`("androidx.**")
        `import`("dagger.hilt.**")             // @HiltViewModel
        `import`("javax.inject.**")            // @Inject
        `import`("com.example.domain.**")

        annotated("HiltViewModel")
            .public.`class`(fileName).superclass("ViewModel") {
                public.`val`("uiState", "StateFlow<${fileName.replace("ViewModel", "UiState")}>")
                public.`fun`("on*")().returns("Unit")
                private.anythingElse()
            }
    }
}
```

List the package, imports, and declarations in that order, and write the members of a class inside that class's `{ }`.
Modifiers and annotations go before the declaration, and the supertype, type, parameters, and return type go after it. Each is in the same position as when you write Kotlin.

<details>
<summary>A HomeViewModel.kt that satisfies this definition</summary>

```kt title="feature/home/src/main/kotlin/com/example/feature/home/HomeViewModel.kt"
package com.example.feature.home

import androidx.lifecycle.ViewModel
import com.example.domain.GetUserUseCase
import dagger.hilt.android.lifecycle.HiltViewModel
import javax.inject.Inject
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow

@HiltViewModel
class HomeViewModel @Inject constructor(
    private val getUser: GetUserUseCase,
) : ViewModel() {
    private val state = MutableStateFlow(HomeUiState())
    val uiState: StateFlow<HomeUiState> = state

    fun onRefresh() {}
}
```

If you write even one import line in `ktFileContent { }`, every import that matches none of the lines you wrote is a violation.
So without the `dagger.hilt.**` and `javax.inject.**` lines, the imports of `@HiltViewModel` and `@Inject` would be violations.

</details>

## Only the kinds you write become allow lists

Of the package, imports, top-level declarations, and class members, **each kind you write even one line for becomes an allow list**, and anything that matches none of the lines you wrote is a violation. Kinds you write no lines for are not checked.

```kt
// Decide only the declarations. The package and imports are not checked
ktFileContent {
    `interface`(fileName)
}
```

```kt
// Decide only the imports. Declarations are not checked
ktFileContent {
    `import`("kotlin.**")
    `import`("kotlinx.serialization.**")
}
```

Members work the same way. If you don't attach `{ }` to a class line, that class's members are not checked. If you attach `{ }`, the lines you write inside it become the allow list for the members. An empty `{ }` means "no members at all".

## Installation

`ktFileContent { }` lives in a separate artifact, `me.tbsten.katachi:katachi-konsist`. Add it to the dependencies in `build.gradle.kts`.

```kts title="build.gradle.kts" {2}
dependencies {
    testImplementation("me.tbsten.katachi:katachi-konsist:<version>")
}
```

Next, pass `FileConstraintCheck()` to `projectArchitecture.assert()` to run the `ktFileContent { }` checks. With `assert()` alone nothing is checked, and the test fails with `[UncheckedFileConstraint]`.

```kt del={3} ins={4}
@Test
fun `files are placed according to the architecture`() {
  projectArchitecture.assert()
  projectArchitecture.assert(FileConstraintCheck())
}
```

[`konsist { }`](/katachi/guides/konsist-integration/) lives in the same artifact too, and it is checked by the same `assert(FileConstraintCheck())`.

You write `ktFileContent { }` inside a Role's block. It applies to the `.kt` files that match that Role's `layout { }`. `.kts` files are not checked.
You can't write it in a Role that has no `layout { }`. Also, for now you can write only one `ktFileContent { }` in a Role.

`ktFileContent { }` is an experimental feature during v0.3 and is annotated with `@ExperimentalKatachiApi`. How you write it may change in the future.

## How to write declarations

### Kind and name

You write a declaration line by wrapping the Kotlin keyword in backticks and passing a name.

| Syntax | Matches |
|---|---|
| `` `class`(name) `` | class (including data class, enum class, sealed class, value class, and annotation class) |
| `` `interface`(name) `` | interface (including fun interface) |
| `` `object`(name) `` | object (including data object and companion object) |
| `type(name)` | any of class, interface, or object |
| `` `fun`(name) `` | function (including extension functions; the name is the part without the receiver) |
| `` `val`(name) `` / `` `var`(name) `` | property (inside a class, including `val` and `var` in the primary constructor) |
| `` `typealias`(name) `` | typealias (can be written only at the top level of a file) |

### Modifiers

As in Kotlin, you join modifiers before the declaration with `.`.

```kt
public.data.`class`(fileName)          // public data class HomeUiState
sealed.`interface`(fileName)           // sealed interface HomeAction
const.`val`("*")                       // const val TAG = "Home"
`fun`.`interface`("*Listener")         // fun interface ClickListener
```

Every modifier you write must be present. Modifiers you don't write are not checked, so if you don't write a visibility, both public and private declarations match.
`public` matches both a declaration written with `public` and one with no visibility written, because both are public in Kotlin.

If you write a combination that can't be put on any declaration, such as `` data.`interface` `` or `public.internal`, it is an error as soon as the definition is read.

### Annotations

You write an annotation as `annotated("…")` and join it before the declaration, like a modifier.
When it gets long, start the next line with `.` and continue. It looks the same as writing the annotation on the line above in Kotlin.

```kt
annotated("HiltViewModel")
    .public.`class`(fileName).superclass("ViewModel")      // @HiltViewModel public class HomeViewModel : ViewModel()

annotated("Composable").public.`fun`(fileName)            // @Composable public fun HomeScreen()
annotated("Serializable").data.`object`(fileName)         // @Serializable data object HomeNavKey
```

<Aside type="caution">
Writing `annotated("…")` alone on a line does not attach it to the declaration on the next line. Start the next line with `.` so the two are joined into a single declaration.
</Aside>

Annotations are compared by simple name. If you write a name that contains `.`, such as `annotated("androidx.compose.runtime.Composable")`, it is compared by fully qualified name.
Annotation arguments are not checked. If you write several annotations, all of them must be present.

### Writing "any of"

Joining with `or` means "any of". It works for modifiers, annotations, and kinds.

```kt
(internal or private).data.`object`("*")                                     // a data object that is internal or private
(annotated("Preview") or annotated("PreviewLightDark")).private.`fun`("*Preview")
(`class` or `interface`)(fileName)                                           // a class or an interface. An object does not match
```

A kind is a value, so you can give a name of your own to a combination you use often and reuse it.
Make it an extension property of `DeclarationListScope` and it can be used only inside `ktFileContent { }`. It works at the top level of a file and inside a class's `{ }` alike.

```kt
val DeclarationListScope.classOrInterface get() = `class` or `interface`

ktFileContent {
    classOrInterface(fileName)
}
```

### Supertypes, types, parameters, and return types

Supertypes, property types, function parameters, and return types go after the declaration.

| Syntax | Meaning |
|---|---|
| `` `class`(fileName).superclass("ViewModel") `` | `ViewModel` is among the supertypes (what you write after `:` in Kotlin). It matches both class inheritance and interface implementation |
| `` `val`("uiState", "StateFlow<*>") `` | The property's type |
| `` `fun`("load")() `` | No parameters |
| `` `fun`("save")("String", "Int") `` | The parameter types are these, in this order (parameter names are not checked) |
| `` `fun`("on*")(anyArgs()) `` | Any parameters (same as not writing the parameters) |
| `` `fun`("on*")().returns("Unit") `` | The return type |

If you write several names in `superclass`, all of them must be among the supertypes. If you don't write type arguments, the comparison uses the name without its type arguments. For example, `superclass("Repository")` matches `Repository<User>`.

A type is compared with the type string written in the source. The package part is stripped before comparing, and `*` can be used (`"StateFlow<*UiState>"`). Nullability is distinguished, so `"String"` does not match `String?`.
A property or function whose type is left to inference does not match a line that specifies a type. However, a function with a block body and no return type written is treated as a function that returns `Unit`, as in Kotlin.

### package

```kt
`package`("com.example.feature.**")       // packages under com.example.feature
`package`(matchingDirectory)              // the package that matches the file's directory
```

Paths are separated by `.`; `*` matches one level and `**` matches any number of levels.
`matchingDirectory` is the package made by joining with `.` the directories below the source set's `kotlin/` (including Android's `java/`). For `src/main/kotlin/com/example/home/HomeScreen.kt`, it is `com.example.home`.

### import

```kt
`import`("kotlinx.coroutines.**")       // anything under kotlinx.coroutines
`import`("kotlinx.coroutines.*")        // matches kotlinx.coroutines.launch, but not kotlinx.coroutines.flow.Flow
```

Paths are written the same way as for package. An import is compared by the path exactly as written in the file.
Aliases (`as`) are not checked. A star import (`import a.b.*`) is compared as the path `a.b.*`. Packages that Kotlin imports by default, such as `kotlin.*`, are not checked, because the file has no import lines for them.

## Names

### Writing part of a name with `*`

A `*` in a name matches one or more characters, just like in file names in `layout { }`. `"*Preview"` matches `HomePreview` but not `Preview`. Names are case-sensitive.

### Using the file name and capture values

`fileName` is the part of the name of the file being checked that comes before the first `.`. For `GetUserUseCase.kt` it is `GetUserUseCase`, and for `Platform.android.kt` it is `Platform`.
`captureValue("feature")` is the value that `capture("feature")` captured in the path of `layout { }`.

The `ktFileContent { }` block is evaluated once per file. So `fileName` and `captureValue(…)` are both plain `String`s holding that file's values.

| Line written | In `HomeViewModel.kt` | In `SettingsViewModel.kt` |
|---|---|---|
| `` `class`(fileName) `` | `class HomeViewModel` | `class SettingsViewModel` |
| `` `val`("uiState", "StateFlow<${fileName.replace("ViewModel", "UiState")}>") `` | `val uiState: StateFlow<HomeUiState>` | `val uiState: StateFlow<SettingsUiState>` |
| `` `package`("com.example.feature.${captureValue("feature")}") `` | `package com.example.feature.home` | `package com.example.feature.settings` |

You can use `String` functions such as `replace` as they are, and you can also use `if` to write something different for each file.

```kt
// Put object HomeRoute and NavGraphBuilder.homeScreen(…) in HomeRoute.kt
ktFileContent {
    val feature = fileName.removeSuffix("Route").replaceFirstChar { it.lowercaseChar() }
    `object`(fileName) {
        const.`val`("PATH", "String")
    }
    `fun`("${feature}Screen")
}
```

## Required and optional

Whether a line is required or optional follows the same rule as in `layout { }`.

| Name or path | Meaning |
|---|---|
| Contains no `*` (including ones with `fileName` or `captureValue(…)` filled in) | Required. It is a violation unless the file has at least one |
| Contains `*` | Optional. It may be absent, and any number of matches are fine |

Adding `.optional()` makes a line optional.

```kt
ktFileContent {
    `import`("com.example.App")                // required. This file must import App
    `import`("androidx.compose.**")            // optional

    `class`(fileName)                          // required
    private.const.`val`("TAG").optional()      // optional
}
```

An import line that contains no `*` is also required. If you only want to allow the import of a single class, add `.optional()`.

## Prohibiting, and "anything else is fine"

Putting `not.` at the start of a line makes it a prohibited line. Anything that matches a prohibited line is a violation, even if it also matches an allowed line. To allow part of what a prohibited line covers, add `.except(…)`.

```kt
ktFileContent {
    `import`("**")
    not.`import`("com.example.feature.**")
        .except("com.example.feature.${captureValue("feature")}.**")   // do not import other features
}
```

`anythingElse()` allows declarations (top-level declarations and class members) that match none of the lines. If you put a modifier in front, it allows only declarations that have that modifier.
To say "anything else is fine" for imports, write `` `import`("**") ``.

```kt
ktFileContent {
    `class`(fileName)
    private.anythingElse()        // any private helper functions and constants are fine
}
```

Lines are judged in this order: prohibited lines, allowed lines, then `anythingElse()`. If none of them matches, it is a violation.

<Aside type="caution">
A kind for which you write only `not.` lines also becomes an allow list. Since there are no allowed lines, everything that does not match a prohibited line is a violation too.
When you want to prohibit only some things, also write a line that allows the rest, such as `` `import`("**") `` or `anythingElse()`.
</Aside>

## Class members

If you attach `{ }` to a class, interface, or object line, its members also become an allow list. What you write inside the `{ }` is the same as at the top level of a file.

```kt {5,8-9}
"UseCase" {
    layout { "core/domain" / mainSourceSet / kotlin / "com/example/domain" / "*UseCase".ktFile() }
    ktFileContent {
        `interface`(fileName) {                                    // for GetUserUseCase.kt, interface GetUserUseCase
            operator.`fun`("invoke")
        }
        `class`("Default$fileName").superclass(fileName) {          // class DefaultGetUserUseCase : GetUserUseCase
            override.`fun`("invoke")
            private.anythingElse()
        }
    }
}
```

What counts as a member is functions, properties, and nested classes, interfaces, and objects. Properties include `val` and `var` in the primary constructor, and objects include companion objects.
Constructors, `init` blocks, and enum entries are not counted.

Private, protected, and override members are counted just like other members. Members that are not written in the source, such as members inherited from a parent or the `copy` that a data class generates, are not checked.

`val` and `var` in the primary constructor are also members, so if you write `` data.`class`(fileName) { } `` with an empty `{ }`, the class can't have any properties. To allow properties, write something like `` `val`("*") `` inside the `{ }`.

## When adding it to an existing project

`ktFileContent { }` doesn't treat anything as a special case. Private declarations, imports of external libraries, and imports of other files in the same Role are all violations unless you write them.

When you add it to an existing project, it is easier to start with lines that allow broadly. For declarations, add `anythingElse()` next to the lines for the ones that must be there, so that other declarations are allowed.
Allow every import with `` `import`("**") ``, and prohibit only the ones you don't want used with `not.`. As you fix violations, remove `anythingElse()` and narrow the import lines to allow less and less.

```kt
ktFileContent {
    `import`("**")
    not.`import`("android.**")

    `class`(fileName)
    anythingElse()
}
```

If there are too many violations to fix right away, you can use [Baseline](/katachi/guides/baseline/) to tolerate the existing violations and make only new violations errors.

## Dividing the work with `konsist { }`

`layout { }`, `ktFileContent { }`, and `konsist { }` divide up what they decide as follows.

| What it decides | Where to write it |
|---|---|
| Where files may be placed | `layout { }` |
| The package and imports, and the shape of declarations and members (kind, modifiers, annotations, name, supertype, type, parameter types, return type) | `ktFileContent { }` |
| Everything else (expressions, function bodies, KDoc, strings, and so on) | `konsist { }` |

Rules that `ktFileContent { }` can't express are written with `konsist { }`, using Konsist's API. You can write both `ktFileContent { }` and `konsist { }` in a single Role.
See [Define custom rules with Konsist](/katachi/guides/konsist-integration/) for details.

## Generated documentation

The Role pages created by [Document generation](/katachi/guides/document-generation/) get a `## Kotlin file content` section. It is a table made by applying the lines you wrote in `ktFileContent { }` to the Role's example files.

## Summary

- `ktFileContent { }` is an allow list, written in the same order as Kotlin source, of the package, imports, declarations, and members that may appear in a Role's Kotlin files.
- **Only the kinds you write at least one line for become allow lists.** Kinds you write no lines for are not checked.
- A line whose name contains no `*` is required, and a line that contains one is optional (the same as `layout { }`). `.optional()` makes a line optional.
- Prohibit with `not.`, and allow the rest with `anythingElse()` and `` `import`("**") ``.
- `fileName` and `captureValue(…)` are plain `String`s holding a value for each file.
- Add `katachi-konsist` to your dependencies and call `assert(FileConstraintCheck())` in the test to run the checks.
