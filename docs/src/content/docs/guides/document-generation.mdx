katachi can generate Markdown documentation from an `architecture { }` definition.

## Basics

Configure it in `build.gradle.kts`.

```kts title="architecture-test/build.gradle.kts" {2-3}
katachi {
    // ⭐️ The fully qualified name of the property holding your `architecture { }`
    architecture = "com.example.projectArchitecture"
}
```

{/* TODO: State explicitly that `processors { register("docs", ...) }` is not needed, because the plugin registers `docs` by default. As written now, the reader cannot tell whether registering it is required */}

Once that is set, running the `runKatachiProcessor --processor="docs"` Gradle task generates the documentation.

```shell
./gradlew runKatachiProcessor --processor="docs" 
```

### Example output

Take the following definition as an example.

```kt
architecture {
    title = "myapp"

    "domain".group {
        title = "Domain layer"
        summary = "App-specific behavior and the values it acts on"

        "UseCase" {
            title = "Use case"
            summary = "A single app-specific behavior that happens on a screen"
            example("GetItemListUseCase", "The list of items")
            example("SignInUseCase", "Signing in")
            layout { ":core:domain".module { mainSourceSet / kotlin / modulePackage / "useCase" / "*UseCase".ktFile() } }
            "has only an invoke method".konsist { /* ... */ }
        }

        "Repository" {
            title = "Repository"
            summary = "The boundary where data is fetched and saved"
            layout { ":core:domain".module { mainSourceSet / kotlin / modulePackage / "repository" / "*Repository".ktFile() } }
        }
    }
}
```

```
build/katachi/docs/
├── README.md
└── domain/
    ├── README.md
    ├── UseCase.md
    └── Repository.md
```

The `myapp` in the heading is the name given by `architecture { title = "myapp" }`; **if you leave it out, it becomes `アーキテクチャ`.**
The `[myapp](../README.md) / [Domain layer](README.md)` at the top of each page is a breadcrumb, so
**every page leads back to the index.**

The placement tree **collapses directories that have only a single child.** That is why `src/` `main/` `kotlin/` `**/`
appear on one line instead of four: the tree only means something **from the point where it starts to branch.**

`Repository` has neither `konsist { }` nor `example()`, so **the `## 制約` and `## 例` sections are left out entirely.** Empty sections are never generated.

## Output directory

By default the documentation is generated under `build/katachi/docs/`.

The destination can be changed by setting `katachi.processors.docs.outputDir` in `build.gradle.kts`.

{/* TODO: There is no section on the root page's `title` / `description`.
    They are the two of `architecture { title = "..."; description = "..." }`, the same words as on a group or role.
    If left out, the heading is `アーキテクチャ ドキュメント` and there is no body.
    **They cannot be set from build.gradle.kts** (0.2 removed `docs { rootTitle }` and `--arg rootTitle`;
    the one place to write them is inside the definition) */}

{/* TODO: There is no section on `--arg mode=check`. It writes nothing, compares against what is on disk, and fails on any mismatch.
    It is how CI checks "is it up to date" when the generated files are committed, and it is the most in-demand use.
    It reports all three kinds -- missing / different content / extra -- together in one exception */}

```kt {5-7}
katachi {
    architecture = "com.example.projectArchitecture"

    processors {
        docs {
            outputDir = rootProject.layout.projectDirectory.dir("docs/")
        }
    }
}
```

## Properties used to generate the documentation

The documentation is generated from the properties you set on roles and groups.

### Role

| Property | What it becomes in the generated documentation | Pages it is used on |
|---|---|---|
| `title` | The heading of the role page. Defaults to the role's identifier | `<Role>.md`, and the link text in the index and listings |
| `summary` | The single line that goes in the listing table | `<Role>.md`, the parent's `README.md` |
| `description` | The body of the role page. The Markdown you write goes in as is, newlines included. katachi adds no structure of its own, so **the headings inside are yours to choose** | `<Role>.md` |
| `example(name, description)` | A concrete example. Call it once per example; they appear **in the order you called them** | `## 例` in `<Role>.md` |
| `documented` | Set to `false` to keep it out of the documentation. It only stops being documented -- **it still takes part in `assert()` and the other checks** | --- |

### group

A group takes the same four properties a role does. **Only `example()` is missing.**

| Property | What it becomes in the generated documentation | Pages it is used on |
|---|---|---|
| `title` | The heading of the group's README. Defaults to the group's identifier | `README.md`, `<group>/README.md` |
| `summary` | The single line in the parent's document map and in the group's section | `README.md`, `<group>/README.md` |
| `description` | The body of the group's README. | `<group>/README.md` |
| `documented` | Set to `false` to keep the whole group out of the documentation. It still takes part in the checks | --- |

<details>
    <summary>Careful: documented is not inherited</summary>

    A role inside a group with `documented = false` **still appears in the documentation unless it says `documented = false` for itself.** The same goes for a nested group.

    ```kt
    "build".group {
        documented = false
        "VersionCatalog" { documented = false }   // the group alone is not enough
    }
    ```

</details>

### Custom sections

To add your own sections to the documentation on top of the built-in ones such as the title, define a section with `documentSection()`.

{/* TODO: Show documentSection with a CodeComparison. It is implemented, so the following can be written.
    - `val TestPolicy = documentSection("Test policy")` and `var MetadataScope.testPolicy by TestPolicy`
    - **The receiver type decides where it can be written**:
      with `MetadataScope`, on a group, a role, or the root;
      with `DeclarationContainerScope`, only on a group or the root (not on a role);
      with `RoleScope`, only on a role
    - **Nesting** is `TestPolicy.documentSection("Unit tests")`. The heading level follows from the depth.
      If the parent has no body but a child does, the parent's heading still appears. A depth beyond `######` throws at declaration
    - A section with no heading (`documentSection("")`) throws at declaration
    - User-defined sections come **after the built-in sections (配置場所 / 制約 / 例)**, in the order written */}

## Summary

- The documentation is generated from **the same definition as the checks**. The two are not written separately, so **the documentation and the code do not drift apart**.
- Two things are generated: **role pages** (what this role is and where it goes) and **the placement tree in a group's README** (what may be placed in this directory).
{/* TODO: The placement tree appears not only in a group's README but also in the root README, as `## ルート直下の配置`.
    Change "in a group's README" to something equivalent to "on container pages" */}
- **Only named `konsist { }` blocks appear under `## 制約`.** Writing a name is enough to get listed, which gives a natural reason to write one.
