katachi can generate Markdown documentation from an `architecture { }` definition.

## Basics

Configure it in `build.gradle.kts`.

```kts title="architecture-test/build.gradle.kts" {2-3}
katachi {
    // ⭐️ The fully qualified name of the property holding your `architecture { }`
    architecture = "com.example.projectArchitecture"
}
```

{/* TODO: State explicitly that `processors { register("docs", ...) }` is not needed, because the plugin registers `docs` by default. As written now, the reader cannot tell whether registering it is required */}

Once that is set, running the `katachiDocs` Gradle task generates the documentation.

```shell
./gradlew katachiDocs
```

### Example output

Take the following definition as an example.

```kt
architecture {
    title = "myapp"

    "domain".group {
        title = "Domain layer"
        summary = "App-specific behavior and the values it acts on"

        "UseCase" {
            title = "Use case"
            summary = "A single app-specific behavior that happens on a screen"
            example("GetItemListUseCase", "The list of items")
            example("SignInUseCase", "Signing in")
            layout { ":core:domain".module { mainSourceSet / kotlin / modulePackage / "useCase" / "*UseCase".ktFile() } }
            "has only an invoke method".konsist { /* ... */ }
        }

        "Repository" {
            title = "Repository"
            summary = "The boundary where data is fetched and saved"
            layout { ":core:domain".module { mainSourceSet / kotlin / modulePackage / "repository" / "*Repository".ktFile() } }
        }
    }
}
```

The `myapp` in the heading is the name given by `architecture { title = "myapp" }`; **if you leave it out, it becomes `アーキテクチャ`.**
The `[myapp](../README.md) / [Domain layer](README.md)` at the top of each page is a breadcrumb, so
**every page leads back to the index.**

`Repository` has neither `konsist { }` nor `example()`, so **the `## 制約` and `## 例` sections are left out entirely.** Empty sections are never generated.

## Output directory

By default the documentation is generated under `build/katachi/docs/`.

The destination can be changed by setting `katachi.processors.docs.outputDir` in `build.gradle.kts`.

    while a Directory or a File is treated as an absolute path */}

{/* TODO: The contract that **the output directory belongs to katachi** is not written down.
    Any `*.md` the run did not generate is deleted (files other than `.md` are kept, and each deletion is logged).
    Pointing it at a directory holding hand-written Markdown deletes that Markdown, so make this stand out */}

{/* TODO: With the destination outside `build/`, `gitTracked()` picks up the generated files and
    the check fails on them as "files no role declares". They have to be **declared as a role**.
    sample/<name>/docs is exactly that setup, so point to it as the real-world example */}

{/* TODO: There is no section on the root page's `title` / `description`.
    They are the two of `architecture { title = "..."; description = "..." }`, the same words as on a group or role.
    If left out, the heading is `アーキテクチャ ドキュメント` and there is no body.
    **They cannot be set from build.gradle.kts** (0.2 removed `docs { rootTitle }` and `--arg rootTitle`;
    the one place to write them is inside the definition) */}

{/* TODO: There is no section on `--arg mode=check`. It writes nothing, compares against what is on disk, and fails on any mismatch.
    It is how CI checks "is it up to date" when the generated files are committed, and it is the most in-demand use.
    It reports all three kinds -- missing / different content / extra -- together in one exception */}

```kt {5-7}
katachi {
    architecture = "com.example.projectArchitecture"

    processors {
        docs {
            outputDir = rootProject.layout.projectDirectory.dir("docs/")
        }
    }
}
```

## Generated files

These are the files generated from an `architecture { }` definition.

### Without groups

<FileTree>
- \<output directory>/
  - README.md
  - \<Role>.md
</FileTree>

### With groups

<FileTree>
- \<output directory>/
  - README.md
  - \<Role>.md
  - \<group>/
    - README.md
    - \<Role>.md
    - \<nested group>/
      - README.md
      - \<Role>.md
</FileTree>

Groups can nest, and a nested group is generated below the directory of its parent group.

File and directory names are decided by the **identifier** (`UseCase` in `"UseCase" { }`, `domain` in `"domain".group { }`), not by `title`. Changing `title` does not change the file name.

## Properties used to generate the documentation

The documentation is generated from the properties you set on roles and groups.

### Role

| Property | What it becomes in the generated documentation | Pages it is used on |
|---|---|---|
| [`title`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/title.html) | The heading of the role page. Defaults to the role's identifier | `<Role>.md`, and the link text in the index and listings |
| [`summary`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/summary.html) | The single line that goes in the listing table | `<Role>.md`, the parent's `README.md` |
| [`description`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/description.html) | The body of the role page. The Markdown you write goes in as is, newlines included. katachi adds no structure of its own, so **the headings inside are yours to choose** | `<Role>.md` |
| [`example(name, description)`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/example.html) | A concrete example. Call it once per example; they appear **in the order you called them** | `## 例` in `<Role>.md` |
| [`documented`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-role-scope/documented.html) | Set to `false` to keep it out of the documentation. It only stops being documented -- **it still takes part in `assert()` and the other checks** | --- |

### group

A group takes the same four properties a role does. **Only `example()` is missing.**

| Property | What it becomes in the generated documentation | Pages it is used on |
|---|---|---|
| [`title`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/title.html) | The heading of the group's README. Defaults to the group's identifier | `README.md`, `<group>/README.md` |
| [`summary`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/summary.html) | The single line in the parent's document map and in the group's section | `README.md`, `<group>/README.md` |
| [`description`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/description.html) | The body of the group's README. | `<group>/README.md` |
| [`documented`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/-group-scope/documented.html) | Set to `false` to keep the whole group out of the documentation. It still takes part in the checks | --- |

<details>
    <summary>Careful: documented is not inherited</summary>

    A role inside a group with `documented = false` **still appears in the documentation unless it says `documented = false` for itself.** The same goes for a nested group.

    ```kt
    "build".group {
        documented = false
        "VersionCatalog" { documented = false }   // the group alone is not enough
    }
    ```

</details>

### Custom sections

To add your own sections to the documentation on top of the built-in ones such as the title, define a section with [`documentSection()`](/katachi/api-docs/katachi/me.tbsten.katachi.dsl/document-section.html).

Declare a section with `documentSection("heading")`, and create a property to write it through with `by`.

```kt
val TestPolicy = documentSection("Test policy")
var MetadataScope.testPolicy by TestPolicy
```

**The receiver type of the property decides where it can be written.**

| Receiver type | Where it can be written |
|---|---|
| `MetadataScope` | Anywhere: a group, a role, or the root |
| `DeclarationContainerScope` | Only a group or the root (not a role) |
| `RoleScope` | Only a role |

Sections can be nested. Declare the child on its parent section, as in `TestPolicy.documentSection("Unit tests")`.
**The heading level follows from the depth.** The top level is `##`, and each level down adds one `#`.
Even if the parent has no body, its heading still appears when a child has one.

<CodeComparison>
    <CodeComparison.Panel label="Section definition">
        ```kt
        @file:OptIn(ExperimentalKatachiApi::class)

        val TestPolicy = documentSection("Test policy")
        var MetadataScope.testPolicy by TestPolicy

        val UnitTest = TestPolicy.documentSection("Unit tests")
        var RoleScope.unitTest by UnitTest

        val projectArchitecture = architecture {
            "UseCase" {
                title = "Use case"
                summary = "A single app-specific behavior that happens on a screen"
                example("SignInUseCase", "Signing in")
                layout { "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile() }

                unitTest = "Replace the repository with a fake and check the return value."
            }
        }
        ```
    </CodeComparison.Panel>
    <CodeComparison.Panel label="Generated Markdown">
        ```md title="UseCase.md"
        [アーキテクチャ](README.md)

        # Use case

        A single app-specific behavior that happens on a screen

        ## 配置場所

        | モジュール | パス | 使い分け |
        |---|---|---|
        |  | `src/main/kotlin/com/example/useCase/*UseCase.kt` |  |

        ## 例

        - `SignInUseCase` ... Signing in

        ## Test policy                                 ← no body, but shown because a child has one

        ### Unit tests                                 ← one level down, so ###

        Replace the repository with a fake and check the return value.
        ```
    </CodeComparison.Panel>
</CodeComparison>

Custom sections come **after the built-in sections (`## 配置場所` / `## 制約` / `## 例`)**, in the order they are written in the definition.

The following two throw **when the section is declared**, not when the documentation is generated.

- An empty heading (`documentSection("")` or whitespace only): `KatachiUnnamedDocumentSectionException`
- Nesting deeper than `######` (the sixth level and below, counting the top level `##` as the first): `KatachiDocumentSectionTooDeepException`

<Aside>
    `documentSection()` is an experimental API. A file that uses it needs `@OptIn(ExperimentalKatachiApi::class)` (the example above opts the whole file in with `@file:OptIn`).
</Aside>

## Summary

- The documentation is generated from **the same definition as the checks**. The two are not written separately, so **the documentation and the code do not drift apart**.
- Two things are generated: **role pages** (what this role is and where it goes) and **the placement tree in the READMEs of groups and of the root** (what may be placed in this directory). The placement tree appears as `## このグループの配置` in a group's README and as `## ルート直下の配置` in the root README.
- **Only named `konsist { }` blocks appear under `## 制約`.** Writing a name is enough to get listed, which gives a natural reason to write one.
