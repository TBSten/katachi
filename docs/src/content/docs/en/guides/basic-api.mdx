This page introduces katachi's core API.
Once you know these, you should understand the basics of using katachi.

## 1. `architecture { }`

`architecture { }` is the entry point for defining your project's overall architecture.
Inside it, you write the roles of the files that exist in your project.

```kt
architecture {
  "UseCase" { /* ... */ }
  "Repository-interface" { /* ... */ }
}
// This project has two roles: `UseCase` and `Repository-interface`
```

The elements inside an architecture (Role) are covered in more depth in a later section.

## 2. Testing the architecture with `assert()`

`assert()` is the function that tests the architecture defined with `architecture { }`.

```kt {8}
val projectArchitecture = architecture {
  "UseCase" { /* ... */ }
  "Repository-interface" { /* ... */ }
}

@Test
fun `files are placed according to the architecture`() {
  projectArchitecture.assert()
}
```

## 3. Declaring a Role with `"Name" { }`

As part of the architecture definition, `"Name" { }` declares the role that a file appearing in the project plays.

```kt {2,4}
architecture {
  "UseCase" { /* ... */ }

  "Repository-interface" { /* ... */ }
}
```

Writing `"Name" { }` inside an `architecture { }` block lets you declare the roles of files that appear in the project.

### Example roles

If you're using a well-known architecture, roles typically look something like this.

| Group | Role |
|---|---|
| MVC | `Controller` |
| | `View` |
| | `Model` |
| MVVM | `View` |
| | `ViewModel` |
| Clean architecture | `Service` |
| | `UseCase` |
| | `Entity` |
| | `Repository-interface`, `Repository-implementation` |

### Deny by default

In katachi, **only files with a declared Role are allowed to exist in the project**.

In other words, adopting katachi requires you to enumerate the Roles that match your project's conventions.

### Related documentation

For Role, also see [Role definitions in depth](/katachi/en/guides/role/).

## 4. Grouping Roles with `"...".group { }`

`"Name".group { }` is a block for grouping Roles together.

For example, in Clean architecture, `UseCase` and `Repository-interface` are both **roles in the same domain layer**.

```kt {2}
architecture {
  "domain".group {
    "UseCase" { /* ... */ }
    "Repository-interface" { /* ... */ }
  }
}
```

Expressing a group like "the domain layer" in the DSL makes the relationships and hierarchy between roles clearer. Grouping Roles at a sensible granularity is important for building an architecture definition that's easy to understand.

### Related documentation

For grouping Roles, also see [Role definitions in depth](/katachi/en/guides/role/).

## 5. Defining where files may exist with `layout { }`

Declaring a Role with `"..." { }` doesn't say anything about the files that correspond to that Role.

`layout { }` is the block that defines where the files for a Role may be placed.

```kt {3-5}
architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }
  }
}

// A UseCase may be placed at `src/main/kotlin/com/example/useCase/*UseCase.kt`
```

### How it works

Under the Deny by default principle, you can't place a file anywhere that isn't declared in `layout { }`.

Say an AI Agent tries to place a new UseCase file at `src/main/kotlin/com/example/GetItemUseCase.kt` (it should really go inside the useCase package). The moment `assert()` is called, katachi detects that no Role matches this path, and the test fails.

### Related documentation

For `layout { }`, also see [Layout definitions in depth](/katachi/en/guides/layout/).

## 6. Constraining a file's contents with `"...".konsist { }`

You can set constraints on the files of a declared Role using [Konsist](https://docs.konsist.lemonappdev.com/).

```kt {8}
architecture {
  "UseCase" {
    layout {
      "src/main/kotlin/com/example/useCase" / "*UseCase".ktFile()
    }

    "has exactly one invoke function".konsist {
      classes().must { it.functions().map { f -> f.name } == listOf("invoke") }
    }
  }
}
```

You can set constraints on the files matched by `layout { }` using the Konsist API.

### Related documentation

For `"...".konsist { }`, also see the [Konsist integration guide](/katachi/en/guides/konsist-integration/).
