# 11. ドキュメントがガイドのルールに沿っているか

[SKILL.md](../SKILL.md) の手順 11 の詳細。

手順 5 は「実装とドキュメントが合っているか」、これは「**ドキュメントの中で、ガイドが書いたルール・ベストプラクティスに、
ほかのページのコード例や本文が沿っているか**」。ルールに反するコード例を利用者が写すと、悪い形が広まる。
**直さず報告する。**Gradle を使わず、ファイルも書き換えないので、ほかの手順と待ち合わせなくてよい。
対象は日本語の原本だけ（英語は訳で、手順 2 が原本に揃える。原本が直れば訳も直る）。

## 最初に `lint:text` を回す

手順の最初に `cd docs && pnpm run lint:text` を回す（`docs/prh.yml` の言い換え辞書による機械の検査）。
落ちたら、その内容（ファイルと行・語）を結果の冒頭に書いて報告に入れる（直さない）。通ったことも書く。

## 対象

- 検査される側: `docs/src/content/docs/ja/` の全ページ（get-started / guides / recipes / roadmap）、`README.ja.md`、
  `docs/public/install/ja/` の手順書（`index.md` とテンプレート HTML）。ルールの出どころ自身も、他のガイドとの食い違い
  （例: role.mdx の例が basic-api.mdx の「1 Role 1種類」に反する）は検査する。
- ルールの出どころ（既定）: `docs/src/content/docs/ja/guides/` の `basic-api.mdx`・`role.mdx`・`layout.mdx`・`konsist-integration.mdx`。

## 手順

### 1. 出どころを確かめる（チェックの前に、必ず）

既定の4ページだけで決めない。次を読み、ルール・ベストプラクティス・推奨/非推奨の書き方（「〜が既定」「〜しない」「〜を推奨」
「ベストプラクティス」「良い〜」「避ける」「逃げ道」の節・Aside・見出し）があれば対象に足す。

- `docs/src/content/docs/ja/guides/` のほかのガイド（`generate-code-from-template.mdx`・`processor.mdx`・`baseline.mdx`・
  `document-generation.mdx` など）
- `docs/AGENTS.md`（`docs/CLAUDE.md` は同じ内容）: コード例の書き方・用語・節の作り方の決まり。とくに「文章の方針」の節（原則・理由・🆖/🆗 の例）は、機械（`lint:text`）では拾えない判断の要る決まりなので、必ずチェックリストに入れ、例に似た別の場面にも当てはめて照合する
- `docs/src/content/docs/ja/recipes/` のうち、自分でルールを述べているもの

確認には `grep -n -E "推奨|ベストプラクティス|既定|しない|避け|逃げ道|良い|悪い|注意" <ファイル>` が使える。
**どのページのどの見出しから何を拾ったか**（採用したページ・「ルールは無かった」と判断したページ）を、結果の冒頭の表に書く。

### 2. チェックリストを作る（1体目の subagent。model: opus）

役割: ルールを**照合できる形**に起こすこと（照合はしない）。各項目は「何が OK / NG か」を1行で言える粒度にし、
**根拠のページと見出し**を付ける。`tmp/docs-rules/rules.md` に書く。書式は次のとおり。

```md
## A. 用語・書き方
- [ ] 概念は「役割」ではなく「Role」と書く。（role.mdx「Role を定義する」）
## B. layout / C. konsist / D. docs/AGENTS.md の決まり / E. ガイド同士の食い違い（報告用）
```

観点の例（今回の版で最新のガイドから拾い直す。この例をそのまま使わない）: 1つの Role には1種類のファイル、Role 名は
PascalCase、`"build".ignore()` を推奨形にする、`anyFile()`/`ignore()` は逃げ道なので理由を添える、`capture()` はテンプレートの話、
修飾名の区切りは `.`、konsist の制約名は「〜すること」形、判定は `must`/`mustNot`/`mustBeEmpty` のみ、コード例はファイルの宣言と
`.template` の間で改行、ハイライト行が主要な行を指す（空行や閉じかっこを指さない）、削除済みの節・廃止した書き方を書かない。
ガイドから「削除した」「もう書かない」とされたものは、NG 側のチェック項目として拾う。

直前のリリースで手作業でまとめたチェックリストが `.local/tmp/*/rules.md` 等にあれば材料にしてよい（無ければ気にしない）。
**リストの版（拾った日・出どころ）を先頭に書く。**

### 3. 照合（ページのまとまりごとの subagent。model: sonnet。並列）

1. `python3 .claude/skills/prerelease/scripts/list-site-pages.py --group ja` で日本語のページを列挙する（`tmp/docs-rules/pages-ja.txt`）。
2. 次のまとまりに分ける。1体が50KB を超えるなら分ける。
   - `get-started/` ＋ `roadmap.mdx`
   - `guides/`（出どころのガイド自身を含む。1体が大きすぎれば前半・後半に）
   - `recipes/`
   - `README.ja.md` ＋ `docs/public/install/ja/`
3. 各 subagent に渡すもの: `tmp/docs-rules/rules.md`、担当ファイルの一覧、下の「指示に入れること」、priority の基準表。
   コードブロックごと（ハイライト行・`.template` の改行・書き方）と本文ごと（用語・説明）に、全項目を当てさせる。
   「該当なし」で済ませず、コード例の数と見たコード例の数を報告させる。
4. 結果は `tmp/docs-rules/part-<まとまり>.md`。

指示に入れること:
- **ページを直さない。**見つけたものを警告として報告するだけ。ファイルを書き換えない。
- **自分が変えていないファイルは、差分があっても戻さない**（git の add / commit / stash / checkout / restore / reset / clean もしない）。
- 1件ごとに、ファイルと行・該当のコードや文・破っているチェック項目の番号と根拠・priority・直し方の案を書く。
- 迷ったら低い priority を付け「要確認」と書く。ルールの側が曖昧・食い違っているなら、コード例の側の問題にせず「E. 食い違い」として報告する。
- 書き終えたら件数（priority ごと）と、書いたファイルのパスを返す。

### 4. まとめる（オーケストレータ）

`tmp/docs-rules/part-*.md` を 1 つにして `.local/release-v<版>/docs-rules.md` に書く。同じ原因（同じルール違反のコピー）は
1件にまとめ、該当箇所を並べる。

priority は [check-docs-against-impl](../../check-docs-against-impl/SKILL.md) の基準表に合わせる。

| priority | 基準（この手順での例） |
|----------|------------------------|
| 9〜10 | 書いたとおりにすると失敗し、原因にたどり着けない（ルール違反というより手順 5 の領域。見つけたら手順 5 へ回す） |
| 7〜8  | コンパイルできない・廃止された API や書き方のコード例（削除済みの `DirectOnly` など）。エラーから直せる |
| 5〜6  | ルールに反するコード例で、利用者が写すと悪い形が広まる（1 Role に2種類のファイル、`anyFile()`/`ignore()` の乱用、`assertTrue` 系 など） |
| 3〜4  | 読み手が迷う（用語の不統一、ハイライト行がずれている、ガイド同士の食い違い） |
| 1〜2  | 表記ゆれ・改行の作法（`.template` の前の改行など） |

雛形:

```md
# ドキュメントのルール適合チェック（v<版>）

## ルールの出どころ
| ページ | 拾った見出し・項目 |   ← 「ルールは無かった」ページも書く
## 結果
| priority | 件数 |
## priority 7〜8 / 5〜6 / 3〜4 ...（警告は `### [WARN / priority n/10] {タイトル}`。1〜2 は <details>）
## ガイド同士の食い違い（E）
## 確かめたページ数・コード例の数
```

- prerelease-check-list.md には、件数と priority 7 以上の警告、出どころに足したページだけを書く。
- 出どころのガイドを直す判断（ルール自体の変更）は利用者に聞く。TODO.html の「判断してほしい」に入れる。
