---
name: check-docs-against-impl
description: >-
  ドキュメントの記述が、katachi の実際の実装・挙動と食い違っていないかを確かめる
---

ドキュメントは人が書き、実装は先に進む。気づかないうちに「まだ使えない」と書いた機能が使えるようになっていたり、
コード例が今の API ではコンパイルできなくなっていたりする。この SKILL で食い違いを洗い出す。

**直さずに報告する。** ドキュメントの本文は人が書く（`docs/CLAUDE.md`）。利用者が「直して」と言ったときだけ直す。

## 対象

| 何                   | どこ                                                                     | 備考                                                                              |
|----------------------|--------------------------------------------------------------------------|-----------------------------------------------------------------------------------|
| ドキュメントサイト   | `docs/src/content/docs/ja/**/*.mdx`                                      | **日本語が原本なので、日本語だけを確かめる。**英語は translate-ja-en で追随させる |
| README               | `README.ja.md`、`sample/**/README.md`                                    | 同上。`README.md` は訳                                                            |
| インストールキット   | `docs/public/install/ja/index.md`、`katachi-install.sh` が出すメッセージ | 手順書どおりにスクリプトが動くか                                                  |
| API リファレンスの元 | `katachi/src/main`・`katachi-konsist/src/main` の公開 API の KDoc        | KDoc の例は自己検査でコンパイルされるので、確かめるのは文章の主張だけ             |
| サンプル             | `sample/**` の定義・ビルド設定・コメント                                 | 利用者が写す見本。CI で緑でも、古い書き方や嘘のコメントは残る                     |

実装の側の根拠は、`katachi/`、`katachi-konsist/`、`katachi-gradle-plugin/`、`tool/dokka/` のソースと、`sample/` の実際の挙動。

**サンプルは根拠であると同時に、確かめる対象でもある。** CI が保証するのは「今の定義で緑になる」ことだけで、
「今の katachi で推奨される書き方になっている」「コメントが本当のことを言っている」ことは保証しない。
利用者もドキュメントのレシピもサンプルを写すので、古い書き方が残るとそのまま広がる。

## ワークフロー

### 1. 範囲を決める

引数で基準（コミットやタグ）を渡されたら、そこからの実装の変更を起点にする。無ければ直前のリリースのタグ（
`git tag --sort=-creatordate` の先頭）を使う。

```shell
git diff <基準> --stat -- katachi/src/main katachi-konsist/src/main katachi-gradle-plugin/src/main tool/dokka/src/main
```

変更された公開 API・振る舞いを列挙し、それに触れているドキュメントを grep
で探す。変更が無い範囲のドキュメントも、ページ単位で一通り目を通す（ずれは実装の変更と無関係に残っていることがある）。

### 2. 並列に確かめる

ドキュメントのまとまりごとに1体ずつ、並列な subagent（model: opus。主張と実装を突き合わせる判断が要る）に任せる。目安は「get-started」「guides」「recipes
と roadmap とトップ」「README とサンプルの README」「インストールキット」「サンプル」。

#### 動かして確かめるときは、リポジトリの写しで

**`sample/` を直接動かさない・いじらない。** どのサンプルも `includeBuild("../..")` でリポジトリのルートを取り込むので、
同じ `katachi/build/` を取り合う。また、ドキュメントのコード例を試すにはサンプルを書き換える必要があり、
本物を書き換えると**戻し忘れ**がそのままコミットに紛れ込む。写しなら捨てるだけで済む。

動かす subagent には、**1体に1つ**リポジトリの写しを作らせる。`sample/` だけを写すと `../..` が外れるので、
ルートごと写す。

```shell
W=.local/tmp/docs-vs-impl-<日付>/work-<担当名>
mkdir -p "${W}"
rsync -a --exclude .git --exclude .local --exclude build --exclude .gradle --exclude .kotlin \
  --exclude node_modules --exclude .idea ./ "${W}/"
git -C "${W}" init -q && git -C "${W}" add -A   # 無いと gitTracked() が 0 件になり、何も検査されない
```

- 写しの中は自由に書き換えてよい（ドキュメントの例を貼る、違反を仕込む、など）。本物の `sample/` と `docs/` には触らない
- Gradle は写しの中で `--project-cache-dir` をその写しの `.gradle-cache/` に向けて走らせる。写しが別なら並行してよい
- 結果の根拠に写しのパスを書くときは、何を書き換えたかも添える（本物では再現しないため）

サンプル担当に確かめさせること（上の項目に加えて）:

- **今の katachi で推奨される書き方か**: 基準以降に入った機能で置き換えられる古い書き方が残っていないか
  （例: `gradle()` があるのに Gradle のファイルの役割を手で並べている、Gradle plugin があるのに手で配線している）
- **非推奨 API を使っていないか**（`@Deprecated`、警告を抑制して使っている箇所）
- **「1 つの役割 = 1 種類のファイル」を守っているか**。サンプルは見本なので、ドキュメントで禁じた形を持っていてはいけない
- **コード内のコメント・KDoc の主張**が実装と合っているか（「〜はまだ無いので」「〜のため手で書く」など）
- **サンプル同士・ドキュメントとの食い違い**: 同じことを3つのサンプルで別の書き方をしていないか、
  ドキュメントが「サンプルではこう書いている」と言っている形と合っているか
- **ビルド設定**: バージョンの SSoT（`gradle/libs.versions.toml`）から外れて直書きしている箇所、
  Kotlin のバージョンに合わないコンパイラオプション（2.4 以降の `-Xcontext-parameters` など）

subagent に確かめさせること:

- **状態の主張**: 「まだ使えない」「v0.x で入る予定」「〜だけです」のような記述が、今の実装と合っているか
- **コード例**: 今の公開 API
  でそのまま成り立つか（シグネチャ・import・存在しない関数や非推奨でコンパイルエラーになるもの。例: `konsist { }` の中の
  `assertTrue`）。シェルの例はコマンドとして成り立つか
- **振る舞いの説明**: 例外になるのか・コンパイルエラーになるのか・警告なのか、出力の形（違反の報告、生成物のパス）が実装と合っているか。必要なら
  `sample/` で実際に動かして確かめる
- **本文とコード例の食い違い**: 同じページの中で、本文の名前とコード例の名前が違う（例: 本文は `Deprecated`、コードは
  `Obsolete`）
- **ページの説明文（frontmatter の `description`）** が本文の中身と合っているか
- **書きかけの残り**（途中で切れた文など）。これは直す対象ではなく、報告だけ

priority は「3. まとめる」の基準表をそのまま渡して付けさせる。1件ごとに次を書かせる:

- ドキュメントの場所（`file://` の絶対パスと行）
- 何と書いてあるか / 実装はどうか（根拠のファイルと行、または実行した結果）
- 直し方の案

**subagent にもドキュメントを直させない。**自分が変えていないファイルは差分があっても戻さない（利用者が IDE
で同時に編集していることがある）。Gradle を走らせるときは他のビルドと重ならないようにする（`pgrep -fl GradleWrapperMain`
で確かめる。`project-cache-dir` は `.local/tmp/gradle-cache/<名前>`）。

### 3. まとめる

結果を1つのファイルにまとめる。置き場所は呼び出し元が指定する（無ければ `.local/tmp/docs-vs-impl-<日付>.md`）。

- 重大度で並べる。利用者が書いたとおりにすると失敗するもの（コンパイルできない例、存在しない API、誤った手順）を上に、言い回しのずれを下に
- 同じ原因のものは1件にまとめる
- priority は次の基準で付ける。subagent にもこの表を渡し、基準をそろえる

| priority | 基準 | 例 |
|---|---|---|
| 9〜10 | 書いたとおりにすると**失敗し、原因にたどり着けない**。または検査が黙って効かなくなる | 手順どおりでビルドが通らない、テストが 0 件のまま緑になる、存在しないコマンド |
| 7〜8 | 書いたとおりにすると失敗するが、**エラーメッセージから直せる** | コンパイルできないコード例、存在しない API・オプション、誤ったタスク名 |
| 5〜6 | 失敗はしないが、**誤った理解や古い書き方が広まる** | 「まだ使えない」と書いた機能が使える、サンプルが推奨されない書き方、振る舞いの説明（例外か警告か）が違う |
| 3〜4 | 読み手が迷う・遠回りする | 本文とコード例の名前の食い違い、description と本文のずれ、リンク先の行ずれ |
| 1〜2 | 言い回し・表記ゆれ・書きかけの残り | 途中で切れた文、用語の揺れ |

迷ったら低いほうを付け、「要確認」と書く。
- 警告は次の形で書く

```md
### [WARN / priority 8/10] {タイトル}

- 場所: file://{絶対パス}:{行}
- 書いてあること: …
- 実装: …（根拠: file://…）
- 直し方の案: …
```

### 4. 報告

件数（重大度ごと）と、まとめたファイルの `file://` リンクを返す。重大なもの（priority 7 以上）だけは本文にも短く書く。
