## 対象のフィードバック
{記録の一覧}
記録は `node docs/src/integrations/feedback/server/cli.mjs read <id>` で全部読むこと。置き場の直接の変更・移動・削除はしない。
記録には新形（schema: 1。source・stale・dirty などがある）と旧形（page と created だけ）がある。無い項目は「情報が無い」だけで異常ではない。
`kind: elements` の記録は、frontmatter の source・xpath・selector・heading が配列で、本文の節が `### n.` で要素ごとに並ぶ。`attachments` にスクリーンショットの PNG があれば、Read で画像を見てから判断する（パスは dev のリポジトリのルートからの相対）。
{各件の要約}
`stale: true` は、記録のあとにソースが変わったこと。source の行番号は今のソースとずれているかもしれない。まず `git log` で、すでに直っていないかを確かめる。

## 関係するメモ
{そのページのメモのパス（無ければ「なし」）}
メモ（`<Inbox>/memo/<言語>/<ページのパス>.md`）は、利用者がページを読みながら書き溜めた考え。記録の意図の手がかりとして読む（末尾の HTML コメントの JSON は読まなくてよい）。メモは書き換えない。記録とメモが食い違ったら、新しいほう（各メモの「最終更新」と記録の created）を優先し、報告に両方を書く。記録に無いメモだけの指摘は直さず、報告に「メモにあった未対応の指摘」として並べる。

## 決まり
- チケット: {チケット}。hook は掴んだチケットが無いと Edit/Write を止める。
- docs のページは、日本語（docs/src/content/docs/ja/）が原本。直すのは頼まれたページだけ。ほかのページへの波及は、直さず報告の「提案」に書く。英語の訳は自分では直さず、「要翻訳のページ」として報告する（オーケストレータが translate-ja-en を回す）。
- docs/prh.yml と docs/AGENTS.md は直さず、足したい項目を報告の「提案」に書く。
- 日本語を書いたら yomiyasu skill で推敲する。`.module { }` を例に書かない。docs/src/content/docs/0.2/ と ja/0.2/ は凍結なので触らない。
- 確認: `cd docs && pnpm run lint:text`。ビルドは `pnpm exec astro build --outDir /Users/tbsten/dev/katachi/.local/tmp/{作業名}/dist`（docs/dist に書かない）。他の担当の作業途中で落ちたら、自分の変更が原因でない限り直さず報告に書く。
- dev サーバーは本物の docs/ で立てない（利用者の編集で落ちる）。必要なら repo-copy を作ってポートを指定してもらう。保存先は KATACHI_FEEDBACK_DIR を .local/tmp/ に向ける。本物の .local/feedback/ には書かない。

## 禁止
- 記録の archive・移動・削除・変更（archive はオーケストレータだけ）。
- 自分が変えていないファイルの差分を戻すこと（git restore / checkout / stash を含む）。利用者が docs/ を編集中のことがある。git の変更操作（add / commit / mv など）。
- 他のプロセスの kill（自分が起動したものはよい）。
- 大きな設計変更の実装。必要なら実装せず、選択肢と推奨を報告に書く。小さな判断は既存の流儀に最も合う形で進め、「判断した点」に書く。

## 報告（日本語、簡潔に）
記録ごとの結果（直した/すでに反映済み/判断待ち）/ 変更したファイル / 要翻訳のページ / 提案（波及・prh・AGENTS）/ 確認コマンドの結果 / 判断した点 / 利用者の確認が要る点
```

### 調査型
```
## 種類: 調査
1. 利用者の質問を 1 文で言い直す。
2. 根拠（ファイルと行、実際に動かした結果）つきで答える。ドキュメントと実装の照合は .claude/skills/check-docs-against-impl/SKILL.md の手順に従い、直さず報告する。
3. まず stale / 古い dev サーバー（再起動で直る）を疑う。
4. 本当に食い違っていれば、最小の直しを案として書く（直すのは頼まれたページだけ）。
```

```

現状と問題（根拠のファイルと行）/ 影響範囲 / 案 2〜3 と長所短所 / 推奨と理由 / 利用者に決めてほしい点。
