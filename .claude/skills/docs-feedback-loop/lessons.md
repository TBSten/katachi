# 落とし穴（docs フィードバックの loop）

出どころ: グローバルの `feedback-mode` skill の lessons を、docs サイトに当てはまるものに絞って置き換えた。

## 古い dev サーバー・古い記録
統合（`docs/src/integrations/feedback/`）を直しても dev を再起動しないと効かない。記録に `stale: true` が付く、質問型で「なぜか動かない」が出る、はまずこれを疑う。再起動で直る。

## 共有ファイルの編集が消える
`docs/prh.yml`・`docs/astro.config.mjs`（sidebar）・同じページの ja/en の対を複数の担当が同時に直すと消える。書く直前に読み直す。同じページの件は 1 人にまとめる。`prh.yml` は最後に 1 人がまとめて足す。

## build が一時的に落ちる
`pnpm run build` は他の担当が作業中の mdx で落ちる。自分の変更が原因でなければ直さず報告する。

## dev のリロードで検証が揺れる
利用者や他の担当が mdx を直すたびに dev がリロードされる。通し検証は repo-copy の dev で回す（GIT_DIR を本物に向ける）。保存先は `KATACHI_FEEDBACK_DIR` を `.local/tmp/` に向け、本物の `.local/feedback/` を汚さない。

## 記録が 0 バイト
保存は排他的に開いてから書くので、一瞬 0 バイトに見える。少し置いて再確認。数分たっても 0 バイトなら利用者に聞く。

## 旧形と新形
旧形（schema 無し）にはソース行・stale・dirty が無い。無いことを異常と読まない。書き換えない。

## 利用者の編集を戻される
subagent が「自分が変えていないファイル」を HEAD で上書きすることがある。指示に「差分があっても戻さない」を必ず入れる。

## 検証担当の変異を commit しない
検証で一時的に壊した行（`if (false` など）が commit に入る事故がある。commit 前に跡を探す。

## 設計型は判断を待つ
設計型の提案は利用者の判断を待ってから実装する。判断待ちの一覧は毎回の報告の最後に累積する。報告は承認ではない。

## 長く動く subagent
30 分を超えたら `SendMessage` で進み具合と期限を聞く。勝手に kill しない。

## 日付
長いセッションでは `date` を見て、HISTORY.md の日付に使う。
