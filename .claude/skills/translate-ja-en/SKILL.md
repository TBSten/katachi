日本語ドキュメントが主導で更新されており、定期的に英語ドキュメントへ翻訳同期が必要。
この SKILL で翻訳同期を行う。

**日本語が原本、英語は訳。**英語側で書き起こしたり、英語側だけに内容を足したりしない
（`docs/CLAUDE.md` の「日本語が原本、英語は翻訳」の節と同じ決まり）。

**食い違ったら、いつも日本語を正として英語をそろえる。**利用者に確かめない。英語にしか無い節・段落・コードのコメント、
英語だけ違う構成（原本が `<Tabs>` なのに英語は見出し、など）は、原本の形に直すか消す。
原本のほうが間違っていると気づいたときだけ、訳さずに利用者に知らせる（下の「守ること」）。

## 対象ファイルのパターン

**[`target-file-pattern.csv`](target-file-pattern.csv) が唯一の置き場。**組を足す・変えるときはそのファイルだけを直す。
`scripts/list-targets.py` もそのファイルを読むので、ここやスクリプトに組を書き写さないこと。

書き方（1行が1組）:

| 列               | 中身                     |
|------------------|--------------------------|
| `対象ファイル`   | 日本語の原本             |
| `翻訳先ファイル` | 英語の訳                 |
| `備考`           | その組だけの注意（任意） |

- ディレクトリの組は `<dir>/**/*.<拡張子>` で書く。原本のディレクトリからの相対パスが同じファイルどうしが組になる
- **拡張子は1行に1つ。**`*.{md,mdx}` のようにまとめるとカンマが列の区切りとぶつかるので、拡張子ごとに行を分ける
- ファイルの組はワイルドカードを含まない1ファイルどうし

対象にしないもの: `docs/public/ja/api-docs/index.html`（訳ではなく、日本語ページから API リファレンスへ送るリダイレクト1枚。どの組にも当たらないので
CSV には書かない）。

### トップページの文言（CSV の組にしない）

トップページ（`/katachi/`・`/katachi/ja/`）は content collection の MDX ではなく、`docs/src/pages/` の `.astro`
で、文言は **`docs/src/components/home/strings.ts` の1ファイルに `ja`（原本）と `en`（訳）が並んでいる。**
原本と訳が別ファイルではないので、`target-file-pattern.csv` の組にはしない（`list-targets.py` にも出ない）。

- `strings.ts` の `ja` が変わっていたら、同じキーの `en` をその場で訳す。変わったかどうかは
  `git diff -- docs/src/components/home/strings.ts` と `git log -1 -- docs/src/components/home/strings.ts` で見る
- `en` の型は `ja` から決まる（`const en: HomeStrings`）。`ja` にだけキーを足すと型検査で落ちるので、キーの取りこぼしは起きない。
  中身の訳し漏れは目で確かめる
- `Html` で終わるキーの HTML タグ（`<br />`・`<code dir="auto">` など）は写す。サイト内リンクは locale の付かない形
  （`guides/document-generation/`）のままで、`/katachi/ja/` → `/katachi/` の書き換えは要らない
- ページの構造（`docs/src/components/home/Home.astro`）は1か所しかないので訳す対象ではない

## ワークフロー

### 1. 対象ファイルをコマンドで列挙

対象ファイルのパターンに従って具体的な対象ファイルを列挙する。

```shell
python3 .claude/skills/translate-ja-en/scripts/list-targets.py
```

リポジトリの直下で実行する。訳し直しが要る組だけが出る（`--all` を付けると全部出る）。

| 判定      | 意味                                   | やること                                                                                 |
|-----------|----------------------------------------|------------------------------------------------------------------------------------------|
| `missing` | 訳が無い                               | 原本を丸ごと訳して新しく作る                                                             |
| `stale`   | 原本のほうが新しい                     | `base` 以降の原本の差分を訳に反映する                                                    |
| `drift`   | 時刻は追いついているが見出しの数が違う | 原本と訳を節ごとに突き合わせて構造をそろえる。**訳にしか無い節・記述は消す**（原本が正） |
| `orphan`  | 訳の側にだけある                       | 訳さない。原本を消したのか、英語で書き起こしてしまったのかを利用者に確かめる             |

「新しい」は最終変更の時刻で比べる。未コミットの変更があればファイルの更新時刻、無ければ最後のコミットの時刻。

時刻だけでは、原本と訳を同じコミットで触った組のずれ（最後に同期したときに既にずれていたもの）が見えない。`drift`
はそれを拾うための2つめの目で、Markdown の見出しの数をコードブロックの外だけで数えて比べる。

`stale` の原本がどう変わったかは、スクリプトが出す `base`（訳を最後に変えたコミット）から読む。

```shell
git diff <base> -- <原本のパス>
```

作業ツリーの未コミットの変更も含めて出る。

### 2. 対象ファイルを英語ドキュメントに翻訳する

**差分だけを反映する。**`stale` のときに訳を丸ごと書き直すと、以前の訳で決めた言い回しや、訳の側で直した誤りが消える。
`missing` のときだけ全体を訳す。

守ること:

- **節の構成・順序・表の行は原本と1対1。**英語側だけに節を足さない
- **原本の `TODO` は訳でも `TODO` のまま残す。**MDX コメント（`{/* TODO ... */}`）の中身は英語に訳す。埋めるのは原本が先
- **コードブロックの中の日本語も訳す**（制約名の文字列、コメント、`example()` の説明など）。訳さないと英語ページに日本語が出る
    - katachi が出力する固定の文字列（生成ドキュメントの見出し `## Placement` `## Constraints` `## Examples`、表の見出し
      `Role | Summary` など）は英語で、原本にも英語で書いてある。訳の側もそのまま写す
- コマンド、API 名、ファイルパス、コードの識別子は変えない
- リンクは日本語版の `/katachi/ja/...` を英語版の `/katachi/...` に変える
- frontmatter の `title` / `description` も訳す
- 未使用の import のような、明らかな無駄は写さなくてよい
- **原本が間違っていると気づいたら、訳さずに利用者に知らせる。**誤りを2言語に増やさない

`docs/public/install/` の追加の決まり:

- `index.md` は、AI エージェントがそのまま実行する手順書。コマンドは1文字も変えない。ただし、実行させるコマンドの
  `--lang ja` は `--lang en` にし、`install/ja/` への URL は `install/en/` にする（「日本語なら `--lang ja`
  」のように選択肢を説明する文はそのまま）
- `*.html` は、表示の文言だけを訳す。埋め込まれた JSON のキー、項目の `id`、`data-*` 属性、スクリプトは変えない。項目の
  `label` は訳す（手順書は項目を `check 1-1` のように `id` で指しているので、`label` の文言はつながっていない）

進め方:

- 対象が複数あるときは、**1ファイルにつき1体の subagent（model: sonnet）**に並行で任せる。渡すものは次の4つ
    - 原本と訳のパス
    - `base`
    - `git diff` の出力
    - この節の決まり
- `docs/src/` は利用者が IDE で同時に編集していることがある。ファイル全体を読んで書き戻すより、該当箇所だけを書き換える。書く直前にファイルが変わっていたら読み直す

### 3. 確かめる

```shell
# 1. 訳し直しが要るものが残っていないこと
python3 .claude/skills/translate-ja-en/scripts/list-targets.py

# 2. 節の数が原本と訳で一致していること（訳したファイルごとに）
grep -c '^#' <原本> <訳>

# 3. ドキュメントサイトがビルドできること（リンク検査を含む）
cd docs && pnpm run build
```

`docs/public/install/` の `index.md` は、ビルドの対象ではない（加工されずに配信される）。2 の節の数の一致で確かめる。

1 で `stale` が残っていて、原本と訳の中身が既に一致しているときは、訳の側を変えていない（時刻で比べているため）。訳を直したのに残る場合は、訳のファイルを保存し直したか確かめる。
