KATACHI-86調査: SARIF の GitHub 受理・PR 注釈・reviewdog の実確認

docs の GitHub レシピは「SARIF を上げれば PR に注釈が付く」と書くが、注釈の見え方と reviewdog で読めるかを 1 回通して確かめた記録が無い

今
ci.yml: upload-sarif で :architecture-test の SARIF を code scanning へ（dogfooding）V5: PR の該当行に注釈がどう見えるか     → 確認の記録が見つからないV6: reviewdog（-f=sarif）で読めるか       → 未確認V4: GitHub が受け付けるか → CI のアップロードが通っていれば実質確認済み（推測）
やること
1. わざと違反を入れた PR を開き、Files changed の注釈をスクショ2. reviewdog を手元で通し、コメントの見え方を確かめる3. 結果を docs のレシピと照らし、ずれがあれば提案（docs は人が書く）
リスク・デメリット
  • 利用者確認しないまま、注釈の位置がずれる・message が長すぎて切れる、などに利用者が先に気づく
  • ライブラリわざと違反を入れた PR はマージしない運用が要る。reviewdog は依存が増えるので CI には入れず手元の確認だけにする
